# RRA-017: Row-Level Security Beneath the RRA Scope

**Authority:** this document governs from the commit in which the sole owner merges it to `main`
(`governance/CONSTITUTION.md` §II); before that merge it is a proposal. Its state is the
`governance/registry.yaml` row, not this line. It was drafted by automation, which "checks facts and
consistency; it does not approve changes or act as a separate authority" (§I).

Every code citation below was verified at `main` `4276814`.

## Outcome

When implemented, a unit of work acting for one RRA scope cannot read or write another scope's
rows **at the database**, for the tables this specification covers. The wall does not depend on
the application's own scoping predicates (`FR-236`), but it does depend on the application setting
the right scope per unit of work (`FR-233`): a wrong setting is a wrong scope. A PostgreSQL test
running as the application role proves it.

Which tables that is stays open until the owner decides Open item 4: `FR-230` names the tables with
an `owner_id` column, and whether the scope-owned tables without one (`FR-231`) are walled, and how,
is item 4's. Nothing here claims those tables are walled.

**What the wall does not hide.** PostgreSQL runs referential-integrity and uniqueness checks without
row security. A write that collides with another scope's key, or names another scope's parent, can
therefore fail differently from one that does not, which tells the writer the other row exists. The
Outcome is about reading and writing rows, not about that existence signal, and this specification
does not claim to close it.

## Why this artifact exists

`KHEPRI-DEC-035` §1 selects PostgreSQL row-level security as the only admissible shape for
anchoring the RRA scope in the database, §2 states what it must cover, and §4 makes it,
implemented and verified, a precondition of beta authorization. §5 then refuses to stand in for the
requirement: "The slice that implements §2 first lands the requirement it builds against, in
`RRA-001` or a successor." This is that requirement. `#595` tracks it.

**Successor, not amendment.** `RRA-001` is a closed, 32-line requirement set for invitations and
sessions. Row-level security crosses every RRA table that carries `owner_id`, changes the runtime's
database connection model, and needs its own exclusions and verification. Folding it into
`RRA-001` would widen that artifact's outcome ("one isolated, pseudonymous session") into an
operations boundary it never named. `RRA-001` stays `active` and unedited; nothing here narrows its
application-level isolation requirement ("fail closed on cross-session access").

## Implementation is blocked

This requirement can merge with its open items open. **No implementing slice starts until a merged
amendment to `RRA-017`, or a decision it cites, resolves each of Open items 2, 3, 4 and 5.** Each
blocks independently; resolving some does not admit a partial slice.

Item 3 is the most severe. Without it, enabling the policies empties the one read every beta
request uses to learn its scope, and at least one caller of that read then **fails open** rather
than closed (`FR-238`). The others make the wall incomplete; item 3 can make it admit what it
should refuse.

Item 1 does not block the RRA slice; it bounds what this specification covers. Item 6 does not
block.

## Requirements

- **FR-230 — Coverage by property.** Every `khepri.rra` table that carries an `owner_id` column has
  row-level security enabled **and forced** (`ALTER TABLE … ENABLE ROW LEVEL SECURITY` and
  `… FORCE ROW LEVEL SECURITY`). The covered set is defined by that property, not by a list, so a
  table added later with `owner_id` is either covered or fails the coverage test. The table extent
  is derived twice, once from the metadata after importing every module under `khepri.rra`
  (`pkgutil.walk_packages`) and once from the migrated catalogue, and the two must agree
  (Verification 11). Importing only `khepri.rra.persistence` is not enough:
  `rra_operational_events` joins the metadata only when `khepri.rra.telemetry_persistence` is
  imported.
- **FR-231 — Tables without `owner_id` are enumerated, not assumed.** Five `khepri.rra` tables carry
  no `owner_id`:

  | Table | Reached through | Holds |
  |---|---|---|
  | `rra_report_job_attempts` | `(job_id, session_id)` → `rra_report_jobs` (`fk_job_attempt_job_scope`) | per-attempt dispositions of one scope's job |
  | `rra_report_delivery_surfaces` | `(job_id, bundle_id)` → `rra_report_deliveries` (`fk_delivery_surface_bundle`) | per-surface content digests of one scope's report |
  | `rra_operational_events` | `(job_id, session_id)` → `rra_report_jobs` (`fk_operational_event_job_scope`) | content-free stage telemetry of one scope's job |
  | `rra_deletion_evidence` | `deletion_id` → `rra_deletion_jobs` (`fk_evidence_deletion`) | location and content digests of one scope's deleted objects |
  | `rra_invitations` | nothing; no session, owner or scope column | salted secret hashes and expiry only |

  The first four are **scope-owned**: every row belongs to exactly one scope through its parent.
  `rra_invitations` is **pre-scope**: it is read at redemption before any `owner_id` exists
  (`RRA-001`, "Redeeming a valid invitation creates an opaque owner ID"), and no row references a
  scope. A foreign key does not carry the parent's policy: PostgreSQL runs referential-integrity
  checks without row security, so a scope-owned child without a policy of its own is readable and
  writable across scopes by any role that can reach it. How the four are walled is Open item 4.
  A table added later without `owner_id` is a defect until it is classified here (Verification 9,
  over the extent Verification 11 derives).
- **FR-232 — Policy.** Each covered table has a policy whose `USING` and `WITH CHECK` both compare
  `owner_id` with the unit of work's scope setting, so `SELECT`, `UPDATE` and `DELETE` see only the
  scope's rows and `INSERT` or `UPDATE` cannot write a row naming another scope. **An unset or empty
  setting matches nothing** (Constitution V), **including a row whose `owner_id` is itself empty.**
  The property binds, not a mechanism: on a pooled connection that earlier ran `SET LOCAL`, a
  missing-setting read returns an empty string rather than `NULL`, so a policy of the form
  `owner_id = current_setting(…, true)` alone matches a row whose `owner_id` is `''` and does not
  satisfy this requirement. Whether an `owner_id <> ''` CHECK is added as well is Open item 6.
- **FR-233 — Per-unit-of-work scope.** The scope setting is established with `SET LOCAL`, the
  mechanism `KHEPRI-DEC-035` §1 names, inside every transaction that touches a covered table, from
  the scope the application has already resolved. It never survives the transaction. Redemption,
  which mints a new `owner_id`, sets that scope before inserting the session row. How a request
  that knows only its `session_id` learns the scope to set is Open item 3. Verified by
  Verification 12.
- **FR-234 — Application role.** The runtime connects as a role that does not own the covered
  tables, is not a superuser, and does not hold `BYPASSRLS`. A test asserts all three against the
  catalogue.
- **FR-235 — Cross-scope uses, enumerated pass by pass.** Migrations, and the deletion and retention
  sweeps that must cross scopes (`KHEPRI-DEC-035` §2's list, and only that list), run under a
  separately named role. The sweeps exist to meet `RRA-002`'s seven-day deletion and
  `KHEPRI-DEC-033`'s horizons, and this requirement does not weaken either. How that role crosses
  the policies, whether migrations and sweeps share it, and whether it is held per process or per
  component is Open item 5. **The rows below marked "conditional on item 5" hold only if item 5's
  answer keeps the sweep's per-session and per-owner work off the cross-scope role.** Today
  `khepri.runtime.wiring.build_retention_sweep` hands one `stack.factory` and
  `stack.services.deletion` to every pass, so a per-process role would not. Item 5's answer must
  therefore amend this table and Verification 7. Admission is by **pass**, not by entry point,
  because one entry point runs passes this list does not admit:

  | Entry point and pass | Cross-scope read | Status |
  |---|---|---|
  | `khepri.runtime.retention_sweep.RetentionSweeper.sweep`, pass `PASS_EXPIRED_SESSIONS` | `_expired_session_ids`, which lists expired sessions across all scopes | **admitted** for the listing only, **conditional on item 5**. Each session is then deleted by `_expire_sessions` through `DeletionService.delete_session_content`, one call per session, with **that session's `owner_id` set** — the same deletion the request route runs, not a cross-scope write. The listing must therefore also yield each session's `owner_id` |
  | same, `RetentionPasses` pass `raw_uploads`: `khepri.runtime.workspace_retention.RawUploadRetentionSweeper.sweep` | `_due`, which selects due `rra_uploads` rows across all scopes | **admitted** for `_due` only, **conditional on item 5**. `_purge_scope` and `_delete_row` then act per `owner_id` with that `owner_id` set |
  | same, `RetentionPasses` pass `evidence`: `khepri.rra.evidence_retention.DeletionEvidenceSweeper.sweep` | purges `rra_deletion_evidence` by horizon across all scopes | **conditional on Open item 4.** If item 4 leaves `rra_deletion_evidence` without a policy, the pass needs no cross-scope role; if it adds one, the pass is admitted |
  | same, pass `PASS_EXPIRED_LEASES` (`recover_expired`) and pass `PASS_ORPHANED_JOBS` (`recover_orphans`) | job recovery across all scopes | **not admitted.** Open item 2, wherever called |
  | same, `RetentionPasses`' RCA passes (accounts, membership events, commercial sessions, invitations, recovery events, workspace audit) | RCA tables | outside this specification (Open item 1) |

  Three paths that reach RRA tables are **not** cross-scope and run under the application role with
  a scope set:
  - `DeletionService.delete_session_content` reached from the request route
    (`DELETE /api/v1/beta/content`, `khepri.rra.api`), acting for the requesting session's scope;
  - `khepri.runtime.workspace_deletion.WorkspaceDeletion`, which reads `rra_uploads` by
    `(owner_id, ciphertext digest)` and the run-linked `rra_report_jobs` rows in
    `_sessions_of_version`, then calls `delete_session_content` per session in
    `_end_derived_content`, all with the **organization's** `owner_id` set;
  - `khepri.runtime.workspace_retention.retain_workspace_content`, called from
    `khepri.runtime.workspace_recording` through the RCA factory, which updates `rra_uploads`,
    `rra_report_deliveries` and `rra_report_artifacts` by `(owner_id, session_id)`, with that
    `owner_id` set.

  The first two still reach `delete_session_content`'s own unscoped session read, which is Open item 3's.
  An unenumerated cross-scope use is a defect, and any other path found to cross scopes is
  reported, not admitted to that role.
- **FR-236 — Application isolation stays.** `IsolationService.resolve_scope` on the commercial
  path (`RCA-001`), and RRA's own owner-scoped verbs — `get_session_for_owner`,
  `get_upload_for_scope`, `get_profile_for_scope`, `get_package_for_scope` and the other
  `(owner_id, session_id)` predicates in `khepri.rra.persistence` — remain required and unchanged
  in meaning. Row-level security is an additional wall beneath them, not a replacement; no scoping
  predicate is removed from application code because a policy now enforces it.
- **FR-237 — Module boundary.** `R7-01` holds: `khepri.rca` and `khepri.rra` do not import each
  other. Policies and roles are composed in Alembic migrations and `khepri.runtime`, not by one
  package reaching into the other's metadata. The existing import tests are its verification:
  `tests/test_r707_commercial_bridge.py`
  (`test_khepri_rca_imports_no_khepri_rra_module`, `test_khepri_rra_imports_no_khepri_rca_module`)
  and `tests/test_rca001_boundary.py` (`test_no_rra_module_imports_rca`).
- **FR-238 — A read the policy can empty never admits.** No guard or recorder may treat an empty
  read **run without the unit's scope set**, where row-level security can therefore be the reason
  it is empty, as permission or as "nothing to
  do". Two callers are named at `main`:
  - `khepri.runtime.beta_membership_guard.BetaMembershipGuard.admits` returns `True` when
    `_owning_organization` returns `None`. That happens on **two** reads: `sessions.get_session`
    returning nothing, and `SqlIsolationScopes.organization_of` returning nothing. Today both
    `None`s are legitimate (no cookie; a beta scope no organization owns, where the route decides).
    Under row-level security the first can also mean "the policy hid the session", and if Open
    item 1 brings `rca_isolation_scopes` under a policy, so can the second. The guard must refuse,
    not admit, when either read is empty for that reason.
  - `khepri.runtime.pipeline_recording.PipelineRecorder._workspace_of` returns `None` when its
    `get_session` read is empty, and also when `_scopes.exists(session.owner_id)` is false, a read
    of `rca_isolation_scopes` that Open item 1 could bring under a policy. `admitted` then records no version and `requested` starts no run.
    It runs on request paths: `RecordingProfilingService.profile_session_upload` and
    `RecordingReportRequests.request_session_report`. A hidden session would degrade silently to
    "not a workspace", and the workspace would miss the version and the run without any error.

  **When the guard's fail-open is reachable.** Only if Open item 3's mechanism lets the route
  handlers read the session while the guard's own read still runs without a scope. If both read
  nothing, the request fails closed downstream as an unavailable session. This requirement binds
  whichever mechanism is chosen, so the reachability does not depend on getting that choice right.

## Exclusions

This specification does not authorize:

- row-level security on any `khepri.rca` table (Open item 1);
- running any pass not admitted in `FR-235` under the cross-scope role (Open item 2);
- a foreign key onto `rca_isolation_scopes`, or a CHECK or trigger that consults another table,
  from any RRA table: `KHEPRI-DEC-035` §1 refuses both;
- a change to any scope, identity, session or consent rule of `RRA-001`. The unscoped `session_id`
  lookups `#152` holds stay `#152`'s to fix; but row-level security **changes what they return**
  (nothing, with no scope set), so the implementing slice may not treat them as untouched. Open
  item 3 governs that change;
- a new data use, field, table or telemetry event, beyond the roles, policies and settings above.
  Adding `owner_id` to a table is one of Open item 4's options and needs the owner's decision
  first;
- selecting the secret source, provider or hosted environment for the roles' credentials; that
  remains `OPS1`'s and `KHEPRI-DEC-028`'s;
- beta authorization itself. Satisfying this specification discharges one gate of
  `KHEPRI-DEC-035` §4 and nothing in `KHEPRI-DEC-030` §6.

## Open items for the owner

These are raised, not decided.

1. **Do RCA tables take the same policy?** The `#595` owner decision (2026-09-26) says "RLS enabled
   on tenant-owned data", which reads broader than RRA. `KHEPRI-DEC-035` §5 decides only RRA and
   leaves RCA open: "Whether RCA tables take the same policy is not decided here, and nothing here
   excludes it." This specification therefore covers RRA only and does not decide RCA. If RCA is
   in, it needs its own requirement (RCA family), because RCA's scope key and cross-scope paths
   differ. It would also make `organization_of`'s empty read policy-dependent (`FR-238`).
2. **How does the report-job claim and its recovery run?** `rra_report_jobs` carries `owner_id`, so
   `FR-230` covers it. `FR-230` covers only tables with `owner_id`. The tables whose rows reach
   `rra_report_jobs` by foreign key are `rra_report_job_attempts` and `rra_operational_events`
   directly (no `owner_id`; Open item 4), `rra_report_deliveries` directly (covered in its own
   right), and, through `rra_report_deliveries`, `rra_report_delivery_surfaces` (item 4) and
   `rra_report_artifacts` (covered). These operations select across all scopes before they know whose job
   it is:

   | Operation | Lock it takes | Call sites |
   |---|---|---|
   | `khepri.rra.job_persistence.next_claimable_statement` | none: a plain `SELECT … LIMIT 1` | `khepri.rra.claim_queue.ClaimingReportQueue._next_claimable`; `khepri.local.worker.ClaimablePoller.next_job_id` |
   | `SqlReportJobRepository.lease` | `FOR UPDATE` on the one named job | `ClaimingReportQueue.receive`; `khepri.rra.worker.ReportWorker.process`; `khepri.runtime.pipeline_recording.SettlingJobStore.lease` |
   | `SqlReportJobRepository.recover_expired` | `FOR UPDATE SKIP LOCKED` | `ClaimingReportQueue.recover`, reached from `khepri.runtime.worker.ClaimWorkerLoop` before every claim; `SettlingJobStore.recover_expired`; `RetentionSweeper.sweep` (`PASS_EXPIRED_LEASES`) |
   | `SqlReportJobRepository.recover_orphans` | `FOR UPDATE SKIP LOCKED` | `SettlingJobStore.recover_orphans`; `RetentionSweeper.sweep` (`PASS_ORPHANED_JOBS`) |

   Under a scoped application role each would see nothing; `lease` is included because the worker
   names a job before it knows the job's scope. `KHEPRI-DEC-035` §2 names only migrations and the
   sweeps as cross-scope uses. Whether these join that list, or are restructured (for example a
   claim that returns only an opaque job identifier through a narrowly granted function, after
   which the worker sets the job's scope), is the owner's, and the implementing slice may not
   choose it. Whichever is chosen must preserve `RRA-007`'s restart recovery and orphan detection.
3. **How is a session's scope resolved before any scope is set?** A beta request carries only its
   `session_id` cookie and learns its `owner_id` from the unscoped
   `SqlSessionStore.get_session(session_id)` read on `rra_beta_sessions`
   (`khepri.rra.persistence`). Its callers are `khepri.rra.datasets` (two), `khepri.rra.intake`,
   `khepri.rra.packages` (two), `khepri.rra.deletion`, `khepri.rra.sessions` (two),
   `khepri.runtime.pipeline_recording` (`_workspace_of`), and
   `khepri.runtime.beta_membership_guard` (`_owning_organization`). Under
   `FORCE ROW LEVEL SECURITY` with no setting, every one of those reads returns nothing. Most
   callers then fail closed, as an unavailable session. Two do not: the membership guard fails open
   and `_workspace_of` degrades silently (`FR-238`). Candidate mechanisms, none chosen here:
   - a narrow `SECURITY DEFINER` lookup that returns only the `owner_id` for one `session_id`;
   - carrying the owner in the session credential so the scope is known before the first read.
     This **changes the session credential `RRA-001` governs**, so it would need a merged
     `RRA-001` amendment first;
   - a dedicated resolution role with `SELECT` on `(session_id, owner_id)` only.

   Whatever is chosen must satisfy `FR-238`. **This item blocks implementation.**
4. **How are the four scope-owned tables without `owner_id` walled?** `FR-231` names them. Options,
   none chosen here:
   - a policy that derives the scope from the parent: an `EXISTS` on the parent row, which the
     parent's own policy then filters;
   - adding an `owner_id` column to each, which is a schema change and a new field under this
     specification's exclusions;
   - narrowing the Outcome permanently to tables with `owner_id` and accepting the children as
     reachable only through application code.

   Verification 1 extends to them once this is decided.
5. **How does the cross-scope role cross the policies, and who holds it?**
   - *Mechanism*, none chosen here: the role holds `BYPASSRLS`; the role owns the tables, which
     `FORCE ROW LEVEL SECURITY` would still subject to policy unless combined with another option;
     or a permissive policy granted to that role only. Each differs in what a leaked credential
     for that role exposes.
   - *Migrations and sweeps*: whether they share one role. If they do, the sweep process's
     credential also carries DDL rights.
   - *Per process or per component*: `khepri.runtime.wiring.build_retention_sweep` builds every
     sweep from one `stack.factory` and shares `stack.services.deletion` with the request path,
     and passes that factory to the RCA sweepers as well. `khepri.local.wiring` composes the same
     way. A per-process cross-scope role would therefore reach the RCA sweepers and the deletion
     service; a per-component role needs a second engine in the composition root. **Item 5's answer
   must amend `FR-235`'s admission table and Verification 7**, whose "conditional on item 5" rows
   and recipient rule assume the per-component answer.
6. **Is an `owner_id <> ''` CHECK added to each covered table?** It would make `FR-232`'s empty-owner
   case unrepresentable rather than only unreadable. It is a single-column constraint that consults
   no other table, so it is not `KHEPRI-DEC-035` §1's refused shape 2, which is a CHECK or trigger
   standing in for the scope anchor. It does not replace `FR-232`. If adopted, Verification 4's
   `''` seed becomes an assertion that the CHECK exists on every covered table. Non-blocking.

## Verification

Items 1 to 6, 12 and 13 run against PostgreSQL, not SQLite, connected **as the application role**
of `FR-234`, in tests carrying the `concurrency` marker so
`.github/scripts/require_concurrency_tests.py` fails the build if they skip in CI. Items 7, 9, 10
and 11 inspect the code, the metadata or the catalogue; item 8 runs where it says.

"Refused" has one meaning throughout:
- for `INSERT`, an error with SQLSTATE `42501` (`insufficient_privilege`, row-level security's
  refusal), not `23503` (foreign-key violation);
- for `UPDATE` and `DELETE`, zero rows affected.

1. **Positive and negative control.** In every covered table, with rows seeded for both A and B, a
   unit of work scoped to A reads and writes A's rows and reads none of B's. The positive half
   defeats a `USING (false)` policy. The same holds for the tables Open item 4 brings under the
   wall once it is decided.
2. Inserting a session or child row whose `owner_id` differs from the setting is refused. So is
   inserting one whose `owner_id` is `''` while the setting is empty. B's parent
   `rra_beta_sessions` row **exists** when the child insert is attempted, so the refusal is
   row-level security's (`42501`) and cannot be a foreign-key violation (`23503`).
3. With B's rows existing, `UPDATE` and `DELETE` scoped to A affect zero of them. With B's parent
   session existing, an `UPDATE` that re-points one of A's rows' `owner_id` to B is refused.
4. **Empty-setting case, with an empty-owner row present.**
   - In each covered table the test first seeds, as the migration role, a row whose `owner_id` is
     `''`.
   - It pins **one physical connection** and runs a scoped transaction on it.
   - It asserts the same `pg_backend_pid()` before and after, then opens a transaction with no
     setting. That transaction reads zero rows and has every write refused.

   Without the seeded row a naive `owner_id = current_setting(…)` policy would pass this test, so
   the seed is required, not illustrative. If Open item 6 adopts the CHECK, the seed becomes an
   assertion that the CHECK exists.
5. `FR-238`: with row-level security enabled and the session hidden from the reading role,
   `BetaMembershipGuard.admits` **refuses**. `_workspace_of` either resolves the scope or fails
   loudly, and never returns `None`, whatever mechanism Open item 3 selects. If Open item 1 brings
   `rca_isolation_scopes` under a policy, the same holds for the guard's `organization_of` read and
   `_workspace_of`'s `_scopes.exists` read.
6. The coverage test of `FR-230` and the role test of `FR-234`.
7. **Cross-scope recipients.** A test finds **every composition root by construction**. It sweeps
   every module under `src/khepri` for code that builds an engine or session factory, which
   includes `khepri.runtime.wiring` and `khepri.local.wiring`. The sweep is anchored on the
   installed package's path, not the working directory.
   - The test derives every component that receives the cross-scope role's engine or credential,
     and compares that set with `FR-235`'s admitted passes.
   - A recipient not on the list fails, and so does an admitted pass that receives the application
     engine.
   - RCA components are **recipients like any other**. An RCA sweeper handed the cross-scope
     credential gains nothing on RCA tables, which carry no RRA policy, but it holds a credential
     that crosses RRA's, so it fails unless enumerated.

   This rule is **conditional on Open item 5**, and item 5's answer amends it.
8. **The application-isolation suite runs where no policy can mask it.** The existing suite that
   `FR-236` keeps runs unchanged with row-level security absent: on SQLite as it runs today, or on
   PostgreSQL as a table-owner role without `FORCE`. A scoping predicate removed from application
   code therefore fails it, rather than being hidden by the policy beneath.
9. **Classification.** The tables without `owner_id`, in the extent Verification 11 derives, equal
   `FR-231`'s list exactly.
10. `FR-237`'s import tests still pass.
11. **Extent.** Importing every module under `khepri.rra` yields a set of `khepri.rra` tables. That
    set equals the set in the migrated catalogue.
12. **`FR-233`.** Every transaction that touches a covered table sets the scope with `SET LOCAL`.
    The setting is gone in the next transaction on the same physical connection.
13. **The RRA route and store suites run as the application role under `FORCE`.** They pass with
    row-level security enabled and a connection as the `FR-234` role. This shows the wall does not
    break the paths it sits beneath.

## Route-level harness

- **FR-239 — One PostgreSQL journey harness.** Route-level tests for this specification, including
  Verification 5 and 13, reuse the PostgreSQL-backed journey harness `#388` introduces. They do not
  build a second one. If that harness has not landed when the implementing slice opens, the slice
  waits for it or lands it first under `#388`'s own authority.

Row-level security changes the connection model as well as the schema, so the implementing slice
coordinates with `OPS1`'s environment work (`KHEPRI-DEC-035` Consequences).
