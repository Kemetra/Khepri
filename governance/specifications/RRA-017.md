# RRA-017: Row-Level Security Beneath the RRA Scope

**Authority:** this document governs from the commit in which the sole owner merges it to `main`
(`governance/CONSTITUTION.md` §II); before that merge it is a proposal. Its state is the
`governance/registry.yaml` row, not this line. It was drafted by automation, which "checks facts and
consistency; it does not approve changes or act as a separate authority" (§I).

Every code citation below was verified at `main` `4276814`. The `#595` amendment (§Open items 2 to
5, resolved, and the edits it makes elsewhere) was verified at `main` `11ac802`.

## Outcome

When implemented, a unit of work acting for one RRA scope cannot read or write another scope's
rows **at the database**, for the tables this specification covers. The wall does not depend on
the application's own scoping predicates (`FR-236`), but it does depend on the application setting
the right scope per unit of work (`FR-233`): a wrong setting is a wrong scope. A PostgreSQL test
running as the application role proves it.

The covered tables are `FR-230`'s, which carry an `owner_id` column, and the four scope-owned
tables without one that `FR-231` names, which `FR-269` walls through their parents.
`rra_invitations` is pre-scope (`FR-231`) and carries no policy.

**What the wall does not hide.** PostgreSQL runs referential-integrity and uniqueness checks without
row security. A write that collides with another scope's key, or names another scope's parent, can
therefore fail differently from one that does not, which tells the writer the other row exists. The
Outcome is about reading and writing rows, not about that existence signal, and this specification
does not claim to close it.

## Why this artifact exists

`KHEPRI-DEC-035` §1 selects PostgreSQL row-level security as the only admissible shape for
anchoring the RRA scope in the database, §2 states what it must cover, and §4 makes it,
implemented and verified, a precondition of beta authorization. §5 then refuses to stand in for the
requirement: "The slice that implements §2 first lands the requirement it builds against, in
`RRA-001` or a successor." This is that requirement. `#595` tracks it.

**Successor, not amendment.** `RRA-001` is a closed, 32-line requirement set for invitations and
sessions. Row-level security crosses every RRA table that carries `owner_id`, changes the runtime's
database connection model, and needs its own exclusions and verification. Folding it into
`RRA-001` would widen that artifact's outcome ("one isolated, pseudonymous session") into an
operations boundary it never named. `RRA-001` stays `active` and unedited; nothing here narrows its
application-level isolation requirement ("fail closed on cross-session access").

## Requirements

- **FR-230 — Coverage by property.** Every `khepri.rra` table that carries an `owner_id` column has
  row-level security enabled **and forced** (`ALTER TABLE … ENABLE ROW LEVEL SECURITY` and
  `… FORCE ROW LEVEL SECURITY`). The covered set is defined by that property, not by a list, so a
  table added later with `owner_id` is either covered or fails the coverage test. The table extent
  is derived twice, once from the metadata after importing every module under `khepri.rra`
  (`pkgutil.walk_packages`) and once from the migrated catalogue, and the two must agree
  (Verification 11). Importing only `khepri.rra.persistence` is not enough:
  `rra_operational_events` joins the metadata only when `khepri.rra.telemetry_persistence` is
  imported.
- **FR-231 — Tables without `owner_id` are enumerated, not assumed.** Five `khepri.rra` tables carry
  no `owner_id`:

  | Table | Reached through | Holds |
  |---|---|---|
  | `rra_report_job_attempts` | `(job_id, session_id)` → `rra_report_jobs` (`fk_job_attempt_job_scope`) | per-attempt dispositions of one scope's job |
  | `rra_report_delivery_surfaces` | `(job_id, bundle_id)` → `rra_report_deliveries` (`fk_delivery_surface_bundle`) | per-surface content digests of one scope's report |
  | `rra_operational_events` | `(job_id, session_id)` → `rra_report_jobs` (`fk_operational_event_job_scope`) | content-free stage telemetry of one scope's job |
  | `rra_deletion_evidence` | `deletion_id` → `rra_deletion_jobs` (`fk_evidence_deletion`) | location and content digests of one scope's deleted objects |
  | `rra_invitations` | nothing; no session, owner or scope column | salted secret hashes and expiry only |

  The first four are **scope-owned**: every row belongs to exactly one scope through its parent.
  `rra_invitations` is **pre-scope**: it is read at redemption before any `owner_id` exists
  (`RRA-001`, "Redeeming a valid invitation creates an opaque owner ID"), and no row references a
  scope. A foreign key does not carry the parent's policy: PostgreSQL runs referential-integrity
  checks without row security, so a scope-owned child without a policy of its own is readable and
  writable across scopes by any role that can reach it. `FR-269` walls the four.
  A table added later without `owner_id` is a defect until it is classified here (Verification 9,
  over the extent Verification 11 derives).
- **FR-232 — Policy.** Each covered table has a policy whose `USING` and `WITH CHECK` both compare
  `owner_id` with the unit of work's scope setting, so `SELECT`, `UPDATE` and `DELETE` see only the
  scope's rows and `INSERT` or `UPDATE` cannot write a row naming another scope. **An unset or empty
  setting matches nothing** (Constitution V), **including a row whose `owner_id` is itself empty.**
  The property binds, not a mechanism: on a pooled connection that earlier ran `SET LOCAL`, a
  missing-setting read returns an empty string rather than `NULL`, so a policy of the form
  `owner_id = current_setting(…, true)` alone matches a row whose `owner_id` is `''` and does not
  satisfy this requirement. The policy applies to the application and worker roles (`FR-270`).
  Whether an `owner_id <> ''` CHECK is added as well is Open item 6.
- **FR-233 — Per-unit-of-work scope.** The scope setting is established with `SET LOCAL`, the
  mechanism `KHEPRI-DEC-035` §1 names, inside every transaction that touches a covered table, from
  the scope the application has already resolved. It never survives the transaction. Redemption,
  which mints a new `owner_id`, sets that scope before inserting the session row. A request that
  knows only its `session_id` learns the scope to set from `FR-265`'s lookup. Verified by
  Verification 12.
- **FR-234 — Runtime roles.** The runtime connects only as the application, worker and sweep roles
  of `FR-270`, and every composition root connects as exactly the role `FR-270` names for it. None of them owns any table, function or other object, is a superuser, or holds
  `BYPASSRLS`, `CREATEROLE`, `CREATEDB`, or `CREATE` on the database or on any schema, so no runtime
  process holds a DDL right or bypasses row security. A test asserts every one of those properties
  against the catalogue, for each of the three roles.
- **FR-235 — Cross-scope uses, enumerated pass by pass.** Migrations, and the deletion and retention
  sweeps that must cross scopes (`KHEPRI-DEC-035` §2's list, and only that list), run under
  separately named roles: migrations under the migration owner, and the sweeps' cross-scope reads
  under the sweep role (`FR-270`). The sweeps exist to meet `RRA-002`'s seven-day deletion and
  `KHEPRI-DEC-033`'s horizons, and this requirement does not weaken either. `FR-271` says how the
  sweep role crosses the policies and which components hold it: per component, never per process,
  and never shared with migrations. Today `khepri.runtime.wiring.build_retention_sweep` hands one
  `stack.factory` and `stack.services.deletion` to every pass, and `FR-271` replaces that
  composition. Admission is by **pass**, not by entry point, because one entry point runs passes
  this list does not admit:

  | Entry point and pass | Cross-scope read | Status |
  |---|---|---|
  | `khepri.runtime.retention_sweep.RetentionSweeper.sweep`, pass `PASS_EXPIRED_SESSIONS` | `_expired_session_ids`, which lists expired sessions across all scopes | **admitted** for the listing only, on the sweep engine (`FR-271`). The listing also yields each session's `owner_id`. Each session is then deleted by `_expire_sessions` through the sweep's own `DeletionService` over the scoped engine, one call per session, with **that session's `owner_id` set**: the same deletion the request route runs, not a cross-scope write |
  | same, `RetentionPasses` pass `raw_uploads`: `khepri.runtime.workspace_retention.RawUploadRetentionSweeper.sweep` | `_due`, which selects due `rra_uploads` rows across all scopes | **admitted** for `_due` only, on the sweep engine. `_purge_scope` and `_delete_row` then act per `owner_id` on the scoped engine, with that `owner_id` set |
  | same, `RetentionPasses` pass `evidence`: `khepri.rra.evidence_retention.DeletionEvidenceSweeper.sweep` | purges `rra_deletion_evidence` by horizon across all scopes | **admitted**, on the sweep engine. `FR-269` brings the table under a policy, so the purge needs `FR-271`'s sweep policy |
  | same, pass `PASS_EXPIRED_LEASES` (`recover_expired`) and pass `PASS_ORPHANED_JOBS` (`recover_orphans`) | job recovery across all scopes | **no cross-scope policy.** The candidates come from `FR-267`'s two recovery functions, called on the sweep engine. Each transition runs on the scoped engine with the job's `owner_id` set (`FR-268`) |
  | same, `RetentionPasses`' RCA passes (accounts, membership events, commercial sessions, invitations, recovery events, workspace audit) | RCA tables | outside this specification (Open item 1). They run on the scoped engine and never receive the sweep engine |

  Three paths that reach RRA tables are **not** cross-scope and run under the application role with
  a scope set:
  - `DeletionService.delete_session_content` reached from the request route
    (`DELETE /api/v1/beta/content`, `khepri.rra.api`), acting for the requesting session's scope;
  - `khepri.runtime.workspace_deletion.WorkspaceDeletion`, which reads `rra_uploads` by
    `(owner_id, ciphertext digest)` and the run-linked `rra_report_jobs` rows in
    `_sessions_of_version`, then calls `delete_session_content` per session in
    `_end_derived_content`, all with the **organization's** `owner_id` set;
  - `khepri.runtime.workspace_retention.retain_workspace_content`, called from
    `khepri.runtime.workspace_recording` through the RCA factory, which updates `rra_uploads`,
    `rra_report_deliveries` and `rra_report_artifacts` by `(owner_id, session_id)`, with that
    `owner_id` set.

  The first two, and the sweep's per-session deletion, reach `delete_session_content`'s own session
  read with their caller's scope already set, so under `FR-265` it is a scoped read.
  An unenumerated cross-scope use is a defect, and any other path found to cross scopes is
  reported, not admitted to that role.
- **FR-236 — Application isolation stays.** `IsolationService.resolve_scope` on the commercial
  path (`RCA-001`), and RRA's own owner-scoped verbs — `get_session_for_owner`,
  `get_upload_for_scope`, `get_profile_for_scope`, `get_package_for_scope` and the other
  `(owner_id, session_id)` predicates in `khepri.rra.persistence` — remain required and unchanged
  in meaning. Row-level security is an additional wall beneath them, not a replacement; no scoping
  predicate is removed from application code because a policy now enforces it.
- **FR-237 — Module boundary.** `R7-01` holds: `khepri.rca` and `khepri.rra` do not import each
  other. Policies and roles are composed in Alembic migrations and `khepri.runtime`, not by one
  package reaching into the other's metadata. The existing import tests are its verification:
  `tests/test_r707_commercial_bridge.py`
  (`test_khepri_rca_imports_no_khepri_rra_module`, `test_khepri_rra_imports_no_khepri_rca_module`)
  and `tests/test_rca001_boundary.py` (`test_no_rra_module_imports_rca`).
- **FR-238 — A read the policy can empty never admits.** No guard, recorder, sweep, migration or
  other process may treat an empty
  read **run without the unit's scope set**, where row-level security can therefore be the reason
  it is empty, as permission or as "nothing to
  do". Two callers are named at `main`:
  - `khepri.runtime.beta_membership_guard.BetaMembershipGuard.admits` returns `True` when
    `_owning_organization` returns `None`. That happens on **two** reads: `sessions.get_session`
    returning nothing, and `SqlIsolationScopes.organization_of` returning nothing. Today both
    `None`s are legitimate (no cookie; a beta scope no organization owns, where the route decides).
    Under row-level security the first can also mean "the policy hid the session", and if Open
    item 1 brings `rca_isolation_scopes` under a policy, so can the second. The guard must refuse,
    not admit, when either read is empty for that reason.
  - `khepri.runtime.pipeline_recording.PipelineRecorder._workspace_of` returns `None` when its
    `get_session` read is empty, and also when `_scopes.exists(session.owner_id)` is false, a read
    of `rca_isolation_scopes` that Open item 1 could bring under a policy. `admitted` then records no version and `requested` starts no run.
    It runs on request paths: `RecordingProfilingService.profile_session_upload` and
    `RecordingReportRequests.request_session_report`. A hidden session would degrade silently to
    "not a workspace", and the workspace would miss the version and the run without any error.

  **When the guard's fail-open is reachable.** Only if the bootstrap mechanism lets the route
  handlers read the session while the guard's own read still runs without a scope. If both read
  nothing, the request fails closed downstream as an unavailable session. This requirement binds
  whichever mechanism is chosen, so the reachability does not depend on getting that choice right.
  `FR-266` applies it to `FR-265`'s mechanism, `FR-268` to `reconcile`, and `FR-272` to
  `khepri-envelope-migrate`, whose empty count would read as "verified".

## Open items 2 to 5, resolved

**Amendment (`#595`).** This section resolves Open items 2, 3, 4 and 5, each with the option
§Open items listed first for it (item 5's mechanism: a permissive policy granted to one role).
It departs from the `#595` recommendation in two places, each stated where it applies. The job
pickers return the job's `owner_id` beside its `job_id`, so `lease` runs scoped and no definer
function writes (`FR-267`, `FR-268`). The sweep's own `DeletionService` runs over the scoped
engine, not the sweep engine, so per-session deletion stays off the cross-scope role as `FR-235`
requires (`FR-271`).

The four definer functions are not a cross-scope use in `KHEPRI-DEC-035` §2's sense, and no
runtime role is given a policy that crosses scopes for them. Each returns only the scope key of a
row its caller already names, or of a job that is due, and never a row's content. A worker must
learn which scope to set before it can set one, and so must a request carrying only a
`session_id`. §2's list governs the roles that read and write rows across scopes, and the sweep
role is the only runtime role on it. This reading is the amendment's, and the owner's merge
settles it.

It adds `FR-264` to `FR-272` and Verification 14 to 18. It edits the Outcome, §When implementation
may start, `FR-231`, `FR-232`, `FR-233`, `FR-234`, `FR-235`, `FR-238`, §Exclusions, §Open items,
and Verification 1, 2, 4, 5, 6, 7 and 13 to match. Open items 1 and 6 stay open, and it raises
Open item 7. It governs from the
owner's merge (Constitution II), like the rest of this document.

- **FR-264 — Definer functions are the only pre-scope reads.** Exactly four functions run as
  `SECURITY DEFINER`: `FR-265`'s session lookup and `FR-267`'s three job pickers. No other
  definer function reads or writes a `khepri.rra` table. Each of the four:
  - is owned by the definer role (`FR-270`), which cannot log in;
  - only reads: it is declared `STABLE`, writes no row, and builds no SQL from its arguments;
  - takes only the arguments named for it, none of them SQL text or an identifier, and returns only
    the columns named for it;
  - pins its own `search_path` in its definition, so a caller's `search_path` cannot redirect a
    name in its body;
  - has `EXECUTE` revoked from `PUBLIC`, which PostgreSQL grants by default, and granted to the
    roles named for it and no other.

  The definer role crosses the policies by a permissive `SELECT` policy granted to it alone, on
  `rra_beta_sessions` and `rra_report_jobs` only. It holds column-level `SELECT` on exactly the
  columns the four bodies read, and no other standing privilege. A migration may grant it what
  PostgreSQL needs to transfer ownership of a function to it, and revokes that grant in the same
  migration. A dedicated role is needed because a definer function runs with its owner's rights.
  Owned by the migration owner, which `FORCE ROW LEVEL SECURITY` also subjects to policy unless
  it bypasses them, the four bodies would run with DDL rights.
- **FR-265 — Session scope bootstrap (Open item 3).** `rra_session_owner(session_id)` returns the
  `owner_id` of the one `rra_beta_sessions` row whose `session_id` equals its argument. It returns
  `NULL` when no row matches, or when the argument is `NULL` or `''`.
  - It returns one scalar, never a row or a set. It reads only the `session_id` and `owner_id`
    columns: not expiry, consent, deletion state or any other field. It does not decide whether
    the session is usable. The scoped read after it decides that, as today.
  - Only an exact `session_id` yields an `owner_id`. No pattern, prefix or range is accepted, so
    the lookup enumerates nothing. It reveals nothing its caller cannot already reach: the
    `session_id` is the bearer secret, and the cookie's holder can already reach that owner's rows.
  - `EXECUTE` goes to the application role and the worker role only.
  - A unit of work that knows only a `session_id` first calls the lookup. It then sets the returned
    `owner_id` with `SET LOCAL` (`FR-233`) and runs the existing read, all in one transaction.
    Every later transaction of that unit sets the same `owner_id`.
  - **A scope already set is never replaced.** When the unit already has a scope, as
    `WorkspaceDeletion`, the sweep's per-session deletion and a worker's job do, the read still
    calls the lookup. It **raises** when the result is `NULL` or differs from the scope already
    set, and otherwise reads under the scope already set. No `session_id` passed to a unit
    re-scopes it.
  - Every read of `rra_beta_sessions` by `session_id` alone reaches it this way, whether through
    `get_session` or not. That includes `khepri.rra.journey.state._live_session`, which reads
    `database.get(BetaSessionRow, session_id)` directly.
    `SqlSessionStore.get_session`, and every caller Open item 3 names, reach `rra_beta_sessions`
    this way. No unscoped read of a covered table is ever the source of a unit's scope.
  - A `NULL` result sets no scope. The unit then reads nothing and fails closed as an unavailable
    session, as each of those callers already does for a missing session. `FR-266` names the two
    callers that would not.
  - The session credential `RRA-001` governs does not change, and neither does redemption. It
    mints the `owner_id` and sets it before inserting the session row (`FR-233`), so it needs no
    lookup.
- **FR-266 — The guard and the recorder fail closed on the bootstrap (`FR-238`).**
  - `BetaMembershipGuard` takes the session's `owner_id` from `rra_session_owner` and reads no
    covered table. **When the request carries a beta session cookie and the lookup returns `NULL`,
    the guard refuses** with RRA's own `401 {"detail": "Session is unavailable."}` and does not pass
    the request to the route. A request with no beta session cookie still reaches the route, which
    refuses it itself. `REDEEM_PATH` is still never checked.
  - An `owner_id` that no organization owns (`organization_of` returns `None`) is still a
    design-partner scope, and the request reaches the route as today. `organization_of` reads
    `rca_isolation_scopes`, which Open item 1 leaves without a policy.
  - `PipelineRecorder._workspace_of` **raises** when the lookup returns `NULL` or the scoped
    session read after it is empty, instead of returning `None`. It returns `None` only when the
    scope resolved and `_scopes.exists(owner_id)` is false. That is the legitimate
    "not a workspace" case, and Open item 1 leaves that read without a policy too.
  - Neither caller relies on the lookup being right. An empty result is refused or raised. It is
    never read as permission or as "nothing to do".
- **FR-267 — Job claim and recovery candidates (Open item 2).** Three definer functions name jobs
  across scopes. For each job they return `(job_id, owner_id)` and nothing else: no state, attempt
  count, lease, payload or session field.
  - `rra_next_claimable_job(now)` returns at most one row: the job `next_claimable_statement`
    names today, under `claimable_at(now)`, ordered by `available_at, job_id`. It takes no lock.
  - `rra_expired_lease_jobs(now)` returns the jobs `recover_expired` selects today:
    `state = running` and `lease_expires_at <= now`, in the same order.
  - `rra_orphaned_jobs(now)` returns the jobs `recover_orphans` selects today: unfinished jobs
    whose session's content is deleted, in the same order. `orphanable` stays in the per-job
    transition (`FR-268`).

  They take `now` from the caller and never read the database clock, so the clock each composition
  root threads still governs them. They read the `rra_report_jobs` columns `job_id`, `owner_id`,
  `session_id`, `state`, `available_at`, `attempt_count`, `max_attempts`, `lease_expires_at` and
  `queued_at`, and the `rra_beta_sessions` columns `session_id`, `deletion_requested_at` and
  `content_deleted_at`, and nothing else. Each applies the predicate its Python counterpart
  applies. `claimable_at` stays the one definition (`#518`): the SQL bodies are a second
  statement of it, kept equal by test, not a second authority. **A change to `claimable_at` or to
  either recovery predicate ships, in the same slice, a migration that replaces the function**,
  and Verification 16 fails until it does. The worker role
  holds `EXECUTE` on all three. The sweep role holds it on the two recovery functions only
  (`FR-271`). The application role holds it on none.
- **FR-268 — The worker acts in the job's scope, and `RRA-007`'s recovery is kept.**
  - **Claim.** `ClaimingReportQueue._next_claimable` and
    `khepri.local.worker.ClaimablePoller.next_job_id` take `(job_id, owner_id)` from
    `rra_next_claimable_job`. `SqlReportJobRepository.lease` then runs as an ordinary transaction
    scoped to that `owner_id`. It is not a definer function, because the claim already yields the
    scope. It keeps `FOR UPDATE`, `claimable_at` and its transitions. Two workers racing for one
    job are therefore still resolved by the lease, and a job that is no longer claimable is still
    refused. On the local path, where `ReportWorker.process` leases what `ClaimablePoller` named,
    the `owner_id` travels in process beside the `ReportJobMessage`, for example on
    `LeaseRequest`. It is never added to a queue message, which `KHEPRI-DEC-028` keeps to opaque
    job identifiers and routing metadata.
  - **Execution.** From the lease until the job is settled, failed or released, every transaction
    the worker opens for that job sets that job's `owner_id` first. That includes `heartbeat`,
    `complete`, `fail`, `SettlingJobStore.complete`'s `find` and
    `ClaimWorkerLoop._already_succeeded`. No worker transaction touches a covered table with no
    scope set, or with another job's scope.
  - **Recovery.** `recover_expired` and `recover_orphans` take their candidates from `FR-267`'s
    functions. Each candidate is then transitioned in its own transaction, scoped to its
    `owner_id`. That transaction re-reads the job `FOR UPDATE SKIP LOCKED` under the same predicate,
    and then reclaims, reschedules, exhausts or dead-letters it and writes its
    `rra_report_job_attempts` row, exactly as today. A candidate the re-read no longer matches
    (another worker took it, or it settled) is skipped, not treated as an error. A fault on one
    candidate is isolated to that candidate, as `#523` isolates a link in `reconcile`. So restart
    recovery and orphan detection still reach every scope's jobs, the transitions and their
    idempotency are `RRA-007`'s, unchanged, and no definer function writes.
  - **Order.** `ClaimWorkerLoop.run_once` still recovers before every claim, from one clock
    reading.
  - **Reconcile.** `PipelineRecorder.reconcile` still walks `links_of_started_runs` across scopes.
    That is an RCA read, and Open item 1 leaves it without a policy. It reads each link's job with
    **that link's `owner_id` set**. Under that scope an empty job read is not "nothing to do"
    (`FR-238`). It is logged as that link's fault, and the run stays `started` for the next sweep.
- **FR-269 — Parent-derived policy for the four (Open item 4).** Each scope-owned table `FR-231`
  names has row-level security enabled and forced. Each also has a policy, applying to the
  application and worker roles, whose `USING` and `WITH CHECK` are both an `EXISTS` over its parent
  row by the foreign key `FR-231` names:

  | Table | Parent | Key |
  |---|---|---|
  | `rra_report_job_attempts` | `rra_report_jobs` | `(job_id, session_id)` |
  | `rra_operational_events` | `rra_report_jobs` | `(job_id, session_id)` |
  | `rra_report_delivery_surfaces` | `rra_report_deliveries` | `(job_id, bundle_id)` |
  | `rra_deletion_evidence` | `rra_deletion_jobs` | `deletion_id` |

  The `EXISTS` runs under the invoking role's own policy on the parent. A child is therefore
  visible and writable exactly when its parent is, and the parent's `FR-232` policy decides that.
  An unset or empty setting sees no parent, and so no child, including a child whose parent's
  `owner_id` is `''`. Every parent carries `owner_id` and is covered by `FR-230`. The policy adds no
  column, field or constraint and consults no table outside `khepri.rra`, so it is neither a new
  field (§Exclusions) nor `KHEPRI-DEC-035` §1's refused shape 2. These four lack the property
  `FR-230` is defined by, so its coverage test names them.
- **FR-270 — The roles (Open item 5).** Five roles. Each is held by the components named for it
  and by no other:

  | Role | Logs in | Held by | May | May not |
  |---|---|---|---|---|
  | application | yes | the web and API composition; the sweep's scoped engine (`FR-271`); and every other composition root Verification 7 finds that this table does not name, today `khepri.runtime.clerk_hard_stop` (RCA tables only) and `khepri.local.cli`'s `invite` (`rra_invitations`, pre-scope) | read and write covered tables under `FR-232` and `FR-269` with a scope set; `EXECUTE` on `rra_session_owner` | hold any cross-scope policy, or `EXECUTE` on `FR-267`'s functions |
  | worker | yes | the report-worker composition (`khepri.runtime.worker`, `khepri.local.worker`) | the application role's table reach; `EXECUTE` on `rra_session_owner` and all three of `FR-267`'s functions | hold any cross-scope policy |
  | sweep | yes | only the sweep components `FR-271` lists | the cross-scope reads, and the one delete, `FR-271` lists, through permissive policies granted to it alone; `EXECUTE` on `FR-267`'s two recovery functions | `INSERT` or `UPDATE` on any RRA table; `DELETE` on any RRA table but `rra_deletion_evidence`; reading a covered table or column `FR-271` does not list |
  | definer | no | nothing: reachable only through `FR-264`'s functions | what `FR-264` gives it | anything else |
  | migration owner | yes | migration runs only, outside every runtime process | own the tables, policies and roles' grants; run DDL; hold `BYPASSRLS` | be held by any runtime composition |

  - No policy that admits rows across scopes applies to the application or the worker role.
  - The migration owner is the only role that may hold `BYPASSRLS`. Data migrations, and
    Verification 4's seed, must cross the policies. Because it owns the tables, the migration owner
    can already disable row security on them, so the attribute gives its holder nothing new.
  - Migrations and sweeps do not share a role. A leaked sweep credential therefore carries no DDL
    right, and reaches only the rows and columns `FR-271`'s policies admit. Where the credentials
    come from stays outside this specification (§Exclusions).
- **FR-271 — The sweep's composition (Open item 5; amends `FR-235`).** The cross-scope role is held
  per component, not per process. `build_retention_sweep`, and `khepri.local.wiring`'s sweep
  composition, each build two engines:
  - the **sweep engine**, connected as the sweep role. Today each of these reads shares one
    `factory` with the per-owner work of its class, so the slice splits each into a component of
    its own that takes the sweep engine as a constructor argument. It goes to these four
    components and no others: the expired-session lister now in
    `RetentionSweeper._expired_session_ids`, which also yields each session's `owner_id`; the
    due-upload lister now in `RawUploadRetentionSweeper._due`; the `DeletionEvidenceSweeper`'s
    purge store (`SqlDeletionRepository.purge_evidence_before`); and the recovery candidate source
    of `PASS_EXPIRED_LEASES` and `PASS_ORPHANED_JOBS`, which calls `FR-267`'s two recovery
    functions;
  - a **scoped engine**, connected as the application role, for everything else. That covers the
    sweep's own `DeletionService`, built by the same constructor the request path uses so that
    expiry deletes exactly as the request route deletes. It also covers `_purge_scope` and
    `_delete_row`, the per-candidate recovery transitions (`FR-268`), and every RCA sweeper. The
    sweep is no longer handed `stack.services.deletion`, and no `DeletionService` is built over the
    sweep engine.

  The sweep role's policies are permissive, apply to the sweep role alone, and are backed by
  column-level grants on exactly these columns:
  - `rra_beta_sessions`: `SELECT` of `session_id`, `owner_id`, `content_expires_at` and
    `content_deleted_at`;
  - `rra_uploads`: `SELECT` of `upload_id`, `owner_id`, `session_id`, `object_key` and
    `ciphertext_sha256_hex`;
  - `rra_deletion_evidence`: `SELECT` of `attempted_at`, and `DELETE`.

  It also holds a plain `SELECT` grant on the columns `_due` reads from
  `rca_workspace_dataset_versions`, an RCA table with no policy (Open item 1). Before the scoped
  engine touches anything for a session or an owner, that `owner_id` is set from the listing.
- **FR-272 — The envelope migration fails closed (Open item 7).** `khepri-envelope-migrate`
  (`khepri.runtime.envelope_migration`, over `khepri.rra.envelope_migration`) lists every `v1`
  row of `rra_report_artifacts` across all scopes (`_candidates`) and counts the `v1` rows left in
  `rra_report_artifacts` and `rra_uploads` (`_legacy_count`). It reports "verified", and exits 0,
  when both counts are zero. Through the application role under the policies, both reads are
  empty, so it would report "verified" with `v1` rows remaining. That is the condition on which
  `KHEPRI-DEC-028` retires `v1`. Until Open item 7 admits its cross-scope reads, it **refuses to
  run**, with a non-zero exit and no count, whenever its connection is subject to the RRA policies.
  This requirement admits no role for it.

## Exclusions

This specification does not authorize:

- row-level security on any `khepri.rca` table (Open item 1);
- handing the sweep engine to any component `FR-271` does not list, or granting a policy that
  crosses scopes to any role but the sweep and definer roles;
- any cross-scope read by `khepri-envelope-migrate` (Open item 7);
- a definer function beyond `FR-264`'s four, a definer function that writes, or `BYPASSRLS` on any
  role but the migration owner;
- a foreign key onto `rca_isolation_scopes`, or a CHECK or trigger that consults another table,
  from any RRA table: `KHEPRI-DEC-035` §1 refuses both;
- a change to any scope, identity, session or consent rule of `RRA-001`. The unscoped `session_id`
  lookups `#152` holds stay `#152`'s to fix; but row-level security **changes what they return**
  (nothing, with no scope set), so the implementing slice may not treat them as untouched. `FR-265`
  governs that change;
- a new data use, field, table or telemetry event, beyond the roles, policies, functions and
  settings above. `FR-269` walls the four scope-owned tables without a new column, and adding
  `owner_id` to them is not authorized;
- selecting the secret source, provider or hosted environment for the roles' credentials; that
  remains `OPS1`'s and `KHEPRI-DEC-028`'s;
- beta authorization itself. Satisfying this specification discharges one gate of
  `KHEPRI-DEC-035` §4 and nothing in `KHEPRI-DEC-030` §6.

## Open items for the owner

Items 1, 6 and 7 are raised, not decided, and none blocks implementation. Items 2 to 5 were raised
here and are resolved in §Open items 2 to 5, resolved. Their text stays below as the record of the
options considered.

1. **Do RCA tables take the same policy?** Still open. The `#595` owner decision (2026-09-26) says
   "RLS enabled
   on tenant-owned data", which reads broader than RRA. `KHEPRI-DEC-035` §5 decides only RRA and
   leaves RCA open: "Whether RCA tables take the same policy is not decided here, and nothing here
   excludes it." This specification therefore covers RRA only and does not decide RCA. If RCA is
   in, it needs its own requirement (RCA family), because RCA's scope key and cross-scope paths
   differ. It would also make `organization_of`'s empty read policy-dependent (`FR-238`). It
   would also reach the other RCA reads the resolution of items 2 to 5 relies on (§When
   implementation may start), and that requirement must amend `FR-266`, `FR-268` and `FR-271` for
   them.
2. **How does the report-job claim and its recovery run?** **Resolved by `FR-267` and `FR-268`:
   restructured, not added to the cross-scope list.** `rra_report_jobs` carries `owner_id`, so
   `FR-230` covers it. `FR-230` covers only tables with `owner_id`. The tables whose rows reach
   `rra_report_jobs` by foreign key are `rra_report_job_attempts` and `rra_operational_events`
   directly (no `owner_id`; Open item 4), `rra_report_deliveries` directly (covered in its own
   right), and, through `rra_report_deliveries`, `rra_report_delivery_surfaces` (item 4) and
   `rra_report_artifacts` (covered). These operations select across all scopes before they know whose job
   it is:

   | Operation | Lock it takes | Call sites |
   |---|---|---|
   | `khepri.rra.job_persistence.next_claimable_statement` | none: a plain `SELECT … LIMIT 1` | `khepri.rra.claim_queue.ClaimingReportQueue._next_claimable`; `khepri.local.worker.ClaimablePoller.next_job_id` |
   | `SqlReportJobRepository.lease` | `FOR UPDATE` on the one named job | `ClaimingReportQueue.receive`; `khepri.rra.worker.ReportWorker.process`; `khepri.runtime.pipeline_recording.SettlingJobStore.lease` |
   | `SqlReportJobRepository.recover_expired` | `FOR UPDATE SKIP LOCKED` | `ClaimingReportQueue.recover`, reached from `khepri.runtime.worker.ClaimWorkerLoop` before every claim; `SettlingJobStore.recover_expired`; `RetentionSweeper.sweep` (`PASS_EXPIRED_LEASES`) |
   | `SqlReportJobRepository.recover_orphans` | `FOR UPDATE SKIP LOCKED` | `SettlingJobStore.recover_orphans`; `RetentionSweeper.sweep` (`PASS_ORPHANED_JOBS`) |

   Under a scoped application role each would see nothing; `lease` is included because the worker
   names a job before it knows the job's scope. `KHEPRI-DEC-035` §2 names only migrations and the
   sweeps as cross-scope uses. The options were to add these to that list, or to restructure them
   (for example a claim that returns only an opaque job identifier through a narrowly granted
   function, after which the worker sets the job's scope). Either had to preserve `RRA-007`'s
   restart recovery and orphan detection. The restructure is chosen. The picker returns the job's
   `owner_id` with its `job_id`, so `lease` runs scoped and is not a definer function.
3. **How is a session's scope resolved before any scope is set?** **Resolved by `FR-265` and
   `FR-266`: the first mechanism below.** A beta request carries only its
   `session_id` cookie and learns its `owner_id` from the unscoped
   `SqlSessionStore.get_session(session_id)` read on `rra_beta_sessions`
   (`khepri.rra.persistence`). Its callers are `khepri.rra.datasets` (two), `khepri.rra.intake`,
   `khepri.rra.packages` (two), `khepri.rra.deletion`, `khepri.rra.sessions` (two),
   `khepri.runtime.pipeline_recording` (`_workspace_of`), and
   `khepri.runtime.beta_membership_guard` (`_owning_organization`). Under
   `FORCE ROW LEVEL SECURITY` with no setting, every one of those reads returns nothing. Most
   callers then fail closed, as an unavailable session. Two do not: the membership guard fails open
   and `_workspace_of` degrades silently (`FR-238`). The candidate mechanisms were:
   - a narrow `SECURITY DEFINER` lookup that returns only the `owner_id` for one `session_id`
     (chosen);
   - carrying the owner in the session credential so the scope is known before the first read.
     This **changes the session credential `RRA-001` governs**, so it would need a merged
     `RRA-001` amendment first;
   - a dedicated resolution role with `SELECT` on `(session_id, owner_id)` only.

   `khepri.rra.journey.state._live_session` reads the same table by `session_id` without
   `get_session`, and `FR-265` reaches it too. Whatever was chosen had to satisfy `FR-238`, and `FR-266` makes it do so.
4. **How are the four scope-owned tables without `owner_id` walled?** **Resolved by `FR-269`: the
   first option below.** `FR-231` names them. The options were:
   - a policy that derives the scope from the parent: an `EXISTS` on the parent row, which the
     parent's own policy then filters (chosen);
   - adding an `owner_id` column to each, which is a schema change and a new field under this
     specification's exclusions;
   - narrowing the Outcome permanently to tables with `owner_id` and accepting the children as
     reachable only through application code.

   Verification 1, 2 and 4 name them.
5. **How does the cross-scope role cross the policies, and who holds it?** **Resolved by `FR-270`
   and `FR-271`: a permissive policy granted to the sweep role only, a migration owner no runtime
   process holds, and per-component holding.**
   - *Mechanism*. The options were: the role holds `BYPASSRLS`; the role owns the tables, which
     `FORCE ROW LEVEL SECURITY` would still subject to policy unless combined with another option;
     or a permissive policy granted to that role only (chosen). Each differs in what a leaked
     credential for that role exposes.
   - *Migrations and sweeps*: whether they share one role. If they do, the sweep process's
     credential also carries DDL rights. They do not (`FR-270`).
   - *Per process or per component*: `khepri.runtime.wiring.build_retention_sweep` builds every
     sweep from one `stack.factory` and shares `stack.services.deletion` with the request path,
     and passes that factory to the RCA sweepers as well. `khepri.local.wiring` composes the same
     way. A per-process cross-scope role would therefore reach the RCA sweepers and the deletion
     service; a per-component role needs a second engine in the composition root. Per component
     is chosen, and `FR-271` amends `FR-235`'s admission table, with Verification 7, accordingly.
6. **Is an `owner_id <> ''` CHECK added to each covered table?** Still open. It would make
   `FR-232`'s empty-owner
   case unrepresentable rather than only unreadable. It is a single-column constraint that consults
   no other table, so it is not `KHEPRI-DEC-035` §1's refused shape 2, which is a CHECK or trigger
   standing in for the scope anchor. It does not replace `FR-232`. If adopted, Verification 4's
   `''` seed becomes an assertion that the CHECK exists on every covered table. Non-blocking.
7. **Under which role does `khepri-envelope-migrate` read across scopes?** Raised by the `#595`
   amendment. `KHEPRI-DEC-035` §2 lists migrations among the cross-scope uses, but this is not an

   the store, so it needs object-store credentials that the migration owner does not hold, and
   that `FR-270` keeps away from any runtime process. Options, none chosen here:
   - a further sweep-style component holding a permissive `SELECT` policy on the `v1` columns
     of the two tables only, with each reseal run scoped to the row's `owner_id`;
   - running it under the migration owner, which `FR-270` would then have to admit for this one
     command;
   - running it only before the policies are enabled in an environment, and retiring it once no
     `v1` row remains there.

   Until it is resolved, `FR-272` makes the command refuse under the policies. Non-blocking for
   the RRA slice.

## Verification

Items 1 to 6, 12 to 18, and the catalogue half of item 11 run against PostgreSQL, not SQLite. Each connects as the runtime
role it names, or as the application role of `FR-270` where it names none. They carry the
`concurrency` marker, so `.github/scripts/require_concurrency_tests.py` fails the build if they
skip in CI. Items 7, 9, 10 and 11 inspect the code, the metadata or the catalogue, and item 14
inspects the catalogue; item 8 runs where it says.

"Refused" has one meaning throughout:
- for `INSERT`, an error with SQLSTATE `42501` (`insufficient_privilege`, row-level security's
  refusal), not `23503` (foreign-key violation);
- for `UPDATE` and `DELETE`, zero rows affected.

1. **Positive and negative control.** In every covered table, with rows seeded for both A and B, a
   unit of work scoped to A reads and writes A's rows and reads none of B's. The positive half
   defeats a `USING (false)` policy. It runs as the application role and again as the worker
   role, and it covers `FR-269`'s four tables, whose rows are seeded beneath A's and B's parents.
   Items 2 to 4 run as both roles too.
2. Inserting a session or child row whose `owner_id` differs from the setting is refused. So is
   inserting one whose `owner_id` is `''` while the setting is empty. B's parent
   `rra_beta_sessions` row **exists** when the child insert is attempted, so the refusal is
   row-level security's (`42501`) and cannot be a foreign-key violation (`23503`). Likewise, in
   each `FR-269` table, a unit scoped to A inserting a row whose key names B's **existing** parent
   is refused with `42501`.
3. With B's rows existing, `UPDATE` and `DELETE` scoped to A affect zero of them. With B's parent
   session existing, an `UPDATE` that re-points one of A's rows' `owner_id` to B is refused.
4. **Empty-setting case, with an empty-owner row present.**
   - In each covered table the test first seeds, as the migration role, a row whose `owner_id` is
     `''`. In each `FR-269` table it seeds a child of a parent whose `owner_id` is `''`.
   - It pins **one physical connection** and runs a scoped transaction on it.
   - It asserts the same `pg_backend_pid()` before and after, then opens a transaction with no
     setting. That transaction reads zero rows and has every write refused.

   Without the seeded row a naive `owner_id = current_setting(…)` policy would pass this test, so
   the seed is required, not illustrative. If Open item 6 adopts the CHECK, the seed becomes an
   assertion that the CHECK exists.
5. `FR-238` and `FR-266`, with row-level security enabled:
   - a request carrying a beta session cookie for which `rra_session_owner` returns `NULL` is
     refused by `BetaMembershipGuard` with RRA's `401`. That includes an existing session the
     lookup is made to miss, so the guard's refusal does not rely on the lookup;
   - a request with no beta session cookie reaches the route, and a session whose `owner_id` no
     organization owns is admitted to the route;
   - `_workspace_of` raises when the lookup returns `NULL` and when the scoped session read is
     empty, and returns `None` only for a resolved scope that is not a workspace.

   If Open item 1 brings `rca_isolation_scopes` under a policy, the same must hold for the guard's
   `organization_of` read and `_workspace_of`'s `_scopes.exists` read.
6. The coverage test of `FR-230`, naming `FR-269`'s four tables as well, and the role test of
   `FR-234` for the application, worker and sweep roles. The same test asserts that the definer
   role cannot log in, and that no role but the migration owner holds `BYPASSRLS`. It asserts
   from `pg_auth_members` that none of the application, worker and sweep roles is a member of
   another of the five roles, so no runtime role inherits a policy granted to another.
7. **Cross-scope recipients.** A test finds **every composition root by construction**. It sweeps
   every module under `src/khepri` for code that builds an engine or session factory, which
   includes `khepri.runtime.wiring` and `khepri.local.wiring`. The sweep is anchored on the
   installed package's path, not the working directory.
   - The test derives every component that receives the sweep role's engine or credential. That
     set must equal `FR-271`'s list exactly.
   - A recipient not on the list fails, and so does a listed component that receives the scoped
     engine instead. A `DeletionService` built over the sweep engine fails.
   - RCA components are **recipients like any other**. An RCA sweeper handed the sweep credential
     gains nothing on RCA tables, which carry no RRA policy, but it holds a credential that crosses
     RRA's, so it fails.
   - Recipients are compared at constructor-argument level: the component whose constructor
     receives the sweep engine.
   - Every composition root the sweep finds connects as exactly the role `FR-270` names for it. A
     root that `FR-270` does not place, other than by its "every other composition root" row,
     fails. No composition root receives the migration owner's credential.
8. **The application-isolation suite runs where no policy can mask it.** The existing suite that
   `FR-236` keeps runs unchanged with row-level security absent: on SQLite as it runs today, or on
   PostgreSQL as a table-owner role without `FORCE`. A scoping predicate removed from application
   code therefore fails it, rather than being hidden by the policy beneath.
9. **Classification.** The tables without `owner_id`, in the extent Verification 11 derives, equal
   `FR-231`'s list exactly.
10. `FR-237`'s import tests still pass.
11. **Extent.** Importing every module under `khepri.rra` yields a set of `khepri.rra` tables. That
    set equals the set in the migrated catalogue.
12. **`FR-233`.** Every transaction that touches a covered table sets the scope with `SET LOCAL`.
    The setting is gone in the next transaction on the same physical connection.
13. **The RRA route and store suites run as the application role under `FORCE`.** They pass with

    break the paths it sits beneath.
14. **`FR-264`, against the catalogue.**
    - The schema that holds the `khepri.rra` tables contains exactly four definer functions

    - `PUBLIC` holds `EXECUTE` on none of them. The roles that hold `EXECUTE` on each equal the

    - The definer role's column privileges equal the columns `FR-265` and `FR-267` list, and its

15. **`FR-265`, as the application role with no setting.** With sessions for A and B,

    - `reconcile` settles started runs in both A and B.
    - `ClaimWorkerLoop.run_once` still recovers before it claims.
18. **`FR-270` and `FR-271`, as the sweep role.**
    - Across A and B it reads exactly the columns `FR-271` lists. Reading any other covered table,

    - Its `INSERT` and `UPDATE` on every RRA table, and its `DELETE` on every RRA table but

    - The evidence purge removes A's and B's rows past the horizon.
    - One whole sweep, over expired sessions in A and B, deletes both. Each deletion runs on the

    - **`FR-272`.** With `v1` artifacts in A and B, `khepri-envelope-migrate` connected as the

## Route-level harness
