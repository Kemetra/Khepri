# RRA-017: Row-Level Security Beneath the RRA Scope

**Status:** PROPOSED. This document governs nothing until the sole owner merges it to `main`
(`governance/CONSTITUTION.md` §II). It was drafted by automation, which "checks facts and
consistency; it does not approve changes or act as a separate authority" (§I).

## Outcome

A unit of work acting for one RRA scope cannot read or write another scope's rows **at the
database**, independently of the application code that already scopes every read and write. A
PostgreSQL test running as the application role proves it.

## Why this artifact exists

`KHEPRI-DEC-035` §1 selects PostgreSQL row-level security as the only admissible shape for
anchoring the RRA scope in the database, §2 states what it must cover, and §4 makes it,
implemented and verified, a precondition of beta authorization. §5 then refuses to stand in for the
requirement: "The slice that implements §2 first lands the requirement it builds against, in
`RRA-001` or a successor." This is that requirement. `#595` tracks it.

**Successor, not amendment.** `RRA-001` is a closed, 32-line requirement set for invitations and
sessions. Row-level security crosses every RRA table that carries `owner_id`, changes the runtime's
database connection model, and needs its own exclusions and verification. Folding it into
`RRA-001` would widen that artifact's outcome ("one isolated, pseudonymous session") into an
operations boundary it never named. `RRA-001` stays `active` and unedited; nothing here narrows its
application-level isolation requirement ("fail closed on cross-session access").

## Requirements

- **FR-230 — Coverage by property.** Every table in `khepri.rra`'s SQLAlchemy metadata that
  carries an `owner_id` column has row-level security enabled **and forced**
  (`ALTER TABLE … ENABLE ROW LEVEL SECURITY` and `… FORCE ROW LEVEL SECURITY`). The covered set is
  defined by that property, not by a list: a test derives it from the metadata and the live
  catalogue, so a table added later with `owner_id` is either covered or fails that test.
- **FR-231 — Uncovered tables are enumerated, not assumed.** The implementing slice lists every
  `khepri.rra` table **without** an `owner_id` column and states, for each, whether it holds
  scope-owned content and how a row is reached. A table holding scope-owned content with no
  covered path to it is a defect the slice reports; this specification does not accept it.
- **FR-232 — Policy.** Each covered table has a policy whose `USING` and `WITH CHECK` both compare
  `owner_id` with the unit of work's scope setting. **An unset or empty setting matches nothing**
  (Constitution V). The property binds, not a mechanism: on a pooled connection that earlier ran
  `SET LOCAL`, a missing-setting read returns an empty string rather than `NULL`, so a policy that
  relies on `NULL` comparison alone does not satisfy this requirement.
- **FR-233 — Per-unit-of-work scope.** The scope setting is established with `SET LOCAL` (or
  `set_config(…, true)`, its transaction-local equivalent) inside every transaction that touches a
  covered table, from the scope the application has already resolved. It never survives the
  transaction. Redemption, which mints a new `owner_id`, sets that scope before inserting the
  session row.
- **FR-234 — Application role.** The runtime connects as a role that does not own the covered
  tables, is not a superuser, and does not hold `BYPASSRLS`. A test asserts all three against the
  catalogue.
- **FR-235 — Cross-scope role, enumerated.** Migrations, and the deletion and retention sweeps
  that must cross scopes (`KHEPRI-DEC-035` §2's list, and only that list), run under a separately
  named role. The implementing slice enumerates each such use by module and function, with its
  reason, starting from `khepri.runtime.retention_sweep`, `khepri.rra.evidence_retention` and
  `khepri.rra.deletion`; an unenumerated cross-scope use is a defect. Any other path found to cross
  scopes is reported, not admitted to that role (Open item 2).
- **FR-236 — Application isolation stays.** `IsolationService.resolve_scope` and the scoped store
  verbs remain required and unchanged in meaning. Row-level security is an additional wall beneath
  them, not a replacement; no scoping predicate is removed from application code because a policy
  now enforces it.
- **FR-237 — Module boundary.** `R7-01` holds: `khepri.rca` and `khepri.rra` do not import each
  other. Policies and roles are composed in Alembic migrations and `khepri.runtime`, not by one
  package reaching into the other's metadata.

## Exclusions

This specification does not authorize:

- row-level security on any `khepri.rca` table (Open item 1);
- running any path other than migrations and the deletion and retention sweeps under the
  cross-scope role (Open item 2);
- a foreign key, CHECK or trigger from any RRA table onto `rca_isolation_scopes`, which
  `KHEPRI-DEC-035` §1 refuses;
- a change to any scope, identity, session or consent rule of `RRA-001`, or to the unscoped
  `session_id` lookups `#152` holds;
- a new data use, field, table or telemetry event, beyond the roles, policies and settings above;
- selecting the secret source, provider or hosted environment for the two roles' credentials;
  that remains `OPS1`'s and `KHEPRI-DEC-028`'s;
- beta authorization itself. Satisfying this specification discharges one gate of
  `KHEPRI-DEC-035` §4 and nothing in `KHEPRI-DEC-030` §6.

## Open items for the owner

These are raised, not decided. Neither blocks merging this requirement; each blocks the part of an
implementing slice it names.

1. **Do RCA tables take the same policy?** The `#595` owner decision (2026-09-26) says "RLS enabled on
tenant-owned data", which reads broader than RRA. `KHEPRI-DEC-035` §5 decides only RRA and leaves
RCA open: "Whether RCA tables take the same policy is not decided here, and nothing here excludes
it." This specification therefore covers RRA only and does not decide RCA. If RCA is in, it needs
its own requirement (RCA family), because RCA's scope key and cross-scope paths differ.
2. **How does the report-job claim run?** `rra_report_jobs` carries `owner_id`, so `FR-230` covers
   it. The worker's claim query (`khepri.rra.job_persistence`, `FOR UPDATE SKIP LOCKED`, the
   delivery shape `KHEPRI-DEC-028` fixes) selects the next job across all scopes before it knows
   whose job it is, and so do its lease recovery (`recover_expired`) and orphan dead-lettering
   (`recover_orphans`). Under a scoped application role it would see nothing. `KHEPRI-DEC-035` §2 names
   only migrations and the sweeps as cross-scope uses. Whether the claim joins that list, or is
   restructured (for example a claim that returns only an opaque job identifier through a narrowly
   granted function, after which the worker sets the job's scope) is the owner's, and the
   implementing slice may not choose it.

## Verification

Against PostgreSQL, not SQLite, connected **as the application role** of `FR-234`, in tests carrying
the `concurrency` marker so `.github/scripts/require_concurrency_tests.py` fails the build if they
skip in CI:

1. A unit of work scoped to A reads none of B's rows, in every covered table.
2. Inserting a session or child row whose `owner_id` differs from the setting fails at the
   database.
3. A unit of work with no setting reads zero rows, including on a pooled connection reused after an
   earlier scoped transaction (the empty-string case of `FR-232`).
4. The coverage test of `FR-230` and the role test of `FR-234`.
5. The existing application-isolation suite still passes unchanged (`FR-236`).

Route-level tests reuse the PostgreSQL-backed journey harness `#388` introduces, once it lands,
rather than building a second one. Row-level security changes the connection model as well as the
schema, so the implementing slice coordinates with `OPS1`'s environment work
(`KHEPRI-DEC-035` Consequences).
