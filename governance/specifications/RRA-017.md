# RRA-017: Row-Level Security Beneath the RRA Scope

**Authority:** this document governs from the commit in which the sole owner merges it to `main`
(`governance/CONSTITUTION.md` §II); before that merge it is a proposal. Its state is the
`governance/registry.yaml` row, not this line. It was drafted by automation, which "checks facts and
consistency; it does not approve changes or act as a separate authority" (§I).

## Outcome

For every `khepri.rra` table that carries an `owner_id` column, a unit of work acting for one RRA
scope cannot read or write another scope's rows **at the database**, independently of the
application code that already scopes every read and write. A PostgreSQL test running as the
application role proves it.

The outcome does **not** yet extend to the `khepri.rra` tables without `owner_id` (`FR-231`, Open
item 4). Until the owner decides item 4, nothing here claims those tables are walled.

## Why this artifact exists

`KHEPRI-DEC-035` §1 selects PostgreSQL row-level security as the only admissible shape for
anchoring the RRA scope in the database, §2 states what it must cover, and §4 makes it,
implemented and verified, a precondition of beta authorization. §5 then refuses to stand in for the
requirement: "The slice that implements §2 first lands the requirement it builds against, in
`RRA-001` or a successor." This is that requirement. `#595` tracks it.

**Successor, not amendment.** `RRA-001` is a closed, 32-line requirement set for invitations and
sessions. Row-level security crosses every RRA table that carries `owner_id`, changes the runtime's
database connection model, and needs its own exclusions and verification. Folding it into
`RRA-001` would widen that artifact's outcome ("one isolated, pseudonymous session") into an
operations boundary it never named. `RRA-001` stays `active` and unedited; nothing here narrows its
application-level isolation requirement ("fail closed on cross-session access").

## Implementation is blocked until Open items 2–5 are decided

This requirement can merge with its open items open. **No implementing slice may start until the
owner decides items 2, 3, 4 and 5.** Item 3 alone suffices: without it, enabling the policies makes
the beta request path read nothing, and one caller of that read then fails open (item 3). Item 1
does not block the RRA slice; it only bounds what this specification covers.

## Requirements

- **FR-230 — Coverage by property.** Every table in `khepri.rra`'s SQLAlchemy metadata that
  carries an `owner_id` column has row-level security enabled **and forced**
  (`ALTER TABLE … ENABLE ROW LEVEL SECURITY` and `… FORCE ROW LEVEL SECURITY`). The covered set is
  defined by that property, not by a list: a test derives it from the metadata and the live
  catalogue, so a table added later with `owner_id` is either covered or fails that test. This
  requirement is not satisfiable for `rra_report_jobs`, or for the tables whose rows reach it,
  until Open item 2 is decided. It does not say whether any table may be covered before then.
- **FR-231 — Tables without `owner_id` are enumerated, not assumed.** At `main` `4276814`, five
  `khepri.rra` tables carry no `owner_id`:

  | Table | Reached through | Holds |
  |---|---|---|
  | `rra_report_job_attempts` | `(job_id, session_id)` → `rra_report_jobs` (`fk_job_attempt_job_scope`) | per-attempt dispositions of one scope's job |
  | `rra_report_delivery_surfaces` | `(job_id, bundle_id)` → `rra_report_deliveries` (`fk_delivery_surface_bundle`) | per-surface content digests of one scope's report |
  | `rra_operational_events` | `(job_id, session_id)` → `rra_report_jobs` (`fk_operational_event_job_scope`) | content-free stage telemetry of one scope's job |
  | `rra_deletion_evidence` | `deletion_id` → `rra_deletion_jobs` (`fk_evidence_deletion`) | location and content digests of one scope's deleted objects |
  | `rra_invitations` | nothing; no session, owner or scope column | salted secret hashes and expiry only |

  The first four are **scope-owned**: every row belongs to exactly one scope through its parent.
  `rra_invitations` is **pre-scope**: it is read at redemption before any `owner_id` exists
  (`RRA-001`, "Redeeming a valid invitation creates an opaque owner ID"), and no row references a
  scope. A foreign key does not carry the parent's policy: PostgreSQL runs referential-integrity
  checks without row security, so a scope-owned child without a policy of its own is readable and
  writable across scopes by any role that can reach it. How the four are walled is Open item 4. The
  implementing slice re-derives this table from the metadata; a table added later without
  `owner_id` is a defect until classified here.
- **FR-232 — Policy.** Each covered table has a policy whose `USING` and `WITH CHECK` both compare
  `owner_id` with the unit of work's scope setting, so `SELECT`, `UPDATE` and `DELETE` see only the
  scope's rows and `INSERT` or `UPDATE` cannot write a row naming another scope. **An unset or empty
  setting matches nothing** (Constitution V). The property binds, not a mechanism: on a pooled
  connection that earlier ran `SET LOCAL`, a missing-setting read returns an empty string rather
  than `NULL`, so a policy that relies on `NULL` comparison alone does not satisfy this requirement.
- **FR-233 — Per-unit-of-work scope.** The scope setting is established with `SET LOCAL`, the
  mechanism `KHEPRI-DEC-035` §1 names, inside every transaction that touches a covered table, from
  the scope the application has already resolved. It never survives the transaction. Redemption,
  which mints a new `owner_id`, sets that scope before inserting the session row. How a request
  that knows only its `session_id` learns the scope to set is Open item 3.
- **FR-234 — Application role.** The runtime connects as a role that does not own the covered
  tables, is not a superuser, and does not hold `BYPASSRLS`. A test asserts all three against the
  catalogue.
- **FR-235 — Cross-scope role, enumerated.** Migrations, and the deletion and retention sweeps
  that must cross scopes (`KHEPRI-DEC-035` §2's list, and only that list), run under a separately
  named role. How that role crosses the policies is Open item 5. The implementing slice enumerates
  each use by entry point, with its reason. At `main` `4276814` the sweep entry points are:
  - `khepri.runtime.retention_sweep.RetentionSweeper.sweep`, through `_expired_session_ids` and
    `_expire_sessions`, which select expired sessions across all scopes;
  - `khepri.rra.evidence_retention.DeletionEvidenceSweeper.sweep`, which purges deletion evidence
    by horizon across all scopes;
  - `khepri.runtime.workspace_retention.RawUploadRetentionSweeper.sweep`, which selects due
    `rra_uploads` rows across all scopes before grouping them by `owner_id`.

  `DeletionService.delete_session_content` reached from the request route
  (`DELETE /api/v1/beta/content`, `khepri.rra.api`) is **not** a cross-scope use: it acts for the
  requesting session's scope and runs under the application role with that scope set. An
  unenumerated cross-scope use is a defect, and any other path found to cross scopes is reported,
  not admitted to that role (Open item 2).
- **FR-236 — Application isolation stays.** `IsolationService.resolve_scope` on the commercial
  path, and RRA's own owner-scoped verbs — `get_session_for_owner`, `get_upload_for_scope`,
  `get_profile_for_scope`, `get_package_for_scope` and the other `(owner_id, session_id)`
  predicates in `khepri.rra.persistence` — remain required and unchanged in meaning. Row-level
  security is an additional wall beneath them, not a replacement; no scoping predicate is removed
  from application code because a policy now enforces it.
- **FR-237 — Module boundary.** `R7-01` holds: `khepri.rca` and `khepri.rra` do not import each
  other. Policies and roles are composed in Alembic migrations and `khepri.runtime`, not by one
  package reaching into the other's metadata.

## Exclusions

This specification does not authorize:

- row-level security on any `khepri.rca` table (Open item 1);
- running any path other than migrations and the deletion and retention sweeps under the
  cross-scope role (Open item 2);
- a foreign key, CHECK or trigger from any RRA table onto `rca_isolation_scopes`, which
  `KHEPRI-DEC-035` §1 refuses;
- a change to any scope, identity, session or consent rule of `RRA-001`. The unscoped `session_id`
  lookups `#152` holds stay `#152`'s to fix; but row-level security **changes what they return**
  (nothing, with no scope set), so the implementing slice may not treat them as untouched. Open
  item 3 governs that change;
- a new data use, field, table or telemetry event, beyond the roles, policies and settings above.
  Adding `owner_id` to a table is one of Open item 4's options and needs the owner's decision
  first;
- selecting the secret source, provider or hosted environment for the two roles' credentials;
  that remains `OPS1`'s and `KHEPRI-DEC-028`'s;
- beta authorization itself. Satisfying this specification discharges one gate of
  `KHEPRI-DEC-035` §4 and nothing in `KHEPRI-DEC-030` §6.

## Open items for the owner

These are raised, not decided.

1. **Do RCA tables take the same policy?** The `#595` owner decision (2026-09-26) says "RLS enabled
   on tenant-owned data", which reads broader than RRA. `KHEPRI-DEC-035` §5 decides only RRA and
   leaves RCA open: "Whether RCA tables take the same policy is not decided here, and nothing here
   excludes it." This specification therefore covers RRA only and does not decide RCA. If RCA is
   in, it needs its own requirement (RCA family), because RCA's scope key and cross-scope paths
   differ.
2. **How does the report-job claim run?** `rra_report_jobs` carries `owner_id`, so `FR-230`'s
   property reaches it. The worker's claim (`khepri.rra.claim_queue`, through
   `khepri.rra.job_persistence.next_claimable_statement`, the PostgreSQL delivery shape
   `KHEPRI-DEC-028` fixes) selects the next job across all scopes before it knows whose job it is,
   and so do its lease recovery (`recover_expired`) and orphan dead-lettering (`recover_orphans`),
   each `FOR UPDATE SKIP LOCKED`. The worker's pipeline recording then learns the job's workspace by an
   unscoped `get_session` (`khepri.runtime.pipeline_recording`, `_workspace_of`). Under a scoped
   application role each would see nothing. `KHEPRI-DEC-035` §2 names only migrations and the
   sweeps as cross-scope uses. Whether the claim joins that list, or is restructured (for example
   a claim that returns only an opaque job identifier through a narrowly granted function, after
   which the worker sets the job's scope), is the owner's, and the implementing slice may not
   choose it.
3. **How is a session's scope resolved before any scope is set?** A beta request carries only its
   `session_id` cookie and learns its `owner_id` from the unscoped
   `SqlSessionStore.get_session(session_id)` read on `rra_beta_sessions`
   (`khepri.rra.persistence`). At `main` `4276814` its callers are `khepri.rra.datasets` (two),
   `khepri.rra.intake`, `khepri.rra.packages` (two), `khepri.rra.deletion`, `khepri.rra.sessions`
   (two), `khepri.runtime.pipeline_recording`, and `khepri.runtime.beta_membership_guard`. Under
   `FORCE ROW LEVEL SECURITY` with no setting, every one of those reads returns nothing. For most
   callers that fails closed, as an unavailable session. **For `BetaMembershipGuard` it fails
   open:** `_owning_organization` returns `None` when the session read is empty, and `admits`
   returns `True` on `None`. The request would pass the membership guard because the policy hid the
   session. Candidate mechanisms, none chosen here: a narrow `SECURITY DEFINER` lookup that returns
   only the `owner_id` for one `session_id`; carrying the owner in the session credential so the
   scope is known before the first read; or a dedicated resolution role with `SELECT` on
   `(session_id, owner_id)` only. Whatever is chosen must keep the guard refusing, not admitting,
   when the session cannot be read. **This item blocks implementation.**
4. **How are the four scope-owned tables without `owner_id` walled?** `FR-231` names them. Options,
   none chosen here: a policy that derives the scope from the parent (an `EXISTS` on the parent
   row, which the parent's own policy then filters); adding an `owner_id` column to each, which is
   a schema change and a new field under this specification's exclusions; or narrowing the Outcome
   permanently to tables with `owner_id` and accepting the children as reachable only through
   application code. Verification 1 extends to them once this is decided.
5. **How does the cross-scope role cross the policies?** `FR-235` names the role's uses but not its
   mechanism. Options, none chosen here: the role holds `BYPASSRLS`; the role owns the tables, which
   `FORCE ROW LEVEL SECURITY` would still subject to policy unless combined with another option; or
   a permissive policy granted to that role only. Each differs in what a leaked credential for that
   role exposes.

## Verification

Against PostgreSQL, not SQLite, connected **as the application role** of `FR-234`, in tests carrying
the `concurrency` marker so `.github/scripts/require_concurrency_tests.py` fails the build if they
skip in CI:

1. A unit of work scoped to A reads none of B's rows, in every covered table, and in the tables
   Open item 4 brings under the wall once it is decided.
2. Inserting a session or child row whose `owner_id` differs from the setting fails at the
   database.
3. `UPDATE` and `DELETE` scoped to A affect none of B's rows, and an `UPDATE` that re-points a row's
   `owner_id` from A to B fails at the database.
4. A unit of work with no setting reads zero rows, including on a pooled connection reused after an
   earlier scoped transaction (the empty-string case of `FR-232`).
5. `BetaMembershipGuard` **refuses**, not admits, a request whose session read returns nothing under
   row-level security, whatever mechanism Open item 3 selects.
6. The coverage test of `FR-230` and the role test of `FR-234`.
7. A test that derives, from the runtime composition root, every component that receives the
   cross-scope role's engine or credential, and compares that set with `FR-235`'s enumerated list.
   A recipient not on the list, or a listed use that receives the application engine, fails.
8. The existing application-isolation suite still passes unchanged (`FR-236`).

Route-level tests reuse the PostgreSQL-backed journey harness `#388` introduces, once it lands,
rather than building a second one. Row-level security changes the connection model as well as the
schema, so the implementing slice coordinates with `OPS1`'s environment work
(`KHEPRI-DEC-035` Consequences).
