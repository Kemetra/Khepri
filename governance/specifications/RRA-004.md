# RRA-004: Deterministic Retail Fact Package

## Outcome

One immutable, versioned fact package contains every numerical claim, population, basis, caveat,
and citation that may appear on any report surface. It calculates only from semantics admitted by
`RRA-003` and refuses an affected result when its exact population cannot be proven.

## Population contract

Every fact records one of these readable population codes in provenance; an identity hash alone
is insufficient:

- `financial_posted`: posted sale and return events, excluding void and cancelled rows;
- `sales_posted`: posted sale events only;
- `sales_complete_revenue`: `sales_posted` with complete revenue;
- `sales_complete_units`: `sales_posted` with complete strictly positive units;
- `sales_complete_revenue_units`: `sales_posted` with complete revenue, strictly positive units,
  and no unmatched eligible row;
- `sales_complete_transactions`: `sales_posted` with complete canonical transaction keys;
- `sales_complete_revenue_transactions`: `sales_posted` with complete revenue and canonical
  transaction keys;
- `sales_complete_units_transactions`: `sales_posted` with complete strictly positive units and
  canonical transaction keys;
- `financial_complete_revenue_cost`: financial rows with complete revenue and extended cost; and
- `dimension_complete_sales:<dimension>`: sale rows with complete canonical transaction keys and
  a non-null governed dimension value on every row.

The metric assignments are exact:

| Metric | Population |
|---|---|
| Revenue, period revenue, revenue comparison | `financial_posted` with complete revenue |
| Units | `financial_posted` with complete units |
| Transactions | `sales_complete_transactions` |
| AOV | `sales_complete_revenue_transactions` |
| ASP | `sales_complete_revenue_units` |
| Cost, gross profit, gross margin | `financial_complete_revenue_cost` |
| Discounts | posted sales with complete additive discount coverage |
| Returns | negative posted return revenue, published as its positive magnitude |
| Growth decomposition | return-free compared windows over `sales_complete_revenue_units` |
| Items per transaction | `sales_complete_units_transactions` |
| Attach rate | `dimension_complete_sales:<product\|category>` |
| Concentration | complete non-null product/category values over revenue-complete posted sales |

Headline revenue, cost, units, discounts, and returns have no partial-coverage vocabulary and
therefore refuse when a required admitted column has gaps. An optional column absent altogether
refuses only its metric. An explicit zero differs from a missing value. An empty eligible
population states zero only when admitted event-kind and status evidence proves that event class is
absent. Derived facts consume one population-certified aggregate, or compatible bases sharing one
population identity, and never combine unrelated whole-package totals merely because both exist.

## Governed trends and dimension comparisons

The package produces governed time trends and product, category, store, and channel comparisons
only when the relevant dimensions and metric populations are admissible. For each admissible
comparison dimension, it retains the ranked revenue-share curve over the full distinct-value set
before display truncation, together with the distinct-value count and the count actually ranked.
The retained curve carries shares only and no value labels.

When a canonical transaction identifier is mapped, the package retains the distinct transaction
count for each published dimension bucket and the full-set distinct transaction total. A row count
is never a transaction count. For each published time bucket, the package also retains the count
of distinct dates represented. These counts are audit and reconciliation evidence only; neither a
transaction count nor a distinct-date count substitutes for coverage-manifest completeness or
calendar alignment.

## Core formulas and refusal rules

All sums use admitted unrounded decimals. `count_distinct` operates on canonical keys, never rows.

| Metric | Exact formula | Required refusal |
|---|---|---|
| Revenue | `sum(financial signed revenue)` | Missing revenue or monetary semantics |
| Units | `sum(financial signed units)` | Missing or non-integral units; caveat a non-positive net total |
| Transactions | `count_distinct(sale transaction key)` | Any eligible sale row lacks a complete canonical key |
| AOV | `sales revenue / distinct sale transactions` | Incomplete sale revenue/key population or transaction denominator `<= 0` |
| ASP | `sales revenue / positive sale units` | Incomplete sale revenue/unit population or unit denominator `<= 0` |
| Cost | `sum(financial signed extended COGS)` | Any eligible financial row lacks admitted extended COGS |
| Gross profit | `matched revenue - matched extended COGS` | Revenue/cost population mismatch |
| Gross margin | `gross profit / matched revenue` | Gross profit refused or matched revenue denominator `<= 0` |
| Discounts | `sum(non-negative sale discount)` | Not captured, partial, overlapping, or non-additive |
| Returns | `-sum(non-positive return revenue)` | Return-event or revenue semantics are incomplete |
| Absolute delta | `current - prior` | Exact governed counterpart or compatible population is absent |
| Percentage delta | `(current - prior) / prior` | Absolute delta refused or prior denominator `<= 0` |
| Items per transaction | `sum(sale units) / distinct sale transactions` | Incomplete units/keys or denominator `<= 0` |
| Attach rate for value | `distinct containing keys / all eligible keys` | Incomplete dimension/keys or denominator `<= 0` |
| Concentration curve point | `cumulative revenue / total ranked revenue` | Missing dimension on any eligible sale, negative value, or total `<= 0` |
| Top decile share | Curve share after `ceil(distinct values / 10)` ranked values | Concentration curve refused |
| Top quartile share | Curve share after `ceil(distinct values / 4)` ranked values | Concentration curve refused |

Revenue and units include posted returns. Transactions count posted sales only. AOV uses complete
net sale revenue and sale transaction keys, and ASP uses complete net sale revenue and positive
sale units; each carries a caveat when returns make it differ from a return-inclusive headline.
Cost and gross profit may be negative. Gross margin alone refuses at a zero or negative matched
revenue denominator while complete cost and gross profit survive. Missing cost never suppresses
complete revenue. Return units are required only by unit-dependent facts. Every refusal leaves
facts whose own semantics and population remain independently proven.

## Retained audit-only reconciliation bases

The package retains these bases as audit evidence, never as additional customer KPIs:

- `financial_revenue_basis`: complete signed revenue over `financial_posted`;
- `financial_units_basis`: complete signed units over `financial_posted`;
- `sales_revenue_basis`: complete non-negative revenue over `sales_posted`;
- `sales_units_basis`: complete positive units over `sales_posted`;
- `sales_transaction_basis`: the complete canonical sale-transaction key set;
- `sales_revenue_units_basis`: paired sale revenue and units over one complete identical
  population;
- `sales_revenue_transaction_basis`: paired sale revenue and canonical transaction keys over one
  complete identical population;
- `sales_units_transaction_basis`: paired sale units and canonical transaction keys over one
  complete identical population;
- `financial_revenue_cost_basis`: paired revenue and extended COGS over the complete identical
  financial population;
- `dimension_sales_revenue_basis:<dimension>`: complete sale revenue by every admissible value;
- `dimension_transaction_basis:<dimension>`: the complete transaction-membership set for every
  admissible value; and
- aligned daily revenue and unit bases bound to each accepted comparison window.

Every basis records population code, event count, canonical transaction count when applicable,
input digest, mapping version, currency when applicable, precision, and a stable basis identity.
Every derived fact cites exactly one compatible basis or a documented set of bases with the same
population identity. Failure to retain one basis completely refuses only dependent facts.

## Structural coverage signatures and aligned daily bases

For every monthly revenue and unit bucket, the package combines the valid `RRA-003` coverage
manifest with admitted events and retains a deterministic structural coverage signature over only:

- the coverage-manifest identity and input-digest binding;
- the governed aggregate scope identity or complete admitted store set;
- included event-kind and status filters;
- coverage mode and completeness, including full-calendar or contiguous day-1 prefix; and
- relative covered calendar-day ordinals and their covered scope or store set.

The structural signature excludes absolute calendar dates and all revenue, unit, and other measure
values. Its identity proves the recorded structure; cross-window comparability follows the
field-level compatibility rules in `RRA-008`, not raw signature equality.

Aligned daily revenue and unit bases are retained separately from the structural signature. They
record exact start and end dates, store or aggregate scope, event and status filters, population
identity, currency and precision where applicable, and daily revenue and unit values, including
attested zero-activity days. Observed day counts, distinct-date counts, date bounds, equal row
counts, and generated date spines are evidence but are not coverage-manifest completeness proof.

For partial-window alignment, the package may derive a deterministic prefix-scoped structural
coverage projection from a complete full-period structural signature, its bound manifest, and its
separately retained daily bases. A projection covers relative days `1..k`; preserves the parent
signature and basis identities, input and manifest bindings, governed aggregate scope or complete
store set, and event-kind and status filters in provenance; and restricts the parent daily bases to
that prefix. The manifest must prove every projected scope-or-store/day pair complete. A projection
never infers missing coverage, synthesizes an unproven day, or changes a parent measure value.

## Fact-package provenance

Each fact, derived series, and retained basis discloses readable formula version, mapping version,
population code, event-kind and status filters, currency for monetary values, aligned calendar
window when applicable, input bases, precision, rounding mode, caveats, fact identity, and citation
identity. The package also records dimensions, units, input digest, coverage-manifest identity,
coverage signatures, canonical transaction keys or their stable basis identity, aligned daily
bases, and growth rounding-residual evidence when applicable.

Every aggregate reconciles to its compatible retained basis. A reconciliation failure refuses the
affected result or emits its governed caveat; renderers never recalculate it. Stable fact and
citation identities and byte-equivalent reruns bind the exact input and governed versions.

## Precision and rounding

Rounding is decimal round-half-even and occurs once at the published fact boundary, unless an
intermediate published structure such as the concentration curve is itself authoritative.

- Revenue, cost, profit, discounts, returns, AOV, ASP, absolute deltas, and growth effects use the
  largest admitted monetary input scale, with a minimum of two and maximum of six decimal places.
- Integral units and transaction counts use zero decimal places.
- Dimensionless ratios, percentage deltas, items per transaction, attach rates, and concentration
  shares use four decimal places.

Calculations use unrounded admitted decimals. A null required input refuses its dependent result;
zero is admitted only under its metric's denominator and population rules; and negative values are
accepted or refused according to the normalized signs and exact formulas above.

## Stable contract and versions

`FactPackage` is immutable after publication and is the sole numerical source for narrative,
charts, PDF, and Excel. A new input, mapping, formula, population, interpretation, correction, or
serialized shape creates a new recorded version and stable identity.

`rra004.package.v3` succeeds `rra004.package.v2`. It authorizes readable population provenance,
canonical transaction keys, retained reconciliation bases, coverage-manifest identity, coverage
signatures, aligned daily bases, currency, and growth rounding-residual evidence.
`rra004.formula.v2` succeeds `rra004.formula.v1` and governs the formulas, compatible populations,
signs, zero/null/negative behavior, precision, and refusal rules in this specification. Historical
packages remain immutable under their recorded versions and are never silently reinterpreted.

## Exclusions

Fabricated metrics, forecasts, customer-defined formulas, generic non-retail analysis, currency
conversion, fractional quantities, partial headline totals, and renderer-side calculation are
excluded.

## Verification

Golden and adversarial tests cover semantic answerability, every exact population and formula,
conditional survival, time and dimension aggregates, matched revenue and cost, sale-only ratios,
canonical distinct transaction counts, structural coverage signatures and separately aligned daily
bases, null/zero/negative/sign behavior, round-half-even boundaries, reconciliation, deterministic
reruns, refusal, readable provenance, historical-version preservation, and citation integrity.
