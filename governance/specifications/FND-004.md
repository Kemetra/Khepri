# FND-004: Mechanical UI Contract Reference Index

## Outcome

Provide one deterministic, non-authoritative reference index that links an active product-family
requirement to the existing implementation and evidence paths within that specification's scope,
without defining or restating any UI, product, analytical, or presentation meaning.

## Family ownership

`FND` owns this mechanism because it is repository change-control infrastructure: a closed source
format, fail-closed authority and path resolution, deterministic generated metadata, and drift
validation. The referenced product family remains the sole owner of every meaning transported by
the mechanism. A reference record cannot create authority, widen a specification's scope, or join
separate product families under a shared component identity.

## Scope

This specification authorizes only the mechanical foundation at these paths:

- `docs/ui-contracts/records/` — source records containing opaque identifiers, authority pointers,
  optional non-authorizing design pointers, and scope-bound implementation or evidence paths.
- `docs/ui-contracts/generated/ui-contract-reference-index.json` — the canonical deterministic,
  explicitly derived reference projection.
- `docs/ui-contracts/generated/ui-agent-index.json` — a compact deterministic discovery projection
  containing pointers rather than copied governance or design prose.
- `src/khepri_gov/ui_contracts.py` — the closed executable schema, parser, resolver, serializer, and
  generated-artifact comparison logic.
- `src/khepri_gov/validator.py` — only the integration needed to reuse the validated governance
  graph and include UI reference validation in `khepri-gov validate`.
- `src/khepri_gov/cli.py` — only a generation command within the existing CLI architecture.
- `tests/test_ui_contracts.py` and `tests/test_cli.py` — focused mechanical and command-line
  evidence for this specification.

No referenced runtime, template, stylesheet, or product test path becomes writable under this
specification. Those paths remain governed only by their active product-family specifications.

## Requirements

- Define one closed, versioned source-record format and reject unknown fields, unsupported versions,
  partial records, duplicate record identifiers, and duplicate target paths.
- Keep each record subordinate to exactly one active product-family specification and exactly one
  canonical requirement definition in that specification. Initially admit only `RRA` and `RCA`
  specifications as governing UI authorities. `FND` and non-specification artifacts cannot satisfy
  a product-authority reference.
- Resolve artifact identity, type, state, family, and governing document only through
  `governance/registry.yaml`; never accept a syntactically valid identifier as sufficient.
- Resolve a requirement only from exactly one canonical definition inside the governing document's
  `## Requirements` section. Incidental mentions do not satisfy resolution, and suffixed identifiers
  such as `FR-095a` remain distinguishable.
- Bind every implementation or evidence target to an exact repository path grant declared as a
  top-level path bullet in the same specification's `## Scope` section. Require segment-aware path
  containment and reject an absent, ambiguous, malformed, escaping, or cross-family association.
- Treat evidence paths only as navigation pointers. Their presence does not assert that evidence is
  sufficient, approved, or truthful.
- Keep optional design references structurally separate and explicitly non-authorizing. A design
  document can aid navigation but can never satisfy a missing governing specification, requirement,
  or scope grant.
- Restrict record identifiers to opaque transport identity. An identifier cannot establish a
  component name, shared cross-family identity, product capability, or semantic taxonomy.
- Generate both outputs solely from validated source records and the validated governance graph.
  Sort records, references, and paths deterministically; use repository-relative paths; and emit no
  timestamps, local absolute paths, environment data, or copied governing prose.
- Mark generated outputs as derived and identify `governance/registry.yaml` as their authority
  source. Authored records cannot duplicate artifact state, type, family, dependencies, document
  path, or supersession metadata.
- Make `uv run khepri-gov validate` regenerate both outputs in memory and fail on a missing or
  byte-different checked-in artifact. Generation is the only operation permitted to write them.
- Keep parsing, generation, and validation free of runtime UI imports and side effects. Reuse the
  existing Python, YAML, governance-validator, CLI, and deterministic-JSON conventions without a new
  framework, frontend toolchain, or package dependency.
- Admit a production record only when its requirement and every target-to-scope relationship resolve
  unambiguously. If current product-family prose cannot provide a mechanically resolvable grant, the
  record is refused until that owning specification supplies one; this specification cannot infer it.

## Fail-closed invariants

Validation MUST reject an unknown, inactive, retired, non-specification, or disallowed-family
authority; a missing or multiply defined requirement; a missing or ambiguous scope grant; a target
outside its grant; an absolute, escaping, symlink-escaping, missing, or duplicate path; a record that
mixes authorities or families; a design-only authority; an unknown field; nondeterministic output;
and generated-artifact drift. None of these conditions may degrade to a warning.

## Generated artifacts

The reference index answers only which record points to which active authority, implementation
paths, and evidence paths. The agent index is a smaller discovery map from opaque record identifiers
to the source record, authority locator, and implementation paths. Neither output is a governance
registry, product catalog, evidence verdict, or source of UI truth, and neither copies requirement or
design prose.

## Exclusions

This specification does not authorize product semantics, presentation semantics, UI state
definitions, analytical meaning, product capabilities, visual or chart grammar, token policy or
enforcement, accessibility policy, right-to-left policy, responsive policy, interaction behavior,
keyboard or focus rules, visual-regression acceptance criteria, routes, APIs, databases, migrations,
package changes, runtime UI changes, template or stylesheet changes, or generation of Jinja, CSS,
JavaScript, or Python UI code. It does not authorize a shared component identity across `RRA` and
`RCA`, and it does not make FND an authority over either family's product surfaces.

Token, logical-CSS, rendered-accessibility, keyboard/focus, and visual-regression gates remain
outside this slice even where an active product-family specification already authorizes bounded
evidence on a named surface. Any later generic mechanism needs its own FND authority, and any new
product rule or surface needs authority from its owning product family.

## Verification

Focused tests MUST cover a valid single-family record and rejection of: unknown, inactive, retired,
non-specification, FND, and design-only authorities; missing and duplicate requirement definitions;
suffixed requirement identifiers; missing and ambiguous scope grants; targets outside their grants;
absolute, escaping, symlink-escaping, missing, and duplicate paths; cross-authority or cross-family
records; unknown fields and versions; unstable ordering; copied authoritative metadata; and missing
or drifted generated outputs.

The implementation slice must pass:

```text
uv run khepri-gov validate
uv run ruff check .
uv run pytest
```

Implementation may begin only after the repository owner merges this specification as active on
`main`. A branch or pull request containing this document remains a proposal and grants no authority.
