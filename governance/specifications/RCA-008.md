# RCA-008: Executive Decision Workspace Surfaces

## Outcome

An organization member reads a decision from governed facts on one navigable workspace: headline
figures, the limits on them, change, and supported breakdowns, each figure traceable to the exact
semantic view and version that produced it, with no number derived anywhere else.

## Why this artifact exists

`SV1` made governed facts readable through eight versioned projections and `RCA-007` bound one to
a scoped run. Nothing yet decides what a customer sees, in what order, or which projection answers
which question — and no active specification can decide it. `RRA-014` §Scope puts "runtime routes,
templates, shell assets, workspace persistence" outside itself; `RCA-006` excludes "no route,
runtime wiring, template, shell asset, public API, migration, cache, background job, renderer, or
existing workspace file"; `RCA-007` `FR-158` excludes routes and HTTP responses and asserts that
exclusion in test. **`D1` is made entirely of what all three exclude.**

The scope this governs was mapped first and separately, as `G4-01` was for comparison:
`docs/superpowers/plans/2026-09-10-d1-01-workspace-information-architecture.md`, on `main` at
`8e6dc94`. That note is product scope and grants nothing. It is cited here for its four findings,
each verified against shipping code, which this specification answers rather than rediscovers.

**The risk this artifact exists to bound is one sentence:** a surface that computes. Every earlier
program in this repository put its arithmetic behind a governed contract; a dashboard is where that
discipline is most likely to leak, because a total, a percentage or a sort key is one line away and
looks like presentation.

## Scope

- `src/khepri/rca/workspace/` — decision read models only, assembling projections into
  surface-ready structures and computing nothing. New modules; `RCA-005`'s existing files are
  untouched.
- `src/khepri/runtime/shell_api.py` and `shell_templates/` — the decision surfaces, under
  `RCA-002`'s frame and beside `RCA-005`'s Overview, Data and Analyses destinations.
- `src/khepri/runtime/shell_assets/` — stylesheet rules the decision surfaces require. **No active
  artifact names this directory**, which `G4/C1` recorded as an open question; this specification
  claims it for the D1 surfaces only and for no earlier one.
- `tests/` — surface, source-map, refusal, isolation, and bilingual-parity tests.

**Not in scope:** the semantic views and their versions (`RRA-014`), the query orchestration
(`RCA-006`), the composition root (`RCA-007`), the calculation families (`RRA-004`, `RRA-008`), the
catalog routes (`RRA-011`), the component layer (`RRA-012`), workspace persistence and the
comparison request/result routes (`RCA-005`), and identity, membership and session code
(`RCA-001`, `RCA-003`, `RCA-004`).

## The nine surfaces and what each may read

Fixed here so a later slice cannot widen it. Every view is named at an exact version by `FR-160`.

| Surface | Source |
|---|---|
| Executive Overview | `ExecutiveOverviewView` |
| Period Comparison | `PeriodComparisonView` — **see §The open question** |
| Branch Performance | `BranchPerformanceView` |
| Product/Category Performance | `ProductCategoryView` |
| Basket and Concentration | `BasketView` and `ConcentrationView` |
| Exceptions, Caveats, and Refusals | `MetricAvailabilityView`, and each projection's own caveats |
| Recent Analyses and Comparisons | `RCA-005` workspace records and pins |
| Navigable Report Workspace | `RRA-006` report bundle and `RCA-005` analysis detail |
| Metric Detail and Evidence Drawer | `RRA-011` catalog, `RRA-012` drawer, `ReportEvidenceView` |

The last three read no semantic view for their **structure**, and `FR-159` is why that is
admissible: the rule governs figures, not pages. No published view projects a list of runs, so
Recent Analyses could not be a view read at any version.

**The table names views and not version strings, deliberately.** `RRA-014`'s registry is the only
place a published version exists, and `FR-135` admits no second truth. Eight version strings copied
into this document would rot the first time a view is republished, leaving an active specification
asserting a version that no longer resolves — a worse failure than the one the duplication would
guard against. The pin `FR-160` requires lives as a literal in the surface's own module and is
asserted against the registry in test, not kept as a copy here.

## The open question this specification cannot settle by itself

**`PeriodComparisonView` is published and unreachable.** It admits a two-population bundle;
`RCA-007`'s adapter builds only single-population bundles, one per run, so `FR-136`'s shape
predicate refuses it. The `CrossVersionBundle` it needs exists — `C1` ships it and
`comparison_assembly.py` assembles it — but nothing binds that assembly to the semantic-view port.

**This specification does not claim that binding**, and `D1-01`'s note recommended otherwise. The
note's recommendation is refined here for the reason `RCA-007` itself gives for existing: the
binding is a composition-root change in a file `RCA-007` §Scope already governs, and two active
specifications governing one file is the ambiguity this repository fails closed on. Carving an
exception into either document would blur a boundary a successor can state cleanly.

So the Period Comparison **surface** is in scope and its **source** is not yet reachable.
`FR-170` requires that gap be held open visibly rather than rendered as an empty tab, on the
discipline `SV1-04`, `SV1-07` and `SV1-08` used for exactly this shape. **A successor composition
artifact is a precondition for that surface**, and the owner's alternative is to accept a D1
milestone without it.

## Requirements

- **FR-159**: No figure on any surface is derived outside a semantic-view projection. A read model
  may select, order, group for layout, and pass through; it may not sum, average, difference, rank,
  score, normalize, threshold, or compute a percentage, and it may not read raw rows. Structure and
  navigation may come from `RCA-005` records and the `RRA-011` catalog; figures may not.
- **FR-160**: Every view read names its `view_id` and `view_version` exactly, from the eight
  published in `RRA-014`'s closed registry. The version is a **literal constant in the reading
  module**, never obtained at read time from `published_versions`, `published_history`, or any
  other enumeration of what the registry currently publishes. Resolving it dynamically is the
  `latest` alias `FR-143` forbids reached by a different spelling: it would follow a republication
  silently and leave this requirement's pin with nothing to hold. A republication is therefore a
  change to this specification's implementation rather than a transparent one, and the literal is
  what makes that change appear in a diff.
- **FR-161**: A claim is presented only where the reader can also reach whether it is allowed to be
  made. Availability, caveats and refusals are reachable from the surface carrying the figure they
  qualify and are not deferred to a terminal page.
- **FR-162**: A customer-visible metric card exposes, directly or through one action: label, value
  with unit or currency, comparison only when compatible, a status of verified, caveated, refused
  or unavailable, population, formula and contract version, the effective filters and period,
  an evidence action, and a caveat or refusal count. Status is *selected* from
  `MetricAvailabilityView`'s governed availability and reason, the outcome kind, and whether the
  projection carries caveats; it is never counted, scored, or otherwise derived.
- **FR-163**: The two governed empty rules render distinguishably. `stated_no_rows` — the admitted
  request matched nothing — and `stated_absence` — the source published no value — are different
  findings with different remedies, and a surface that renders both as an empty table misstates the
  customer's data.
- **FR-164**: A refusal is presented with `RRA-014`'s governed bilingual wording in the page
  language. No surface invents refusal text, softens a refusal, substitutes a nearby figure, or
  presents an absent comparison as anything but the governed absence it is.
- **FR-165**: Each view read is independently authorized and can independently answer unavailable,
  so a surface renders partial success rather than failing whole. The unavailable outcome is
  content-free: a surface may say a part is unavailable and may never say why.
- **FR-166**: The global controls are modelled as what they are. The period is a **source
  selector** — choosing a completed run — not a view filter; the workspace is the organization
  scope resolved before any read; and only `store`, `product` and `category` are view filters, on
  the three views whose definitions admit them. No surface sends a parameter a view's
  `request_filter_allowlist` does not name, because `FR-137` refuses such a request before
  projection rather than ignoring it. Every effective filter is visible in the request and the
  result.
- **FR-167**: A breakdown figure is qualified only by its own projection's caveats and population
  qualifiers and by the outcome that fetched it. `MetricAvailabilityView` publishes no series
  metric, so no surface may state a four-state availability for a per-store, per-product or
  per-category figure, and none may synthesize one from the core metric it aggregates.
- **FR-168**: No cache, pre-aggregation, materialized view, sampling, or persisted projection is
  introduced. `RRA-014` `FR-144` bars all of them from this path; performance work is a change to a
  governed artifact and not a surface decision.
- **FR-169**: The surfaces add no product-analytics or repeat-use telemetry, no new audit event,
  counter, access record, or content-bearing log, and no retained preference, layout, or filter
  state. `KHEPRI-DEC-015` §3 stands unamended; request parameters and result content do not enter
  existing logs.
- **FR-170**: A promised surface whose governed source is not yet reachable is held open visibly
  and asserted to be unreachable, never rendered as empty or partial. The Period Comparison surface
  is that case today, and the assertion is removed by the slice that makes its source reachable —
  not by the slice that ships the surface.
- **FR-171**: Every surface presents equivalent Arabic and English content, and a figure present in
  one language is present in the other. A refusal, caveat or availability state is not dropped by
  either language.

## Exclusions

This specification authorizes no calculation, formula, projection, or view-definition change, all
of which remain `RRA-014`'s and the calculation families'; no change to the query orchestration or
the composition root; **no cross-version or two-population binding**; no persistence schema change,
migration, or new stored column; no cache, pre-aggregation, or materialized view; no retention,
telemetry, or audit record; no cross-organization access, sharing, or export; no raw-row access; no
public or embedded API; no onboarding, billing, or entitlement surface; no chart grammar,
navigation, accessibility-evidence, or visual-regression programme beyond the tests its Verification
names, which remain `U1-03`, `U1-05`, `U1-06` and `U1-07`'s and need their own authority; and no
edits to `RCA-001`, `RCA-002`, `RCA-005`, `RCA-006`, `RCA-007`, `RRA-011`, `RRA-012` or `RRA-014`
source paths.

## Retention, privacy, and telemetry

Unchanged from `RCA-006` and `KHEPRI-DEC-033`. The surfaces derive at read time and retain nothing
of their own: no layout, filter, sort, or dismissal state, and no record that a figure was viewed.
Content shown is the run's, and its retention is the run's. `KHEPRI-DEC-015` §3's prohibition on
repeat-use telemetry is not amended here and `D1-11` stays unauthorized.

## Invariants

- A surface that computes is a defect, not a feature, whatever the arithmetic's size.
- A refusal is content the customer is entitled to, not an error state to be hidden.
- No fallback, no partial projection, no nearby substitution, and no widening to unfiltered data.
- One requirement states one cause: where a governed refusal covers two published figures, both
  carry the same governed reason.
- The eight view versions are pinned; a surface never resolves a view by name alone.

## Verification

Tests cover: the source map, asserting each surface reads only the views this document names and
that every version it reads is a literal in the reading module which the registry still publishes;
a static check that no read-model or surface module performs arithmetic, raw-row access, or a
`published_versions`/`published_history` call that would resolve a version at read time; both
empty rules rendering distinguishably; refusal wording drawn from governed
vocabulary in both languages; an unsupported filter parameter refusing rather than being dropped;
per-surface partial success when one read is unavailable; a breakdown figure carrying no
four-state availability; cross-organization isolation on every surface; and Arabic/English parity
over figures, caveats, refusals and availability states.

Every slice under this specification passes `uv run khepri-gov validate`, `uv run ruff check .`,
and `uv run pytest`; every new file scores 10.00 in the required server-side CodeScene Code Health
Review and no tracked hotspot declines. That is the standing gate on implementation work under this
document, not a record of any one pull request's result.

## Implementation preconditions

1. An implementation slice identifies itself as `D1-02` through `D1-10` and stays within that
   slice's scope. `D1-01` is complete and is the scope note this document cites. `D1-11` is
   excluded by §Retention.
2. The Period Comparison surface's source precondition is a successor composition artifact, per
   §The open question. A slice may ship the surface with `FR-170`'s visible absence; none may bind
   the two-population source under this document.
3. `U1`'s chart grammar, navigation, accessibility and visual-regression tasks are not preconditions
   and are not authorized here; a slice needing a new shell stylesheet rule for a decision surface
   takes it from this document's Scope and from no other.
