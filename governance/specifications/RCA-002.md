# RCA-002: Commercial Application Shell and Surface Boundary

## Outcome

An authenticated commercial actor reaches every organization-scoped capability through one shell
that resolves exactly one actor and at most one active organization per request, renders in Arabic
and English at parity, and discloses nothing about organizations the actor is not a member of —
including by the shape of its own navigation.

`RRA-009` uses *surface* to mean an output format — web, PDF, Excel — of one report bundle. This
specification uses **surface** to mean an addressable screen in the shell, and says **render
target** where it means `RRA-009`'s sense.

## Requirements

Numbering continues from `RCA-001`, which ends at `FR-040`.

### Shell composition and the authorization checkpoint

- **FR-041**: Every shell request MUST resolve its actor through the canonical checkpoint
  `RCA-001` `FR-026` establishes. The shell MUST NOT introduce a second actor-resolution or
  membership-resolution path, and a shell surface reached without passing that checkpoint MUST be
  unreachable rather than permitted.
- **FR-042**: The shell MUST derive the active organization from the authenticated session, per
  `FR-027`. It MUST NOT accept an organization named by the request as the authority for a scope
  decision; where a request path names an organization, it MUST be compared against the session's
  active organization and MUST fail closed on disagreement, per `FR-024`.
- **FR-043**: Shell request handling MUST attach response security headers explicitly on every
  response. No shell surface may rely on a global middleware to supply them.
- **FR-044**: The shell MUST NOT weaken the content security policy under which the existing
  journey renders. Inline styles and inline scripts MUST remain unavailable to shell templates.
- **FR-045**: The shell MUST serve the same browser security policy as the existing journey,
  including a content security policy admitting no inline source, a deny-framing directive, and
  `Cache-Control: private, no-store`. Any divergence MUST be a strict narrowing, MUST be stated in
  the environment record, and MUST NOT relax caching for an organization-scoped response.

### Surface inventory and reachability

- **FR-046**: The shell MUST define a closed set of surfaces. A surface not named in that set MUST
  NOT be reachable, and an unknown path MUST resolve to the shared unavailable surface rather than
  to a distinct not-found surface.
- **FR-047**: Every surface MUST be addressable under a single language-parameterised prefix, so
  that the rendering language is a property of the address rather than of a stored preference.
- **FR-048**: An authenticated account with no membership in any organization MUST reach a surface
  carrying an explicit next step, and MUST be denied every organization-scoped surface, per
  `FR-028`.
- **FR-049**: A surface MUST NOT be introduced with no capability behind it. A navigation entry
  MUST NOT be rendered for a surface that has no implementation.

### Non-disclosure through the interface

- **FR-050**: Expired, deleted, deletion-requested, session-unavailable, and
  actor-not-a-member MUST render as one indistinguishable unavailable surface. The shell MUST NOT
  distinguish them by copy, status code, page identity, or navigation state, per `FR-025`.
- **FR-051**: No shell surface may name, count, or otherwise reveal an organization in which the
  actor holds no current membership. The organization switcher MUST enumerate only organizations
  in which the actor holds a current membership, per `FR-029`.
- **FR-052**: A denial rendered by the shell MUST be content-free with respect to the requested
  object: it MUST NOT disclose the object's existence, ownership, type, or age. **This is a
  different property from `FR-050` and MUST carry its own evidence.** `FR-050` requires several
  inputs to produce one indistinguishable output; `FR-052` constrains what any single denial may
  contain. One outcome test satisfies both while proving neither: a shell that leaked the object's
  type in every one of the five collapsed states would still be indistinguishable across them.
- **FR-053**: A membership or role change MUST take effect on the next shell request without
  requiring the session to end, per `FR-030`. The shell MUST NOT cache an authorization outcome
  across requests.

### Language and accessibility parity

- **FR-054**: Every shell surface MUST render in Arabic and English with equivalent state, actions,
  and error text, with correct language metadata and right-to-left Arabic layout, preserving the
  parity obligation `RRA-006` fixes.
- **FR-055**: A Latin-script run inside Arabic prose MUST carry an explicit direction so that it
  renders in isolation, and a language switch MUST preserve the actor's position rather than
  returning them to an entry surface.
- **FR-056**: Every interactive target MUST meet the minimum target size the existing journey tests
  already enforce, in both languages and at every supported viewport.

### Report presentation within the shell

- **FR-057**: Where the shell renders report content, it MUST originate from the existing `RRA`
  fact package and report contracts, per `FR-036`. The shell MUST perform no retail calculation and
  MUST NOT re-derive, re-round, or re-format an authoritative figure.
- **FR-058**: The shell MUST preserve `RRA-009`'s tiered classification: Business fields in the
  business region, Audit fields only in the separated audit region, Internal fields on no surface.
- **FR-059**: A refusal rendered in the shell MUST carry every part `RRA-009` requires of a
  refusal. A refusal missing a part MUST NOT render.
- **FR-060**: A rendered figure MUST carry its citation. A report whose citations are incomplete
  MUST NOT render, rather than rendering with the guarantee unmet.
- **FR-061**: Where the shell indicates the direction of a change, that indication MUST express
  direction only. It MUST NOT encode a judgement that a change is favourable or unfavourable, since
  that judgement is a property of the finding and not of the arithmetic.

## Exclusions

This specification does not authorize, and no implementation under it may introduce:

- Any capability `RCA-001` excludes. Its exclusion list applies unchanged and is not restated
  here to be weakened: persistent workspaces, report history, retention changes, billing,
  agency tenancy, scheduled delivery, public self-serve signup, `Seshat-BI` integration,
  forecasting, organization or account deletion, and any role beyond `owner` and `member`.
- **A dashboard, a report history, or a reports index.** These describe a product with durable
  retention, which no active decision grants.
- Any change to the `RRA` beta journey, its routes, its templates, or its assets. The beta surface
  is `RRA`'s and this specification does not modify it.
- Any new membership, role, invitation, or authorization *semantics*. This specification governs
  how existing `RCA-001` semantics are surfaced, never what they are.
- A second definition of actor resolution, membership resolution, or scope resolution. `FR-041`
  forbids it explicitly.
- Any icon, typeface, or third-party asset. Asset admission is governed separately and is not
  granted here.
- Runtime, provider, deployment, or provisioning selection.
- Product implementation until the preconditions below are met. Approval of this specification is
  not itself authority to implement.

## Assumptions

Stated so a reviewer can reject them.

- **A-1**: The shell's actor and scope resolution is the one merged under `RCA-001` — a session
  cookie read at the boundary, resolved through the canonical checkpoint. This specification assumes
  no new token source and no request-supplied account identity.
- **A-2**: Organizations an actor may switch between are readable from existing membership
  persistence. No new read model is assumed.
- **A-3**: The shell renders report content produced by `RRA`, and never produces it. `FR-036`
  already fixes this; `FR-057` restates it for the surface.
- **A-4**: Language is addressed rather than stored. A stored language preference would be new
  account data use and is deliberately not assumed.
- **A-5**: The surfaces this specification governs are those an **authenticated** commercial actor
  reaches. Sign-in and recovery are deliberately out of scope, and this is a boundary rather than an
  omission. `KHEPRI-DEC-025` §2 authorizes **one** external-authentication route at
  `EXTERNAL_SESSION_PATH` (`runtime/external_auth_api.py`), and §3 states that **"Khepri implements
  no credential replacement and no password recovery for a Clerk-backed account"**, holding
  `R5-02`…`R5-04` deferred while Clerk owns credentials. A shell specification that governed a
  sign-in or recovery surface would either restate that authority or contradict it, and would
  reintroduce at the surface layer exactly the second-definition problem `FR-041` forbids at the
  resolution layer. `R8-01`'s surface map lists `sign-in` and `recovery` under the shell prefix;
  their **addresses** may sit there, but what they do is governed by `KHEPRI-DEC-024`/`-025` and
  `RCA-001` `FR-002`, not by this document. If credential ownership ever returns to Khepri —
  `-024` §13's fourth exit path — that is the event that reopens this assumption.

## Verification

- Tests cover all 23 scenarios above, each named for the scenario it verifies.
- A non-disclosure test asserts that scenario 2, scenario 5's three inputs, and scenario 8 produce
  byte-identical responses apart from any per-request identifier — proving indistinguishability
  rather than asserting each in isolation. This covers `FR-050`.
- A **separate** content test asserts what a single denial contains, independent of comparison
  against any other denial: no object identifier, type, ownership, or timestamp. This covers
  `FR-052`, and exists because the indistinguishability test above passes even when every denial
  leaks the same field.
- A structural scan asserts no shell template contains an inline `style` or `script` attribute, and
  **carries an emptiness assertion** so a renamed template directory fails loudly rather than
  scanning nothing.
- A structural scan asserts no shell module defines a membership, actor, or scope resolution
  Protocol of its own, with the same emptiness assertion.
- A parity test asserts every surface renders in both languages with equivalent state, and that
  every copy key exists in both.
- Target-size measurement extends the existing journey browser test to the shell, both languages,
  every supported viewport.
- Each guard is mutation-tested: a mutant that removes the organization comparison, one that names
  the organization in a denial, one that renders a refusal missing a part, and one that renders an
  uncited report must each be killed by a named test.

## Implementation preconditions

Approval of this specification satisfies precondition 1 only.

1. This specification is `active` in `governance/registry.yaml`.
2. `RCA-001`'s own implementation preconditions remain met, and the merged `R6`/`R7` authorization
   and bridge work remains the single canonical checkpoint.
3. The first implementation slice names which surfaces it delivers and asserts the absence of the
   others, so an unimplemented surface is proven absent rather than merely unwritten.

**No decision is required on the browser security policy.** `R8-01` left this open, and reading the
shipped policy closes it: `SECURITY_HEADERS` is already `default-src 'none'` with per-directive
`'self'`, no inline source admitted anywhere, `frame-ancestors 'none'`, and
`Cache-Control: private, no-store`. There is nothing a commercial session needs loosened, and
`private, no-store` matters **more** for an authenticated organization-scoped response than for a
pseudonymous one. The question "same or different?" therefore has an asymmetric answer — identical
is correct and any divergence would be a weakening — which is a requirement (`FR-045`), not a
decision. If a future surface genuinely needs a directive the journey does not, `FR-045`'s
strict-narrowing clause is the path, and widening would need its own authority.
