# RRA-012: Governed Data-Display Component Layer

## Outcome

The report and evidence surfaces render every governed figure, qualification, refusal, and version
through **one** shared set of data-display components — a KPI figure, a status badge, a quality
summary, a refusal panel, an evidence link, a version label, and a coverage indicator — and an
evidence drawer that presents a metric's definition and citation beside the figure it explains.

A reader sees the same figure presented the same way across those surfaces, and a slice adding a new
customer-visible figure has one place to render it rather than a fourth hand-built markup block.

**Two boundaries are stated here rather than discovered by an implementer.**

**The journey surface is not part of this claim.** The component layer cannot reach a journey page —
that surface loads one stylesheet this specification may not touch, for the reason the Scope note
records — so extending the layer there is a later `RRA-010` slice.

**The drawer's *structure* is governed here; the *supply* of its catalog data is not.** Every surface
in Scope is a stored artifact, so supplying a catalog read means changing the materialization path —
a three-implementer renderer contract, three `build_context` callers, the pipeline, and both wirings,
including an Excel renderer that displays no HTML component. That is a different subject, it is
deferred to its own slice under its own authority, and the Scope note records the full enumeration.
This specification governs what the drawer renders and how it behaves, given its data.

**This specification adds no figure, no wording, and no calculation.** Every value these components
display already exists: the figures are `RRA-004`'s and `RRA-008`'s, the words are `RRA-009`'s and
`RRA-011`'s, and the catalog data the drawer reads is `RRA-011`'s. This governs the *presentation
components* those authorities' outputs are rendered through, and nothing else. A slice under it that
computes a figure, authors a customer-visible word, or invents a code is outside it.

**Why this authority is needed, stated plainly.** `RRA-011` merged a metric catalog with six read
routes, and **no template consumes any of them** — verified on `main` at `a2805f9`: no rendered
surface references `catalog/quality`, `catalog/citations`, or `catalog/metrics`. The catalog answers
questions no reader can currently ask. The roadmap's `U1-02` and `U1-04` name that gap, and no active
specification governs the files they would touch: `RRA-011`:69-73 governs the catalog *data* and
expressly disclaims the surfaces consuming it, because two active specifications over one path fails
closed under `AGENTS.md`. This specification is the receiving authority for those surfaces, in the
same shape `RRA-010` receives the journey-presentation surface `RCA-002` excludes, and `RRA-011`
itself received the catalog.

**The family choice is `RRA` and it is not arbitrary.** The surface this specification governs —
`src/khepri/rra/rendering/templates/`, where the report and its evidence region are rendered — is an
`RRA` path, as is the journey surface a later `RRA-010` slice would extend.
`governance/families/RRA.md` owns "deterministic retail facts, grounded bilingual narrative, and
consistent report surfaces", and a component layer delivering *consistent report surfaces* is that
sentence. An `RCA` specification could not govern these files: `RCA-002`:134 excludes any change to
the `RRA` journey's routes, templates, and assets, so an `RCA` authority over `RRA` rendering paths
would contradict an active specification on the day it merged.

**One surface is deliberately left out, and the omission is the point.** The commercial shell's own
component layer — `shell.css` and `shell-components.css`, built under `R8-07` and linked by
`src/khepri/runtime/shell_templates/` and `legal_templates/` — is **not** governed here. Those files
serve `RCA`'s authenticated commercial surfaces. Governing both from one document would put a single
specification across two families' surfaces, which the one-family rule in
`governance/templates/specification.md` forbids. Whether the two layers should later share tokens is
a real question and it is **not answered here**; answering it needs its own artifact naming both
families' paths. Until then each surface keeps its own components, and this specification governs
only `RRA`'s.

## Scope

This specification governs a component layer over surfaces that already exist:

- `src/khepri/rra/rendering/templates/` — the report and evidence templates, including
  `_evidence.html.j2`, `report.evidence.html.j2`, `report.html.j2`, and `report.pdf.html.j2`. These
  are named by no active specification: `RRA-010` names only `rendering/html.py`, and only to place
  it outside itself.
- **A new stylesheet for this component layer**, under `src/khepri/rra/rendering/`, linked by the
  templates above. It is new rather than an extension of `journey.css`, which is `RRA-010`'s.
- `tests/` — parity, fail-closed, and no-duplicate-truth tests over the components.

**Two boundaries were drawn wrongly in an earlier draft of this document and are corrected here,
because both made this specification authorize work it could not deliver.**

**1. The journey templates are NOT in scope.** An earlier draft claimed
`journey/templates/report.html.j2` and `review.html.j2` for presentation-only component adoption.
That is unimplementable: `journey/templates/base.html.j2` loads exactly one stylesheet,
`/beta/assets/journey.css`, which this specification excludes as `RRA-010`'s, and `RRA-010`:88
excludes *"a new route, address, or asset filename; a change to the asset allowlist"*. So a new
component stylesheet could not reach a journey page without violating an active specification, and
adoption there would have been advertised but impossible. **Component adoption on the journey
surface therefore needs an `RRA-010` slice wiring the asset, and is not authorized here.** This
specification governs the report and evidence surfaces only.

**2. The evidence drawer's catalog read is NOT in this specification, and three review rounds are
why.** The drawer was originally required here to read the `RRA-011` catalog (an earlier `FR-096`).
Every surface this specification governs is a **stored artifact**: `report_api.py`'s four surface
routes each return `artifact_response(job_id, ...)`, so nothing renders per-request and no template
can call a route. Delivering a catalog read therefore means threading a prepared projection through
the whole materialization path, and that path was enumerated exhaustively rather than guessed:

- `render_materialized` has **three** implementers — `html.py:318`, `pdf.py:168`, `excel.py:466` —
  behind one Protocol at `report_artifacts.py:143` that `pipeline.py:270` calls uniformly. Widening
  that contract touches the Excel renderer, which renders no HTML component at all.
- `build_context` has **three** callers — `html.py:345`, `pdf.py:213`, and `report_api.py:1004`,
  which is the catalog route's own audit read.
- Both production wirings construct all three renderers (`local/wiring.py`, `runtime/wiring.py`).

That is a materialization-path change wearing a component layer's name. Successive drafts widened
Scope from one file to two to seven while still calling the opening narrow, and a specification whose
Scope grows under review until it spans the render pipeline is not the bounded artifact it claims to
be. **The catalog read is therefore deferred to its own slice under its own authority**, where the
projection's call path, the `render_materialized` contract change, and Excel's pass-through behaviour
can be governed as the subject rather than as an aside.

**What that leaves is still worth merging**: the component set, its chrome vocabulary, parity,
fail-closed rendering, and the drawer's structure and keyboard behaviour — everything `U1-02` needs,
and the presentation half of `U1-04`. The drawer renders the definition and citation data it is
given; *how* that data reaches it is the deferred slice's subject.

**3. The components need labels, and no existing authority provides them.** `RRA-011`'s vocabulary
covers what a **code** means — descriptions, synonyms, unsupported interpretations — and `RRA-009`
covers what a refusal or caveat **says**. Neither authors the chrome a component needs to name
itself: the evidence-drawer control, and the labels for definition, inputs, coverage, and the
answered / caveated / refused groupings. An earlier draft excluded `wording.py` outright while FR-095
forbade this specification from authoring any customer-visible word, which left an implementer
shipping unlabeled components or widening beyond authority. FR-095a authorizes exactly the component
layer's own chrome labels, and nothing that describes a metric, a refusal, or a caveat.

## Requirements

Numbering continues from `RCA-004`, which ends at `FR-091`.

### The component set

- **FR-092**: The layer MUST define exactly one component for each of: a governed figure with its
  unit and precision; a status badge; an analysis-quality summary; a refusal panel; an evidence
  link; a version label; and a coverage indicator. A second component rendering the same concept is
  a duplicate source of presentation truth and is refused.
- **FR-093**: Every component MUST render from values it is given and MUST NOT compute, round,
  re-round, reformat, or derive any figure. Precision arrives with the value; a component applying
  its own is outside this specification. This mirrors `RRA-011`:204 and is stated again here because
  a presentation layer is exactly where re-rounding reappears.
- **FR-094**: A component receiving a code it has no governed rendering for MUST fail closed with the
  governed refusal, and MUST NOT fall back to the code string, to an empty element, or to a blank.
- **FR-095**: Every customer-visible word describing a **metric, refusal, caveat, population, or
  version** MUST come from `RRA-009`'s or `RRA-011`'s existing vocabulary. This specification authors
  none of them and restates none of them.
- **FR-095a**: The component layer MAY author its own **chrome labels** — the visible and accessible
  text a component needs to name itself, such as the evidence-drawer control and the labels for
  definition, inputs, coverage, and the answered / caveated / refused groupings. These MUST live in
  `wording.py` beside the existing tables, MUST be bilingual, and MUST carry the same import-time
  completeness assertion the tables around them use. **A chrome label names a region of the
  interface; it never describes a metric, a refusal, or a caveat** — the moment a word would explain
  what a figure or code *means*, FR-095 governs it and it belongs to `RRA-009` or `RRA-011`.

### The evidence drawer

- **FR-096**: The drawer MUST render the definition, governed version, inputs, coverage, and citation
  **it is given**, for one figure, beside that figure. This specification governs the drawer's
  structure, labelling, and behaviour; **how that data reaches the renderer is deferred** to the
  slice named in the Scope note above, and no slice under this specification may add a route call, a
  new renderer contract, or a bundle re-read to supply it.
- **FR-096a**: Where a field is **absent** — which the catalog does deliberately, returning
  `inputs: None` for derived comparison, growth, basket, and concentration figures, because no
  retained record states them — the drawer MUST render a governed unavailable state for that field
  and MUST NOT invent, infer, or recompute it, and MUST NOT present the field as empty. An absent
  field is not a refusal and MUST NOT be labelled as one. This is FR-097's discipline applied to a
  second case: the catalog declines to state something, and the surface says so rather than filling
  it in.
- **FR-097**: The drawer MUST NOT display a population or basis for an individual figure.
  `RRA-011`'s Outcome records that a `Fact` carries no population identifier; presenting one per
  figure would be the fabricated relationship that specification declines to invent. Package-level
  population reporting is permitted exactly as `RRA-011` serves it.
- **FR-098**: The drawer MUST be reachable by keyboard, dismissible by keyboard, and MUST return
  focus to the element that opened it.

### Parity and consistency

- **FR-099**: Every component MUST render correctly in both languages with right-to-left parity,
  under `RRA-006`'s existing parity rule.
- **FR-100**: A component MUST NOT communicate meaning through color alone; a status, refusal, or
  caveat MUST carry a text or non-color indicator.
- **FR-101**: Where a figure appears on more than one surface **in this Scope** — the web report, its
  evidence region, and the print surface — it MUST render through the same component on each. A test
  MUST prove no surface in Scope renders a governed figure through hand-built markup that bypasses
  the layer — **and that bounded test is authorized here**, notwithstanding the Exclusions' entry on
  visual-regression tooling and surface-inventory guards, which excludes `U1-07`'s general tooling
  and not this one requirement's proof. **This requirement does not reach the journey surface**, which is outside Scope; a
  figure rendered there stays as it is until an `RRA-010` slice wires the asset.

## Exclusions

This specification authorizes none of the following, and a slice claiming it does is outside its
specification within the meaning of Constitution IV:

- Any new metric, population, formula, reason code, caveat code, or figure. It renders what
  `RRA-004`, `RRA-008`, `RRA-009`, and `RRA-011` already govern.
- Any calculation, re-derivation, re-rounding, or re-formatting of a published figure.
- Any new customer-visible word that **names or describes a metric, refusal, caveat, population, or
  version**. Those are `RRA-009`'s and `RRA-011`'s. The component layer's own chrome labels are
  authorized by FR-095a and are the sole exception; a label that explains what a figure or code
  *means* is not a chrome label.
- **Any icon, typeface, or third-party asset.** Asset admission is governed separately, exactly as
  `RCA-002`:134 records, and is not granted here.
- **Any new telemetry event, of any kind.** Content-free or not. Active `KHEPRI-DEC-015` forbids
  product-analytics use of commercial identity data, and `RRA-010`, `RCA-003`, and `RRA-011` each
  exclude new telemetry events under their own authority. `T1-07` and `R8-08` remain blocked pending
  an owner-authored amendment; this specification authorizes no exception.
- **The commercial shell's component layer**, its stylesheets, and its templates. Those are `RCA`'s,
  per the Outcome.
- A chart grammar, a chart type, or any charting behavior. `U1-03` names that work and it needs its
  own authority; nothing here admits a chart.
- Global navigation, filter bars, a dashboard, a reports index, or report history. `U1-05` names the
  first two and the rest describe durable retention, which no active decision grants.
- Visual-regression tooling, and general surface-inventory guards over surfaces this specification
  does not govern. `U1-07` names that work separately. **The single bounded test FR-101 requires is
  authorized**, and is not what this entry excludes.
- Any new route, any change to an existing route's contract, and any change to what the catalog
  serves.
- Any retention, expiry, or deletion behavior, or any presentation implying a retention guarantee the
  system does not make.

## Verification

- Tests prove each component renders in both languages with right-to-left parity, is keyboard
  reachable, and communicates no status through color alone.
- Tests prove an unknown metric, reason, caveat, or version code fails closed with a governed refusal
  rather than rendering the code string, an empty element, or a blank.
- A test proves no surface in Scope renders a governed figure through hand-built markup that bypasses
  the component layer, and that test derives its expectation independently rather than from the
  layer's own registration.
- A test proves the drawer displays no per-figure population or basis.
- A test proves an absent field renders its governed unavailable state rather than an empty element,
  driven by a derived-family figure whose `inputs` the catalog returns as `None`.
- A test proves every chrome label FR-095a authorizes exists in both languages, through the same
  import-time completeness assertion the surrounding tables use.
- A test proves no component computes, rounds, or reformats a value, by rendering a figure whose
  precision differs from the component's default and asserting the given precision survives.
- The normal repository gates pass: `uv run khepri-gov validate`, `uv run ruff check .`, and
  `uv run pytest`.

## Implementation preconditions

1. `RRA-012` is `active` in `governance/registry.yaml`.
2. The implementation slice identifies itself as `U1-02` or `U1-04` and remains within this
   specification. `U1-03`, `U1-05`, `U1-06`, and `U1-07` are **not** authorized here.
3. `RRA-011`'s catalog routes are merged and serve the definition, citation, and quality data the
   drawer reads. Satisfied at `bc96a65` (`#343`).
4. No slice under this specification edits `html.py`, `pdf.py`, `excel.py`, `report_artifacts.py`,
   `pipeline.py`, or the renderer wiring. Supplying the drawer's catalog data is the deferred slice's
   subject, per the Scope note above. **Component adoption on the journey surface is likewise not
   authorized here** and needs an `RRA-010` slice wiring the asset.
5. A slice's only addition to `wording.py` is the component layer's own chrome labels, under FR-095a,
   carrying the import-time completeness assertion the surrounding tables use. A missing or wrong
   metric, refusal, or caveat word is a defect against `RRA-009` or `RRA-011` and is fixed there.

Identity, state, document, dependencies, and supersession are authoritative in
`governance/registry.yaml`.
