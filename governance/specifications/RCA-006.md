# RCA-006: Organization Semantic-Query Orchestration

## Outcome

An authenticated owner or member may request one exact semantic-view version over sources in one
organization. RCA scopes and loads the sources, RRA validates and projects them, and no result is
retained.

## Scope

- `src/khepri/rca/semantic_queries/` -- the future organization semantic-query orchestration
  boundary.
- `tests/` -- independent contract tests for that boundary.

No route, runtime wiring, template, shell asset, public API, migration, cache, background job,
renderer, or existing workspace file is governed.

## Request flow

```text
Request: actor + organization + exact view identity/version + source identifiers + explicit dimensions/filters
RCA work: canonical authorization + organization-scoped source reads + uniform unavailable behavior
RRA work: definition lookup + validation + no-calculation projection + view refusal/empty/result
Result: exact view/source identities + effective request + governed projected state
```

The future RCA implementation calls an injected protocol and does not import a concrete RRA
implementation, following `rca/workspace/comparisons.py`'s `ComparisonAssembly` precedent.

## Requirements

- **FR-145**: Every request resolves the actor and organization through canonical `RCA-001`
  authorization before reading a source or invoking RRA.
- **FR-146**: Every named source is loaded through the requesting organization's opaque scope;
  absent, deleted, corrupt, or cross-scope sources return the same content-free unavailable outcome
  without identifying which condition held.
- **FR-147**: RCA passes only successfully scoped governed sources and the explicit request to an
  injected `RRA-014` protocol, and returns its refusal, empty outcome, or result without
  calculation, relabelling, filtering, or state suppression.
- **FR-148**: A semantic query is derived at read time and writes no database row, object,
  artifact, cache, preference, history entry, tombstone, or deletion evidence; losing a source
  makes a later query unavailable.
- **FR-149**: The path emits no new audit or product-telemetry event, counter, access record, or
  content-bearing log; request parameters and result content do not enter existing logs.
- **FR-150**: Cross-organization, missing, deleted, exact-version, no-write, no-event, and
  no-concrete-RRA-import behavior are independently tested, including byte-identical unavailable
  outcomes and zero writes.

## Retention, privacy, and telemetry

The query is derived at read time. It retains no request, result, source copy, preference, history,
cache, tombstone, deletion evidence, audit record, product-telemetry event, counter, or access
record. Request parameters and result content do not enter existing logs.

## Exclusions

This specification authorizes no surfaces or routes; calculation or projection semantics;
persistence or retention changes; product telemetry; cross-organization joins; sharing or export;
raw-row access; schedules; or edits to `RCA-001`, `RCA-005`, or `RRA-014` source paths.

## Invariants

- `RCA-001` remains the canonical authorization checkpoint for every request.
- `RCA-005` remains the source of organization-scoped version and run lookup, including its
  unavailable behavior for deleted sources.
- `RRA-014` remains the sole authority for exact-version definition lookup, semantic validation,
  no-calculation projection, and view refusal, empty, or result state.
- Unavailable source conditions are uniform, content-free, and byte-identical.
- No semantic query introduces a write, retention record, event, or concrete RRA dependency.

## Verification

- A real two-organization request proves that a source outside the requester's opaque scope returns
  the same content-free unavailable outcome as an unavailable source within it.
- Deleted-source and missing-source requests each prove that the unavailable outcome is
  byte-identical.
- A write-count assertion spans every injected store and proves that every request writes zero
  records.
- An audit and telemetry absence assertion proves that the path emits neither event type, counter,
  access record, nor content-bearing log.
- A static import-boundary assertion proves that the RCA package imports no concrete RRA
  implementation.

## Implementation preconditions

1. `RCA-001`, `RCA-005`, and `RRA-014` are active in `governance/registry.yaml`.
2. An implementation slice identifies itself as the RCA half of `SV1-04` or the isolation/no-write
   half of `SV1-07` and stays within the future package and test scope above.
3. The slice uses injected protocol orchestration, canonical authorization, opaque organization-
   scoped source reads, and the uniform unavailable outcome without adding any retention or event.

Identity, state, document, dependencies, and supersession are authoritative in
`governance/registry.yaml`.
