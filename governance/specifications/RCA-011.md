# RCA-011 — The shell serves its own typeface

**Status:** PROPOSED. This document governs nothing until the sole owner merges it to `main`
(`governance/CONSTITUTION.md` §II). It was drafted by automation, which "checks facts and
consistency; it does not approve changes or act as a separate authority" (§I).

**Family:** `RCA`.
**Depends on:** `RCA-010`.

---

## Why this document exists

`RCA-010` `FR-204` names typography as a comparison dimension. `#489` applied the shell's own
typeface token — `shell.css:158`'s `--font-body` — and found that the face it names cannot load:

| Fact | Verified at `7fc4ff9` |
|---|---|
| Where the `.woff2` files live | `src/khepri/rra/rendering/typefaces/` |
| Who serves them | `add_journey_routes` only, at `/beta/assets/{name}` (`journey/routes.py:129`) |
| Does the deployed app mount `add_journey_routes`? | **No.** `runtime/wiring.py:580-593` mounts commercial, external-auth, legal, landing and shell — not journey |
| What the shell serves | three stylesheets, by exact name (`shell_api.py`'s `_ASSETS`) |
| What a shell page therefore renders in | `"Segoe UI", Tahoma, sans-serif` — the token's fallback |

So the `@font-face` rules in `journey.css` point at `/beta/assets/…woff2`, **which 404s in the
deployed image**. Linking `journey.css` from a shell page would add a failing request, not a font.

**This is not a defect in `#489`.** The cascade falling through to the next available family is the
token working as written, and the shell renders in the intended *class* of typeface. What is
missing is the specific face.

## Why `RCA-010` cannot answer it

Three separate clauses, each independently blocking:

1. **`shell_api.py`'s asset allowlist** — `RCA-010` §Scope: "Not in scope: `src/khepri/runtime/
   shell_api.py` and every other `src/khepri/runtime/*.py` module."
2. **An `@font-face` in `shell-components.css` naming `/beta/assets/`** — `FR-201`: "A slice names
   no custom property, class, or **asset whose authority sits with the journey**." It would also
   404, so it fixes nothing.
3. **Mounting `add_journey_routes` in the deployed app** — §Scope excludes "the composition root".

No slice under `RCA-010` can wire the face. That is the gap this document exists to close, and
closing it is the owner's to approve.

## Scope

This specification governs **the shell's typeface assets and nothing else**:

- `src/khepri/runtime/shell_api.py` — **the asset allowlist only.** Adding the two typeface entries
  to `_ASSETS` and the media type they need. No route, no handler, no destination, no capability,
  no authorization path, no read, and no change to any existing entry.
- `src/khepri/rra/journey/assets/shell-components.css` — the `@font-face` rules that name the
  shell's own asset address. Presentation only, as `RCA-010` §Scope already admits for this file.
- `tests/` — evidence that the face is served, that it is served from the shell's own address, and
  that the shipped image carries it.

**Not in scope:** every other `src/khepri/runtime/*.py` module, `journey.css` and the `/beta`
surfaces (`RRA-010`'s), the composition root, the `RRA` rendering surfaces, the landing surface,
migrations, object storage, and every route, orchestration and persistence path in the repository.
**No existing `_ASSETS` entry is altered or removed**, and no journey address is named.

## Requirements

Numbering continues from `RCA-010`, which ends at `FR-206`.

- **FR-207**: The shell serves its own typeface from its own address. The two Noto Sans Arabic
  subsets ship as package data and are served by exact name through the shell's existing allowlist
  mechanism, not by directory listing, so a file added to either package is not served by arriving.
- **FR-208**: A shell stylesheet names no journey address. The `@font-face` rules the shell links
  resolve to the shell's own asset path. `FR-201` is unchanged and unrelaxed: this document moves
  the *asset* into the shell's ownership rather than permitting the shell to reach into the
  journey's.
- **FR-209**: No external reference is introduced. No `@import`, no font host, no CDN, no runtime
  download. The files are the ones already verified against the repository's SHA-256 typeface
  manifest by `rendering/fonts.py`; this document adds no new font and changes no digest.
- **FR-210**: The fallback chain survives. `--font-body` keeps its full declaration, so a surface
  that cannot load the face still renders in a sans family rather than a serif default. The
  requirement is that the face becomes available, not that the fallback becomes unnecessary.
- **FR-211**: Serving a typeface adds no capability. No authorization path, no session read, no
  telemetry, no access record, and no content-bearing log. The asset route answers the same way for
  every caller, and the shipped Content Security Policy is unweakened.

## Verification

- The two typeface files are served from the shell's own asset address, by exact name, and an
  unknown name is refused.
- No shell stylesheet contains a `/beta` address, asserted by a scan with an emptiness assertion.
- The shipped wheel carries both files as package data — asserted against the built image, not
  against a hand-wired fixture, because a route absent from the image passes every fixture test
  (`W1-07a`'s defect).
- `getComputedStyle(document.body).fontFamily` still names the full `--font-body` chain, so
  `FR-210` holds and the existing `#489` regression test stays passing.
- `RCA-010`'s `FR-200` and `FR-204` evidence still passes unchanged across every shell surface and
  legal page, in both languages, at both viewports. **A typeface change moves text metrics**, so
  the whole browser matrix is re-run rather than the typography case alone — `#489` found a latent
  overflow exactly this way.
- No route, handler, destination or capability changed, by static scope evidence over the
  authorized paths.
- The normal repository gates pass: `uv run khepri-gov validate`, `uv run ruff check .`, and
  `uv run pytest`. Every new file scores 10.00 in the required CodeScene review.

## What this document deliberately does not decide

- **Whether shell surfaces may adopt journey components generally.** That is the owner's filed and
  untaken `RRA-010` journey-adoption reading, and it stays open. This document moves two font files
  into the shell's ownership; it says nothing about the journey's stylesheets, components or
  surfaces, and it is not a precedent for them.
- **Whether `add_journey_routes` should be mounted in the deployed image.** It is not, and this
  document does not change that. If the `/beta` surfaces are ever deployed, they keep serving their
  own assets from their own address.
- **`workspace.css`'s undeclared `--font-sans` and `--font-mono`.** Seven `var()` calls whose
  fallback always wins, recorded in `#489`. A token-declaration question, not an asset one.
