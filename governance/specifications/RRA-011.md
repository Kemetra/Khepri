# RRA-011: Metric, Population, and Reason Catalog

## Outcome

Every metric, population, refusal reason, and caveat code the governed calculation already emits has
one discoverable, versioned, read-only definition — its code, unit, population, formula version,
bilingual business name, and the evidence path a reader follows to check it — assembled from the
constants that already govern those codes and never restated beside them.

A customer can ask what a published figure means, which rows it was computed over, which version
computed it, and what qualified or refused it, and receive an answer derived from the same
declaration the calculation itself used. They can also ask, of one package, what it answered, what it
answered with a caveat, and what it refused — an aggregation of outcomes the package already carries,
expressing **availability and never certainty**.

`RRA-004` governs what a metric *is* and `RRA-008` what a family *computes*; `RRA-009` governs what a
code *says* to a customer. None of them governs the surface that lets a reader *discover* those
answers, and the roadmap's `T1` track names that gap. This specification is the receiving authority
for it, in the same shape `RRA-010` receives the journey-presentation surface `RCA-002` excludes.

**This specification adds no arithmetic and no business meaning.** It catalogs. A slice under it that
computes a figure, invents a code, or decides what a code means is outside it.

## Scope

This specification governs a catalog over calculation that already exists:

- `src/khepri/rra/definitions.py` — the read-only registry: definition records for metric,
  population, reason, and caveat codes, assembled at import from the governed constants that already
  declare them, and the per-package outcome summary derived from an existing report projection.
- `src/khepri/rra/report_api.py` — read routes exposing the registry, the summary, and a fact's
  evidence, session scoped exactly as their existing siblings are.
- `src/khepri/rra/rendering/wording.py` — bilingual names, descriptions, and supported and
  explicitly unsupported interpretations for codes the catalog surfaces, and the import-time
  completeness assertions that keep them whole.

**Outside this scope, and unchanged by it:** `facts.py`'s arithmetic, `populations.py`'s population
semantics, and every `analysis/*.py` formula. This specification reads their exports. A slice that
edits what they compute is an `RRA-004` or `RRA-008` slice wearing this one's name.

**The surfaces that consume this catalog are governed elsewhere, and deliberately not named here.**
`src/khepri/rra/journey/` is `RRA-010`'s by its own Scope, and the shell's closed surface set is
`RCA-002`'s. This specification governs the *data* those surfaces may read; claiming their files
would put two active specifications over one path, which `AGENTS.md` fails closed on. A slice adding
a journey link is an `RRA-010` slice; a slice admitting a shell surface is an `RCA-002` slice. Each
may read this catalog without this specification naming its files.

Three tests bound every change, and a change failing any one is outside this specification however
small it looks:

1. **Derivation.** Every code the catalog can return already exists as a governed constant in a
   module this specification does not govern. The catalog states no code of its own.
2. **Read-only.** The change computes no figure, admits no row, and writes no governed artifact. A
   catalog surface answers from what a package already carries.
3. **Single truth.** The change adds no second place where a code, its unit, its population, or its
   meaning is written down by hand. Where one already exists, a slice under this specification may
   remove it; it may never add one.

Test 3 is the load-bearing one, and it is stated against *hand-maintenance* rather than against
duplication in general. A derived copy computed from the governed source at import is not a second
truth — it is the same truth read twice. A retyped list is a second truth even when it is correct on
the day it is written, because nothing makes it wrong when the source moves.

## Requirements

- Assemble the registry at import from the governed constants and frozensets that already declare
  each code — `facts.py`, `populations.py`, and the `analysis/*` modules for metrics, populations,
  reasons, and caveats. The registry MUST NOT declare a code that does not already exist as a
  governed constant in a module outside this specification's scope.
- Carry on each definition only attributes an existing declaration already states: the code, the unit
  kind and precision its `_fact()` call site declares, the population `RRA-004` assigns it, the
  governed version constants, and the bilingual business name `RRA-009`'s tables already hold. An
  attribute no existing declaration states MUST NOT be added here; it needs its own governed source
  first.
- Refuse a code the relevant governed frozenset does not contain. A lookup MUST fail closed with a
  governed refusal rather than synthesize a definition, and MUST NOT fall back to the code string as
  its own name.
- Expose exactly one evidence projection per fact. A catalog route MUST read the projection the
  report surfaces already render from, never assemble a second one from the bundle directly.
- Carry an import-time completeness assertion on every bilingual table this catalog surfaces to a
  customer, against the governed code set it serves, in the shape `_assert_metric_wording_complete`,
  `_assert_refusal_wording_complete`, and `_assert_caveat_wording_complete` already use.
- Scope every read route to its session through the same caller resolution its sibling routes use,
  and render Business- and Audit-tier fields only. No Internal-tier field may appear on a catalog
  surface, including `section.state`, which `RRA-009` excludes from the audit region for this reason.
- Prove the registry equal, in an automated test, to the union of the governed sets it draws from, so
  that a code added to a source module without reaching the catalog fails rather than silently
  narrowing it. The test MUST derive its expectation independently rather than reading the registry's
  own assembly.
- Reduce, and never increase, the number of hand-maintained code lists in the repository. Where this
  specification's registry makes an existing retyped list redundant, the slice that introduces the
  registry replaces that list with the derived one.
- State, for one produced package, which results it published, which it published with a caveat, and
  which it refused and why — read from the sections, caveats, and reason codes the package already
  carries. This summary is **an aggregation, never a measurement**: it counts and groups outcomes
  that already exist and computes no figure of its own.
- Express availability, and never certainty. The summary and any pre-analysis
  capability-availability contract derived from it MUST report only whether an analysis is
  *available* on the admitted data, and MUST NOT publish a confidence score, a quality score, a
  likelihood, a completeness percentage, or any other invented measure of how good a result is. A
  reader learns what the system can and cannot answer, not how much to trust an answer it gave.
- Derive the summary from the same projection the report surfaces already render from, so a section
  refused in the report is refused in the summary by construction rather than by a second reading of
  the bundle.

## Exclusions

This specification authorizes none of the following, and a slice claiming it does is outside its
specification within the meaning of Constitution IV:

- Any new metric, population, formula, reason code, or caveat code. This catalogs what `RRA-003`,
  `RRA-004`, `RRA-008`, and `RRA-009` already govern and invents none of it.
- Any calculation, re-derivation, re-rounding, or re-formatting of a published figure. A catalog
  surface repeats a value; it never recomputes one.
- Source-to-surface lineage, and any lineage-specific data model. That is `T1-06`'s and needs its own
  slice; nothing here may require a lineage record to satisfy the completeness proof above.
- **Any new telemetry event, of any kind.** Content-free or not, an event recording that a definition
  was read, an evidence surface was opened, or a quality summary was viewed is outside this
  specification. Active `KHEPRI-DEC-015` forbids product-analytics use of commercial identity data,
  and active `RRA-010` and `RCA-003` each exclude new telemetry events under their own authority.
  `T1-07` and `R8-08` remain blocked pending an owner-authored amendment; this specification
  authorizes no exception to it.
- A pre-analysis Impact Preview step, or any new workflow state, step, or journey phase. The
  availability contract the Requirements authorize is **data**; rendering it as a new journey phase
  is a new phase, which `RRA-010` excludes and which needs a specification naming it. An
  already-authorized step may read this contract; a new step to display it may not be added here.
- Any confidence score, quality score, trust score, completeness percentage, or other invented
  measure of how good a result is. The summary reports availability and outcome counts only.
- An editable return-to-mapping or Fix & Continue capability.
- Any change to `RRA-006`'s bundle binding, cross-surface reconciliation, retention, expiry, or
  deletion behavior, and any presentation implying a retention guarantee the system does not make.
- Any new member of the shell's closed authenticated surface set. Admitting one is `RCA-002`'s, and
  this specification supplies only the data such a surface would read.
- Any admissibility change, mapping re-interpretation, or customer-authored definition. A definition
  here is read from governed code; a customer may not write one.
- Any write route, request-shape change, or status-code change on an existing surface.

## Invariants

### Single truth

- No code, unit, population, or version acquires a second hand-maintained representation. The
  registry is derived; where it replaces a retyped list, the retyped list is deleted in the same
  slice.
- A published figure has exactly one definition and one evidence path. Two catalog surfaces
  describing one figure MUST agree because they read one projection, not because they are checked
  against each other.

### Privacy and isolation

- Session isolation and the opaque-owner boundary are unchanged. A catalog surface gains no
  identifier and reveals no cross-session state.
- No customer content, filename, raw source value, or Internal-tier field reaches a catalog surface.
- Operational telemetry remains content-free, and this specification emits no event of its own.

### Bilingual

- Arabic and English remain equal surfaces. Every name, description, and interpretation the catalog
  exposes exists in both, asserted at import rather than left to a reader to notice.
- A code with no accepted wording in either language is not exposed by the catalog at all, rather
  than exposed under its raw code string.

### Fail closed

- An unrecognized metric, reason, caveat, population, or version refuses. No catalog surface
  fabricates a definition, and none degrades to the code string as a display name.

## Verification

Tests cover: registry key sets equal to the union of the governed sets they derive from, proven
against an independently stated expectation; refusal on an unknown code at every catalog entry point;
bilingual completeness for every exposed table, asserted at import; a catalog surface and its
existing report sibling agreeing on the reason and caveat sets they state for one bundle; the outcome
summary reconciling against a package whose published, caveated, and refused results are counted
independently, and moving when one of them moves; absence of every Internal-tier field from every
catalog response; and session scoping identical to the sibling routes.

The repository gates apply: `uv run khepri-gov validate`, `uv run ruff check .`, and
`uv run pytest`. CodeScene Code Health Review is a required server-side gate on every pull request.

## Implementation preconditions

1. `RRA-011` is `active` in `governance/registry.yaml`.
2. `CAL1` is complete on `main`, so the constants this catalog derives from are the governed
   successor versions rather than a moving target.
3. A slice states which of the three scope tests it satisfies, and names the hand-maintained list it
   removes where its registry makes one redundant.
