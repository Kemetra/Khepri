# RRA-003: Retail Data Profiling and Admissibility

## Outcome

The system produces a content-minimized profile and an explicit retail column mapping, then
admits only normalized posted retail events that can support governed retail facts.

## Profiling and mapping requirements

- Profile schema, row count, null rate, distinctness, numeric ranges, date coverage, and
  parse-quality findings without exposing raw values in operational logs.
- Detect likely personal-data columns and exclude them from narrative and reporting inputs.
- Map source columns to governed retail semantics with confidence, evidence, a safe display label,
  and an explicit source-contract declaration.
- Distinguish required, optional, unavailable, ambiguous, and conflicting mappings.
- Reject datasets with no admissible time field, no answerable core retail measure, irreconcilable
  types, or unresolved ambiguous mappings needed by the requested report.
- Preserve the accepted profile, source-contract or attestation identity, input digest, and
  mapping version as fact-package provenance.

## Normalized event contract

Every row used by a governed calculation is one normalized retail event carrying:

- a transaction date;
- an event kind of `sale` or `return`;
- a status proving `posted`, or an explicit `void` or `cancelled` status that excludes the row;
- exactly one normalized uppercase ISO 4217 currency for every monetary measure in the package;
- additive row-level measures, never averages, rates, unit costs, cumulative values, plans,
  forecasts, or repeated invoice totals; and
- the event-identity proof required below.

Event kind, status, currency, and every measure basis must be supplied by an explicitly mapped
source column or by a package-level declaration bound to a recorded source contract. A package
declaration may establish that all rows are sales only when the extract contract excludes returns,
that all rows are posted only when it excludes void and cancelled events, or that all monetary
values use one named currency. Generic headers and observed values never establish event kind,
status, currency, gross/net basis, VAT treatment, additivity, allocation, or coverage.

An unknown or missing event kind, status, currency, or required identity proof refuses every
affected population rather than silently excluding rows. Explicitly void and cancelled events are
excluded from every population. Missing, malformed, or mixed currency refuses monetary facts and
their derived results but does not suppress independently proven count-only facts. Khepri performs
no currency conversion.

## Event and transaction identity

Source-event identity is proven in exactly one of these ways:

1. a stable event or line key, including an admitted composite key, is unique within the package;
2. the source contract explicitly attests unique line-grain rows and the package has no repeated
   canonical row signature across all admitted identity, dimension, and measure fields.

A repeated event key, whether identical or conflicting, refuses every additive or
distinct-transaction result that could include it. Without an event key, a repeated canonical row
signature has the same effect because a legitimate repeated line cannot be distinguished from a
duplicated extract. Repeated products or categories in one transaction remain valid when their
event identities differ.

Every posted sale row used for transaction-dependent facts must carry a canonical transaction
key. A bare source transaction identifier qualifies only when its recorded source contract proves
package-wide uniqueness. Otherwise the canonical key is an admitted composite containing the
source identifier and every field required for uniqueness, normally store, business date, and
terminal or register. Missing components or collisions refuse transactions, AOV, items per
transaction, and attach rate. Neither row count nor a partial identifier substitutes for the
canonical key.

## Governed measures

### Revenue and returns

`revenue` is signed, VAT-exclusive, net realized sales at event posting date:

- sale revenue is non-negative after every line, invoice, promotion, loyalty, and markdown
  discount;
- return revenue is non-positive and is recognized on the return posting date;
- VAT, sales tax, duties, tips, shipping, fees, commissions, and surcharges are excluded;
- void and cancelled events contribute nothing; and
- no exchange-rate conversion is performed.

A directly mapped revenue column must explicitly declare this basis. Generic `revenue`, `sales`,
`amount`, `total`, `grosssales`, VAT-inclusive, or tax-inclusive labels are ambiguous by
themselves. This contract does not reconstruct net revenue from gross sales, tax, discount, and
return components.

`returns` is the positive VAT-exclusive net sales-reversal magnitude derived from admitted return
revenue: for each posted return event, `return magnitude = -return revenue`. No independently
mapped return-amount measure is admitted. Gross merchandise value, tender or tax refunds, fees,
exchange value, and restocking charges cannot substitute. Full and partial returns use their
posting date and never rewrite an earlier sales period. If event-kind coverage proves no return
events, returns is zero; absence of event-kind evidence cannot establish zero.

A return event with missing event kind or revenue, or with revenue whose sign violates this
contract, refuses returns and the financial revenue population. Return units are required only for
unit-dependent facts, so missing return units do not suppress independently proven return revenue.
Revenue comparisons include posted returns; price/volume growth excludes any window containing a
return.

### Discounts

`discount` is a non-negative additive informational amount on sale events. It includes line,
allocated invoice, promotion, loyalty, and markdown discounts only when the source already
prevents overlap and allocates every invoice-level amount exactly once. It never changes governed
revenue, which is already net. A bare discount, rate, percentage, repeated invoice total, or
overlapping component set is refused.

Every posted sale row carries a non-negative discount, including explicit zero, or the package
carries an admitted declaration that no discounts occurred or that discounts are not captured.
Proven absence states zero. Not-captured coverage refuses discounts without refusing independently
proven net revenue.

### Cost and gross profit inputs

`cost` is signed, extended row-level cost of goods sold, VAT-exclusive and in the package
currency. Sale cost is non-negative; return cost is non-positive when inventory value is restored;
and a proven zero-cost item may carry zero. Unit, average, standard, or list cost and a bare
ambiguous `cost` label are non-additive and refused. Gross profit, gross margin, and standalone
cost require complete revenue and extended-cost coverage over the identical financial population.

### Units

`units` is signed physical merchandise movement. Ordinary and free or bonus sale units are
positive, return units are negative, and a sale or return event with zero units refuses
unit-dependent facts. Fractional quantities are refused, never rounded, while independently
proven monetary and dimension facts survive. Headline units are net movement including returns;
ASP and basket calculations use positive posted-sale units only, including free or bonus items.

## Coverage-manifest confirmation

Completeness-dependent comparisons require a separate source-provided or explicitly
operator-attested coverage manifest. It is versioned, bound to the exact input digest, and records:

- covered start and end dates and the reporting timezone;
- the complete store roster, or the identity of one governed aggregate scope;
- every covered `(store or aggregate scope, calendar date)` pair;
- included event kinds and statuses;
- the source-contract or attestation identity and its evidence; and
- every known extraction gap, store closure, and partial terminal boundary.

An attested closure proves complete zero activity; an extraction gap does not. A date spine,
observed minimum or maximum date, equal row or day counts, and absence of events never synthesize
coverage proof. Without a valid manifest, observed trends may survive, but completeness-dependent
period comparisons and growth refuse. When no store dimension is mapped, the manifest must
explicitly identify one store or one already-governed aggregate scope.

## Stable contract and version

`rra003.mapping.v3` succeeds `rra003.mapping.v2`. It governs the semantic declarations, event and
canonical transaction identities, normalized measures, currency, and coverage-manifest
confirmation in this specification. Existing mappings and packages retain their recorded versions
and are not reinterpreted.

## Exclusions

Free-form semantic analysis, arbitrary customer formulas, opaque automatic guessing, raw-row
transfer to an LLM, currency conversion, fractional quantities, and ungoverned normalization
shapes are excluded.

## Verification

Tests cover golden schemas, type conflicts, missing columns, ambiguous generic headers,
personal-data exclusion, event and transaction identity collisions, normalized measure signs and
bases, currency, status and event-kind declarations, coverage-manifest binding, fail-closed
admissibility, independently surviving facts, and deterministic reruns.
