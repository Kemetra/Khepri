## 1. Design

### 1.1 The migration owner is the role that runs Alembic (D-1)

The migration does not create a migration-owner role. The migration owner is whichever role runs
`alembic upgrade`, and it owns every table today. Locally and in CI that is the bootstrap superuser
`khepri`; hosted, it is whatever role `OPS1` provisions. The migration creates the other four.

**Why.** Creating an owner role inside a migration needs a superuser to grant it `BYPASSRLS` (only
a superuser may), every table's ownership transferred to it, and a bootstrap credential to log in
as it, all of which are `OPS1`'s provisioning. Verification 6 still discriminates: "no role but
the migration owner holds `BYPASSRLS`" is asserted over the five roles, the owner identified as
`pg_tables.tableowner` of `rra_beta_sessions`. In CI that owner is a superuser, which `FR-270`
does not forbid. Open question Q1 asks whether the owner wants a named, non-superuser owner role.

### 1.2 The four created roles (`FR-270`)

| Role | Created as | Password in the migration |
|---|---|---|
| `khepri_app` | `LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOINHERIT` | none |
| `khepri_worker` | same | none |
| `khepri_sweep` | same | none |
| `khepri_definer` | `NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOINHERIT` | none |

Each is created in a `DO $$ ... IF NOT EXISTS (SELECT FROM pg_roles ...) $$` block, because roles
are cluster-wide and parallel test databases share them. An existing role is not altered (changing
`SUPERUSER` or `BYPASSRLS` needs a superuser, which a non-superuser owner is not): the migration
checks its attributes and raises if any is wrong, which fails closed. It is never dropped. The downgrade drops policies,
functions and grants and **never drops a role**. Passwords are set by test fixtures
(`tests/rra017_support.py`), by `ops/local/khepri-runtime-roles.sql` for the two compose stacks,
and hosted by `OPS1`. Names are literal in the migration (0035's rule: no import from the model).

### 1.3 Policies (`FR-232`, `FR-269`, `FR-264`, `FR-271`)

The setting is `khepri.owner_id` (D-2). Every covered table gets `ENABLE` and `FORCE ROW LEVEL
SECURITY`. The scope expression is `owner_id = NULLIF(current_setting('khepri.owner_id', true),
'')`. `NULLIF` is what makes the pooled-connection case fail closed: after an earlier transaction's
`SET LOCAL`, an unset read returns `''`, and `owner_id = ''` would match an empty-owner row.

| Policy | Tables | For | To | Expression |
|---|---|---|---|---|
| `rra_owner_scope` | the 8 with `owner_id` | `ALL` | app, worker | scope expression, `USING` and `WITH CHECK` |
| `rra_parent_scope` | the 4 of `FR-269` | `ALL` | app, worker | `EXISTS (SELECT 1 FROM public.<parent> p WHERE p.<key> = <table>.<key>)`, both clauses |
| `rra_definer_read` | `rra_beta_sessions`, `rra_report_jobs` | `SELECT` | definer | `USING (true)` |
| `rra_sweep_read` | `rra_beta_sessions`, `rra_uploads`, `rra_deletion_evidence` | `SELECT` | sweep | `USING (true)` |
| `rra_sweep_purge` | `rra_deletion_evidence` | `DELETE` | sweep | `USING (true)` |

The `EXISTS` runs under the invoking role's own policy on the parent, so a child is visible and
writable exactly when its parent is. Column grants (§2.4) narrow the two permissive roles. All
policies are `PERMISSIVE`; none names `PUBLIC`.

### 1.4 The four definer functions (`FR-264`, `FR-265`, `FR-267`)

All four are `LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public, pg_catalog, pg_temp`,
name every relation `public.`-qualified, take `timestamptz` or `text`, never SQL text, and are
owned by `khepri_definer`. `EXECUTE` is revoked from `PUBLIC` and granted as §2.4 lists.

| Function | Returns | Body (each mirrors a Python statement) |
|---|---|---|
| `rra_session_owner(p_session_id text)` | `text` | `SELECT s.owner_id FROM public.rra_beta_sessions s WHERE p_session_id <> '' AND s.session_id = p_session_id` |
| `rra_next_claimable_job(p_now timestamptz)` | `TABLE(job_id text, owner_id text)` | `claimable_at(now)`'s four clauses, `ORDER BY available_at, job_id LIMIT 1`, no lock |
| `rra_expired_lease_jobs(p_now timestamptz)` | same | `state = 'running' AND lease_expires_at <= p_now`, `ORDER BY lease_expires_at, job_id` |
| `rra_orphaned_jobs(p_now timestamptz)` | same | `session_id IN (deleted-content sessions) AND state NOT IN ('succeeded','dead_lettered')`, `ORDER BY queued_at, job_id` |

`rra_orphaned_jobs` takes `p_now` and does not read it: `FR-267` names the signature, and the
Python predicate it mirrors has no time clause (Q6). The functions are created by the migration
owner and then given to the definer: the migration grants the definer `CREATE` on `public` and, if
the runner is not a superuser, grants the runner membership in the definer; it runs `ALTER FUNCTION
... OWNER TO khepri_definer`; and it revokes both grants in the same migration, as `FR-264`
allows. `pg_temp` is listed last explicitly; PostgreSQL never searches it for functions or
operators, and operators resolve through `pg_catalog`, which precedes it (Q7).

`claimable_at` stays the one definition (`#518`). Verification 16 holds each body equal to its
Python clauses by seeding one job per clause, and fails until a changed clause ships a migration
that replaces the function. Phase 2 names the two recovery predicates as module-level clause
tuples beside `claimable_at`: `expired_lease_at(now)` and `orphaned_at()` in
`khepri.rra.job_persistence`, which `recover_expired`'s re-read and `recover_orphans`'s re-read
both use.

### 1.5 The scope mechanism (`FR-233`): the central decision (D-3)

**Chosen: an explicit owner per store verb, plus an explicitly entered unit for the paths that
span several store calls.** The setting itself is always issued inside the store verb's own
transaction, as that transaction's first statement on a covered table.

The parts, all in two new RRA-side modules (`khepri.rra` stores need them, and `khepri.rra` may
not import `khepri.runtime`):

- `khepri/rra/scope.py`
  - `acting_for(owner_id)`: a context manager over a `ContextVar[UnitScope | None]`. It sets the
    unit's owner, and resets its token in `finally`. Entering it with a different owner while one
    is bound raises `ScopeConflict` (`FR-265`: "a scope already set is never replaced").
    `acting_for_unresolved()` binds the explicit "no scope" state a `NULL` lookup produces.
  - `scoped_begin(factory, owner_id=None)` and `scoped_read(factory, owner_id=None)`: open the
    store verb's transaction, resolve its owner (rules below), and issue
    `SELECT set_config('khepri.owner_id', :owner, true)` first on PostgreSQL.
  - `apply_scope(session, owner_id)`: for a verb that joins an ambient RCA `unit_of_work` session
    (`retain_workspace_content`, `RawUploadRetentionSweeper._delete_row`). It sets the scope with
    a database-side never-replace check: `CASE WHEN coalesce(current_setting(...), '') NOT IN
    ('', :o) THEN NULL ELSE set_config(..., :o, true) END`, and raises `ScopeConflict` on `NULL`.
  - `ScopeRequired`, `ScopeConflict`, and the tripwire key the runtime engine reads (§1.6).
- `khepri/rra/definer_calls.py`: the only module that calls the four functions.
  `SqlSessionOwners(factory).owner_of(session_id)`, `session_owner(session, session_id)`,
  `next_claimable(session, now) -> (job_id, owner_id) | None`, and `RecoveryCandidates(factory)`
  with `expired(now)` and `orphaned(now)`. Each gates its SQLite fallback **by dialect**:
  PostgreSQL calls the function; SQLite runs the Python statement it mirrors; any other dialect
  raises. Verification 8's PostgreSQL half proves the PostgreSQL path calls the function.

**The rules a transaction's owner is resolved by.**

1. A verb whose arguments carry an owner (`scope`, `owner_id`, a record, a job, a `LeaseRequest`)
   uses it. If a unit is bound to a different owner, or bound unresolved, it raises
   `ScopeConflict`.
2. A read of `rra_beta_sessions` by `session_id` alone, and every `*_for_session(session_id)` read
   (`#152`'s), calls `rra_session_owner` first, in the same transaction. If a unit is bound, a
   `NULL` or different answer raises `ScopeConflict` and the scope stays the unit's. If not, a
   `NULL` returns "no such row" without reading, and an owner is set and read under (`FR-265`).
3. A verb with neither (`JobReader.find`, `SqlDeliveryStore.find_delivery`, `find_surfaces`,
   `deliver`, `SqlArtifactRepository.has_complete`, `is_committed`, `list_evidence`, the lease
   verbs when the request carries no owner) uses the bound unit's owner.
4. An unresolved unit runs the transaction with no setting: reads see nothing and writes are
   refused (`42501`), which every caller already reads as an unavailable session.
5. Nothing bound and nothing supplied: on PostgreSQL the tripwire raises `ScopeRequired` (§1.6);
   on SQLite the verb runs as today, since SQLite has no policy and nothing to set.

**Why not ambient state alone, or `after_begin`.** An `after_begin` hook can only apply a scope that
exists when the transaction starts. `FR-265`'s bootstrap must look up, set and read inside one
transaction, and the RCA `unit_of_work` already holds an open session when `_purge_scope` and
`retain_workspace_content` reach an RRA row. A hook keyed only by ambient state would also make a
forgotten scope silent: the policy returns nothing, which is `FR-238`'s hazard. Explicit owners
cover the 41 transaction sites the static test lists (§2.2), and the unit is entered at a handful
of named boundaries (§1.5.1), each visible in code review.

**Why it cannot leak.**

- **Across threads and requests.** A `ContextVar` is per thread and per asyncio task. Starlette's
  `run_in_threadpool` runs each sync handler in a copied context, so a value set inside a handler
  dies with it. The beta middleware sets and resets its value in its own coroutine around
  `call_next`. `ClaimWorkerLoop` is one long-lived thread, and its job unit is a `with` block per
  job, reset in `finally` even when the job raises.
- **Across pooled connections.** The database setting is `set_config(..., true)`, which is
  transaction-local by definition, so a pooled connection carries no scope past `COMMIT` or
  `ROLLBACK` (Verification 4 and 12 prove `''` on the same backend afterwards). The `ContextVar`
  is never read at connect or checkout, only when a verb opens a transaction.
- **Beyond the transaction (`FR-233`).** The `ContextVar` names the unit, never the database
  state; every transaction sets the database state afresh.

**How a forgotten scope fails: closed, and loudly.** Closed: the policy hides every row and refuses
every write. Loudly: on the application and worker engines the tripwire raises `ScopeRequired`
before the statement reaches the database, so a forgotten scope is a 500 and a log line, never an
empty page or a silent "not a workspace". The static half of Verification 12 also fails CI on any
`khepri.rra` transaction that bypasses the helper.

### 1.6 The tripwire (D-4)

`khepri/runtime/scope_tripwire.py` attaches to the application and worker engines (never the sweep
engine, which is cross-scope by design) a `before_cursor_execute` listener. It derives the tables a
statement touches from the compiled construct (`sqlalchemy.sql.visitors.iterate` over
`context.compiled.statement`), not from SQL text. If any is covered and the connection's scope
marker for this transaction is unset, it raises `ScopeRequired`. The helper sets the marker when it
sets the scope or binds "unresolved"; a `begin` listener clears it, so each transaction starts
unmarked. `src/khepri` holds one `text()` statement (`pg_advisory_xact_lock`, RCA), which touches
no covered table. SQLite engines and test-built engines carry no tripwire, which keeps Verification
8's SQLite suite exactly as it is.

### 1.7 The guard and the recorder (`FR-266`)

- `BetaMembershipGuard` gains an `owners` port (`SqlSessionOwners`) and drops its `sessions` port,
  so it reads no covered table. A cookie whose lookup is `NULL` is refused with RRA's `401
  {"detail": "Session is unavailable."}`. No cookie still reaches the route. An owner no
  organization owns still reaches the route.
- `RecorderReads` gains `owners`. `_workspace_of` raises the new
  `SessionScopeUnresolved(LookupError)` when the lookup is `NULL` or the scoped
  `get_session_for_owner` after it is empty, and returns `None` only for a resolved scope that
  `_scopes.exists` denies. `admitted` and `requested` therefore raise instead of silently recording
  nothing; their request-path callers turn that into the unavailable-session response they already
  give.

### 1.8 The worker and recovery (`FR-267`, `FR-268`)

- `ClaimingReportQueue._next_claimable` and `ClaimablePoller.next_job_id` call `next_claimable`,
  which returns `(job_id, owner_id)`. `receive` leases with `LeaseRequest(owner_id=...)`.
- `SqlReportJobRepository` gains a `candidates: RecoveryCandidates | None` constructor argument,
  defaulting to one over its own factory (the worker's case; tests unchanged).
  `recover_expired`/`recover_orphans` take candidates from it, then per candidate open a scoped
  transaction that re-reads `FOR UPDATE SKIP LOCKED` under `expired_lease_at(now)` or
  `orphaned_at()`, skips a candidate the re-read no longer matches, transitions it and writes its
  `rra_report_job_attempts` row exactly as today, and isolates a fault to that candidate (`#523`).
- Order is unchanged: `ClaimWorkerLoop.run_once` recovers before it claims, from one clock reading.

### 1.9 The sweep composition (`FR-271`)

`build_retention_sweep(stack, *, sweep_factory)` and the new `khepri.local.wiring.build_sweeper(
stack, *, sweep_factory)` build the sweep over two factories. The sweep engine goes to exactly four
components, each a constructor argument:

| Component | Module | Reads |
|---|---|---|
| `ExpiredSessionLister` | `khepri.runtime.retention_sweep` | `(session_id, owner_id)` of expired sessions |
| `DueUploadLister` | `khepri.runtime.workspace_retention` | `_due`'s statement, unchanged in shape |
| `SqlDeletionRepository` (the `DeletionEvidenceSweeper`'s purge store) | `khepri.rra.persistence` | `purge_evidence_before` |
| `RecoveryCandidates` | `khepri.rra.definer_calls` | the two recovery functions |

Everything else is on the scoped (application-role) engine: the sweep's own `DeletionService`,
built by a shared `build_deletion_service(factory, objects)` that `build_stack` also uses so expiry
deletes exactly as the request route does; the per-candidate recovery transitions; `_purge_scope`
and `_delete_row`; and every RCA sweeper. The sweep is no longer handed `stack.services.deletion`.
`build_retention_sweeper` gains a `sweep_factory` keyword.

### 1.10 `khepri-envelope-migrate` refuses under the policies (`FR-272`)

`run(stack)` first asks the database, on PostgreSQL, `SELECT row_security_active('public.
rra_report_artifacts') OR row_security_active('public.rra_uploads')`. PostgreSQL's own function
answers exactly "this connection is subject to these tables' policies", with no role-name
heuristic. If true, it prints one content-free refusal line, no count, and returns non-zero. SQLite
runs as today.

### 1.11 Every connection proves its role (D-5)

`khepri/runtime/db_roles.py` is the only module that calls `create_engine`. `engine_for(url,
role)` attaches a `connect` listener that runs `SELECT current_user, r.rolsuper, r.rolbypassrls
FROM pg_roles r WHERE r.rolname = current_user` and raises `RoleMismatch` unless the user is the
role's literal name and neither attribute is set. An environment that still hands the runtime the
owner's or a superuser's credential therefore refuses to start its first transaction instead of
silently bypassing every policy. `DatabaseRole` is an enum of the three login roles; each
composition root names its members literally, which is what Verification 7 reads.

### 2.5 How later migrations stay covered (D-6)

**Each migration grants its own, and a catalogue-derived test enforces it. No `ALTER DEFAULT
PRIVILEGES`.** Default privileges would hand the application and the worker DML on a new table the
moment it is created, before its policy exists: fail-open, against Constitution V. Instead:

- `test_every_covered_table_enables_and_forces_row_security` derives the covered set from the
  catalogue (every `rra_` table with an `owner_id` column, plus `FR-269`'s four), so a new owned
  table without `FORCE` and its policy fails.
- `test_every_table_grants_each_scoped_role_exactly_dml` derives every table from the catalogue, so
  a migration that forgot its grants fails (and so does every feature test on that table as the
  application role).
- `test_no_default_privilege_is_left_for_any_runtime_role` pins that no default ACL exists.
- Verification 9 (`FR-231`) fails a new `rra_` table without `owner_id` until it is classified.

## 7. Design decisions

| ID | Decision | Reason |
|---|---|---|
| D-1 | The migration owner is the role that runs Alembic; the migration creates four roles | §1.1. Creating an owner needs a superuser and `OPS1`'s provisioning; Verification 6 still discriminates over the five |
| D-2 | `set_config('khepri.owner_id', :owner, true)`, not literal `SET LOCAL` | `SET LOCAL` takes no bind parameter (psycopg cannot bind a utility statement), and interpolating an `owner_id` is an injection seam. PostgreSQL documents `set_config(..., true)` as `SET LOCAL`. Verification 4 and 12 prove the property behaviourally (same backend, `''` afterwards) |
| D-3 | Explicit owner per verb, plus a named unit at the boundaries of §1.5.1 | §1.5 |
| D-4 | A construct-based tripwire on the application and worker engines only | Makes a forgotten scope loud where the policy would make it silent; absent on SQLite, so Verification 8's suite is unchanged |
| D-5 | Every connection checks its own role at connect | A runtime handed the owner's credential would bypass every policy without a symptom |
| D-6 | Per-migration grants, enforced by a catalogue test; no default privileges | §2.5: default privileges fail open before a table's policy exists |
| D-7 | Existing PostgreSQL tests move to the migrated schema, migrate-once, truncate-per-test | One schema definition; about 3.4 s once rather than per test |
| D-8 | `SqlDeletionRepository` itself is the evidence purge store on the sweep engine | `FR-271` names it; a new class would be an interpretation. Its other verbs would only be refused there |
| D-9 | All four definer calls live in `khepri/rra/definer_calls.py`, each SQLite fallback gated by dialect | One place to audit what crosses the policy before a scope exists |
| D-10 | `REVOKE CREATE ON SCHEMA public FROM PUBLIC` in the migration | `FR-234` and `FR-264`'s `search_path` rest on it; a no-op on PostgreSQL 15+, needed below |
| D-11 | Role names are literals: `khepri_app`, `khepri_worker`, `khepri_sweep`, `khepri_definer` | 0035's rule: a migration never imports the model. The tests state them independently |
| D-12 | `khepri-envelope-migrate` refuses on `row_security_active(...)` | PostgreSQL's own answer to "subject to the policies"; no role-name heuristic |
| D-13 | Redemption is outside the beta unit middleware | A stale cookie must not stop a new redemption; redemption sets its own minted owner (`FR-233`) |

  runs Alembic (D-1); `OPS1` decides hosted whether that is a dedicated non-superuser role.
- **Q2. `FR-233` says `SET LOCAL`; the slice uses `set_config(..., true)`.** **Recommend:** accept as
  the same mechanism (D-2). If the owner reads `FR-233` literally, the alternative is a `SET LOCAL`
  with a validated, quoted literal, which is worse.
- **Q3. "Refused" for a re-pointing `UPDATE`.** The specification defines refused for `UPDATE` as
  zero rows affected, but an `UPDATE` that re-points A's own row is visible to `USING` and fails
  `WITH CHECK`, which PostgreSQL raises as `42501`. **Recommend:** Verification 3's re-point case
  asserts `42501`; the B-row cases assert zero rows.
- **Q4. Which suites does Verification 13 mean?** **Recommend:** the store suites and journey
  suites §4 names, rerun as the application role through one fixture, with the routes through
  `postgres_journeys`. If the owner wants every RRA test file rerun, the slice grows by roughly
  forty fixture edits.
- **Q5. The guard refuses a cookie whose lookup is `NULL`, including an expired or deleted session's
  stale cookie that today reaches the route and gets the route's own refusal.** The status and body
  are the same `401 "Session is unavailable."`, so no client sees a difference. **Recommend:**
  accept.
- **Q6. `rra_orphaned_jobs(now)` does not read `now`.** **Recommend:** keep the signature `FR-267`
  names; the parity test pins the predicate, which has no time clause.
- **Q7. Operators in the definer bodies are not schema-qualified.** `FR-264` asks for every relation
  and function to be qualified. **Recommend:** qualify relations and functions; leave operators to
  the pinned `search_path` (`pg_catalog` before `pg_temp`, which PostgreSQL never searches for
  operators). Writing `OPERATOR(pg_catalog.=)` throughout is possible if the owner wants it.
- **Q8. The worker role also gets the application role's DML on RCA tables.** `FR-270` says "the
  application role's table reach", and the pipeline recorder writes RCA runs and audit events from
  the worker. **Recommend:** accept; RCA tables carry no policy either way (Open item 1).
- **Q9. Recovery moves from one transaction for all candidates to one per candidate.** `FR-268`
  requires it. A test that asserted all-or-nothing recovery would change; none does at `0c1475f`.
  **Recommend:** accept.

## 9. Size

One PR. It cannot sensibly split (RRA-017 forbids it), and it fits: roughly 55 files and 6,500 to
7,500 lines, more than half of them tests. Production: the migration (about 350 lines), four new
modules and two sweep listers (about 450), store and service edits across 16 existing modules
(about 400 changed), config and compose (about 250). Tests: the RED files committed here (about
2,700 lines), the connection-model and config tests (about 300), the Verification 13 fixture and
suite parametrizations (about 200), and the existing PostgreSQL tests' schema change (about 100).

## 10. Constraints the RED tests put on phase 2

The PostgreSQL RED bodies have not executed at `0c1475f` (every one stops in setup), so these are
pinned here rather than discovered:

- The scope statement is `SELECT set_config('khepri.owner_id', :owner, true)`: the setting name
  literal, the owner bound. `scope_set_by` accepts the name in the text or bound either way.

  against RCA's constraints; adjust the seed, not the property, if they are refused.
