# Plan: #593 profile outlives its upload; #594 revocation takes effect everywhere

Owner decisions: 2026-09-26, recorded on #593 and #594. One PR, one commit per change. Merge is the
owner's: this PR carries governed text and touches auth, tenancy and retention.

## #593: `rra_dataset_profiles.upload_id` → `rra_uploads`, `ON DELETE SET NULL`

- **Grant.** `KHEPRI-DEC-033` §1 names only packages and reports as outliving the raw upload. This
  slice adds one paragraph naming the dataset profile, in the migration's commit.
- **Migration `20260926_0033`.** It makes `upload_id` nullable, then sets dangling ids to NULL (the
  sweeper already leaves them), then creates a single-column `fk_profile_upload`.
  - The downgrade refuses while a profile has outlived its upload.
  - The head pins move: the single-head test, `STATUS.md`, and `RCA_UNREPLAYED`.
- **Tests** go in a new `tests/test_i593_profile_outlives_upload.py`:
  - the real retention sweep keeps the profile with a NULL `upload_id`;
  - a profile naming an absent upload is refused;
  - PostgreSQL: the key's shape, the orphan repair on upgrade, and both downgrade outcomes.

## #594a: the beta cookie stops working when membership is revoked

- **The defect.** The shell's journey entry and artifact handoff issue `khepri_beta_session`. After
  that, every `/api/v1/beta/*` route authorizes on it alone, so a revoked member keeps full access to
  the revoked organization's analysis scope.
- **The fix.** Runtime middleware in `build_web_app`, touching nothing in `khepri.rra` (R7-01).
  - For a beta session whose scope is a workspace (the classification `pipeline_recording` already
    uses), it requires a live `khepri_session`.
  - Then `resolve_scope(account, the organization owning the analysis's scope)` must succeed.
  - Otherwise it answers RRA's existing 401. Invitation sessions and redemption pass through
    unchanged (DEC-023).
- **Grant.** `RCA-001` FR-030: "A session whose active organization membership has been revoked MUST
  cease to authorize actions in that organization."
- **Owner decision (2026-09-26, after review).** The guard checks the analysis's *own* organization,
  not the active one, so a still-member who switches keeps their other tab.

## #594b: after a revocation, the user can choose another organization

- **The defect.** No route switches the active organization inside a session. The chooser's rows
  link to addresses that only compare against the active organization, so after a revocation every
  row lands on `unavailable`.
- **The fix.** A POST route calls `OrganizationSwitcher.switch` (FR-029), then redirects to the
  organization's entry surface. Each chooser row submits it. The visible text is unchanged.
- **Grant.** `RCA-002` gains a clause saying the chooser's selection switches through a POST that
  `FR-029` governs.

## #598: shell form POSTs answer 403 in real Chromium (found in review)

Under `Referrer-Policy: no-referrer` Chromium sends `Origin: null` on a same-origin form POST. The
same-origin check now admits `null` only beside `Sec-Fetch-Site: same-origin`. The owner chose to
carry this in this PR as its own commit, proved by a real-browser test on a loopback server.
