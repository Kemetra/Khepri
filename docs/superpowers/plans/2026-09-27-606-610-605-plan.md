# #606, #610, #605, #611: a locked read that returns a held row, a handoff that does not re-check, and a failure that re-checks visibility only

Product fixes under `RCA-005` (active): `FR-111` (a run bound to what it derived under), `FR-112`
(runs are append-only, one way, never twice) and `FR-127` (each concurrent failure mode fails closed
with the uniform denial). All four defects were found by `#608`'s PostgreSQL `journey()` (`#388`).
They are pinned there as strict `xfail`s, and this slice turns those pins green. No governance
artifact changes. No schema or migration changes.

## Root causes

### A. `#606` and `#610`: an ORM lock returns the row the session already holds

`SELECT ... FOR UPDATE` through the ORM, over a row whose primary key is already in the session's
identity map, returns **that object with its attributes unrefreshed**. SQLAlchemy's
`populate_existing` defaults to off. The lock is held, and `pg_stat_activity` shows the second
request waiting on it. What goes wrong is the decision after the lock is granted: the re-check reads
the state from before the wait.

The workspace store writes through the ambient unit of work (`unit_of_work.writing`). Every read
earlier in one `perform` therefore puts its rows in the session the lock later runs in.

- **`#606`.** `record_completion` peeks the run, locks the version, then locks the run and
  re-checks `state == started`. That re-check reads the peek's object, so a losing settlement passed
  it and was stopped only by the provenance table's primary key (`IntegrityError`).
- **`#610`.** The same re-check, reached while a failure held the run: the settlement completed a run
  that had already failed. `fail_run` writes no provenance row, so nothing collided, and the
  overwrite committed.

**Evidence (PostgreSQL 18, `#608`'s modules).** `.execution_options(populate_existing=True)` on
`run_for_update` **alone** turns the `#606` pin and the `#610` settlement pin into
`XPASS(strict)`. SQLite reproduces the mechanism with no second request:
`tests/test_i606_locked_reads_are_fresh.py`.
- Session A loads the row.
- Session B changes it and commits.
- A's locked read returns B's value only with the option.

A first draft of that test passed with the defect present. The identity map holds objects by weak
reference, so an unreferenced load had been collected. The test now holds the loaded object, as the
production caller's own earlier read does.

**Fix at the root: every lock statement refreshes.** `populate_existing` is applied to every
`with_for_update` in `src/khepri`, not only to the three named workspace locks. The defect is a
property of *an ORM lock after a load*, not of one statement. `tests/test_i606_every_lock_refreshes.py`
is an AST scan that fails if any `.with_for_update(...)` in `src/khepri` is not the direct receiver
of `.execution_options(populate_existing=True)`. It also refuses a lock taken through a
`with_for_update=` keyword, and it pins the number of lock sites (18) so that a new lock is added on
purpose.

**Autoflush holds, so the refresh discards no pending edit.** No module in `src/khepri` sets
`autoflush=False` or uses `no_autoflush`. A locked `SELECT` flushes the session first, so
`populate_existing` overwrites only attributes that match the database.

| Lock site | Runs in | Earlier load of the same row in that session? | Class |
|---|---|---|---|
| `rca/workspace/locks.py` `run_for_update` | ambient unit (`writing`) | yes: `record_completion`'s peek, `WorkspaceRecording._awaiting_run` | **defect** (`#606`, `#610`) |
| `rca/workspace/locks.py` `version_for_update` | ambient unit | possible: the unit reads versions before it seals, tombstones or starts a run over one | **same class**, proven by mechanism test |
| `rca/workspace/locks.py` `live_runs_for_update` | ambient unit | possible: the cascade's unit reads runs first | **same class**, proven by mechanism test |
| `runtime/workspace_retention.py` (via `session_scope_for_update_statement`) | the caller's ambient workspace unit | possible | same class; covered by the scan |
| `rca/persistence.py` `account_for_update`, `organization_owners_for_update`, `owner_memberships_for_update` | own `factory.begin()` | no; the lock is the first load of its entity (`unlink_external_identity_outcome` loads `ExternalIdentityRow` first, a different entity) | hardening |
| `rra/persistence.py` invitation, session, session-scope, deletion-job locks | own `factory.begin()` | no; the lock is the block's first statement | hardening |
| `rra/job_persistence.py` lease, `recover_expired`, `recover_orphans`, heartbeat lock | own `factory.begin()` or a passed database whose block starts with it | no | hardening |
| `rra/artifact_persistence.py`, `rra/deletion_persistence.py`, `rra/delivery_persistence.py`, `rra/telemetry_persistence.py` | the passed database | no earlier load of the same row in their callers | hardening |

### B. `#605`: the handoff acts on a session it never re-checks

`POST .../analyses/{run}/artifacts/{kind}` decides reachability in `_locate`
(`ProvenanceReader._resumable`: no `deletion_requested_at`, not past `content_expires_at`). It then
resumes the session through the bridge and sets the cookie of whatever comes back. A deletion
committing between the two left it answering `303` with a cookie for ended content.

**Where the pause sits.** `#608`'s `_paused_handoff` wraps the bridge in `PausedCall(..., "resume")`,
which waits *before* delegating. The deletion therefore commits before the real `resume` reads the
session, so a re-check of the session `resume` returns closes the window the test drives. A
deletion committing after that read is the legitimate "before" order: the handoff happened first.

**Fix.** There is one liveness predicate, `khepri.rra.sessions.content_is_live`: no
`deletion_requested_at`, and `now < content_expires_at`. It replaces the two copies already in
that module (`_live`, `require_upload_consent`), and both the provenance reader and the handoff call
it. The handoff folds it into its existing `resumed is None` refusal, with the handoff's own `now`.
`CommercialBridge.resume` does not change: `resume_analysis` and `record_analysis_consent` keep
their answers.

`tests/test_i605_handoff_rechecks_the_resumed_session.py` pins the decision on SQLite. A wrapper
returns the real resumed session with a deletion requested, or past its expiry, and the handoff must
answer the uniform 404 with no cookie. A control with nothing changed must still redirect with the
cookie.

### C. `#611`: failing a run re-checks visibility, not liveness

This is a separate root cause, not a stale row. `complete_analysis_run` re-checks under the run lock
with `_visible_in`, which reads the scope alone, where `record_completion` uses `_live_in`, which
also reads the tombstone and the revocation ledger. A run the cascade tombstoned while still
`started` passed that re-check and reached the write. The tombstone guard then raised `ValueError`
where the store should have refused (`False`).

**Evidence.** `#608`'s `test_the_failure_under_the_cascade_is_refused_not_faulted` flips on
`_live_in` alone, with `populate_existing` reverted, and stays `xfail` on `populate_existing` alone.
`tests/test_i611_a_failure_after_deletion_is_refused.py` pins the door on SQLite with no second
transaction: the deletion commits, then the run is failed.

**Fix.** A one-line guard change, `_visible_in` to `_live_in`, which makes both completion doors
state the same rule. `_visible_in` stays for the transitions that must still reach a tombstoned row:
an idempotent tombstone, and the terminal-state guard.

## Mutation

Each mutant removes one `populate_existing` and runs the tests against PostgreSQL 18. The file is
restored byte-for-byte after each one.

| Mutant | Red |
|---|---|
| `run_for_update` | `test_a_locked_read_sees_the_row_as_the_lock_found_it[run_for_update]`, the `#606` pin (`test_the_losing_settlement_is_refused_not_faulted`), and the `#610` pin (`test_a_settlement_waits_for_a_failing_run_and_does_not_complete_it`) |
| `version_for_update` | `test_a_locked_read_sees_the_row_as_the_lock_found_it[version_for_update]` |
| `live_runs_for_update` | `test_a_locked_read_sees_the_row_as_the_lock_found_it[live_runs_for_update]` |
| each of the four in `rra/persistence.py` (a hardening sample) | `test_every_lock_refreshes_the_rows_it_locks` |

Handoff mutants for `#605`, run against PostgreSQL 18:

| Mutant | Red |
|---|---|
| `_still_live` reduced to `resumed is not None` (the old check) | both `test_an_ended_resumed_session_is_refused_without_a_cookie` cases, and `#608`'s `test_a_late_handoff_issues_no_cookie_for_an_ended_session` |
| `content_is_live` ignores `deletion_requested_at` | the deletion-requested case, the `#608` pin, and `test_a_handoff_during_the_ending_does_not_hand_over_ended_content` |
| `content_is_live` ignores `content_expires_at` | the expired case, and `test_rra002_service.py::test_expired_session_is_rechecked_before_object_storage` (the journey's own copy of the rule, now this one) |

For a hardening site the scan is the only red test, by construction: no caller holds the row
first, so no behaviour changes. The scan exists to keep the rule universal, so the next lock written
after an earlier load is not the next `#606`.

The lock-inspecting modules run green on PostgreSQL with the fix in place: 322 passed and 1 xfailed.
The modules are the `rca001` lock, owner, revocation and advisory-lock suites, `rra001`, `rra002`,
`rra007`, `w102`, `w103`, `w104`, `w107b` and `w110_lifecycle_isolation`, plus both concurrency
modules.
