# `G4-02` / `G4-03` — what the two activations must say, prepared

**Authority:** none of its own, and this note **cannot** be the activation. `G4-02` and `G4-03` are
owner-authored specification amendments; the roadmap says so twice and §17 item 20 repeats it. This
note reads `RRA-004`, `RRA-008`, `RCA-005` and `KHEPRI-DEC-033` (all active) and prepares the text
an owner would otherwise draft cold.
**Roadmap:** §17 item 20. Prepares, does not close it.
**Raised on:** `main` at `38ee11e`, after `#394` landed `G4-01`'s scope note.
**Blocked by:** `Constitution VII` is absent (§17 item 21). Until it is restored, neither amendment
can cite the least-data article that `KHEPRI-DEC-033` §2 and `KHEPRI-DEC-015` §3 both route through
— and a comparison run's retention question (§3 below) is exactly a least-data question.

## 0. One correction to `G4-01` first

`G4-01` §5 (merged at `38ee11e`) records this obligation:

> `G4-02` should add the `Fact` field that records `COMPARISON_FORMULA_VERSION`, which
> `comparison.py` records as deferred and which `C1-03` would otherwise inherit as a governed gap.

**That is wrong, and `G4-02` should not carry it.** Both halves were already discharged:

| Claim | Reality |
|---|---|
| `Fact` needs the field | **`Fact.formula_version` exists** (`src/khepri/rra/facts.py:267`), a real field with a default, added when `APP-014` amended `RRA-004` to require it. Its docstring already argues "a hash names a fact and cannot be read back off one." |
| Nothing records it for comparison facts | **`comparison.py:603` sets `formula_version=COMPARISON_FORMULA_VERSION`** on the one `Fact` it constructs. Landed in `#81` — "record every fact's formula version." |

The `G4-01` note took `comparison.py`'s module docstring (lines 81–89: *"Nothing does today — no
section carries them and no bundle includes them"*) at face value. **That docstring is stale**, by
roughly three hundred PRs: `#77` derived the facts, `#81` recorded their version, and the prose was
never updated. `RRA-004`'s Fact-package provenance section likewise already requires each fact to
disclose "readable formula version".

**What remains is smaller and real.** `fact_identity()` is called with
`COMPARISON_FORMULA_VERSION` (`comparison.py:392`) while `Fact.formula_version` defaults to
`FORMULA_VERSION` (`rra004.formula.v2`) — two different constants, one hashed and one recorded. The
single construction site sets the field explicitly, so today they agree. **A second construction
site that omits the argument would silently stamp `rra004.formula.v2` onto a fact hashed under
`rra008.comparison.v2`**, and nothing would refuse it. That is a test obligation for `C1-03`, not a
specification amendment for `G4-02`.

> **Recorded as a lesson, not a slice.** A stale docstring asserting an open obligation is
> indistinguishable from a real one until you read the code it describes. `G4-01` cited the prose;
> this note read `facts.py:267` and `comparison.py:603`.

## 1. The split, and why it is two amendments

`G4-01` established that `C1`'s comparison is not a new calculation but a new **admission**: a run
whose input is two dataset versions. That divides cleanly along the family boundary already in the
registry, which is why one activation cannot do both:

| | `G4-02` | `G4-03` |
|---|---|---|
| Family | `RRA` | `RCA` |
| Document | `RRA-008` (amend) | `RCA-005` (amend) |
| Owns | What a comparison **fact** is, and when it refuses | Who may **ask** for one, and what is kept |
| Consumes | `RRA-004`'s population contract, unchanged | `G4-02`'s facts, plus `KHEPRI-DEC-033`'s matrix |

A single specification would have to depend on two families, which the validator rejects — a
`specification` must "depend on exactly one family" (`validator.py:302-308`). The split is
structural, not stylistic.

## 2. `G4-02` — the RRA comparison-fact amendment

**Amends `RRA-008`.** Its Outcome derives every fact "from **one** compatible `RRA-004` population
and retained basis." That sentence is the thing being widened, and it should be widened by
*addition* rather than by rewriting: a new section for the two-population case, leaving the
existing single-population guarantees untouched.

### 2.1 What it must add

1. **A two-population comparison fact.** Same `Fact` shape, no new type. Its `formula_version` is a
   new governed constant (`rra008.crossversion.v1` or similar) — **not** `COMPARISON_FORMULA_VERSION`,
   because a cross-version delta is a different derivation from a period-over-period one and must
   not be confusable with it by identity or by provenance.
2. **The six admission predicates from `G4-01` §4**, restated as refusal rules in `RRA-008`'s own
   voice: one organization scope, identical mapping / formula / package versions, same currency and
   the same governed aggregate scope or complete admitted store set, and complete coverage for both
   periods per the authoritative `RRA-003` manifest.
3. **The period rule (`G4-01` P-1).** Compared as stated, never aligned — no truncation, rescaling,
   or per-day normalization across two versions. It must say explicitly that this **does not**
   refuse a natural calendar length difference, because `RRA-008` already permits those and
   `G4-01`'s first draft got this wrong (`#394` review).
4. **A caveat and a refusal string per predicate**, bilingual, because `RRA-008`'s Verification
   already requires "bilingual caveat and refusal parity" and a new refusal cause without one
   fails that clause.

### 2.2 What it must not do

- **Not touch `RRA-004`.** The population contract, the `Fact` type, and provenance fields all
  stand. `G4-01` §5 already routes `Fact`-shape questions to `RRA-004`, and §0 above shows the one
  field people expected to be missing is present.
- **Not admit the prefix concession across versions.** `RRA-008` lets an incomplete current month
  compare a day-`1..k` prefix against a prior projection. Across two dataset versions that needs
  two reconciled coverage manifests, which nothing authorizes — so both periods must be complete.
- **Not admit N-way.** `G4-01` UC-4 defers it; pairwise is a table, N-way is a chart and
  `RRA-012`'s.
- **Not add a figure to any workspace surface.** That stays `RCA-005`'s first exclusion.

## 3. `G4-03` — the RCA orchestration amendment

**Amends `RCA-005`**, and this is the harder of the two, because it must **remove one of its own
exclusions** to do anything at all. `RCA-005` currently reads:

> Any calculation, comparison, aggregation or re-rendering of figures on a workspace surface.
> Comparison is `G4/C1`'s.

That deferral is what `G4-01` respected by not appending FRs there. `G4-03` is the artifact
entitled to narrow it — and it should narrow, not delete: the exclusion's *reason* (a workspace
surface does not calculate) survives, while comparison **orchestration** becomes admissible.

### 3.1 The four requirements it must add

`RCA-005` runs `FR-108`–`FR-129`, so these are `FR-130`–`FR-133`:

| FR | Requirement |
|---|---|
| **FR-130** | An owner or member of one organization may request a comparison of two dataset versions **in that organization**, and the request is refused with a uniform cause when either version is outside the scope — `RCA-005`'s isolation invariant, applied to a two-input read |
| **FR-131** | The request is refused, with the stated cause, when `G4-02`'s admission predicates do not hold; no partial or indicative figure is derived or shown |
| **FR-132** | A completed comparison is reachable from the Analyses surface with its two source versions named, each linking to the Passport that `FR-119` already requires |
| **FR-133** | One audit event per comparison request and per refusal, content-free, under `FR-125`'s existing shape and its twelve-month horizon |

### 3.2 The question `G4-03` cannot answer without the owner

**Is a completed comparison retained content?** `KHEPRI-DEC-033` §2's content matrix has no row for
it, and `KHEPRI-DEC-015` §4 forbids retaining a field "because it may become useful later." Two
readings, and the amendment must pick one **before** `FR-132` is written, because they produce
different surfaces:

| Reading | Consequence |
|---|---|
| **Derived at read time** | No new table, no new retention row, nothing to delete. The comparison is a query over two retained versions — the same argument `KHEPRI-DEC-034` §1 used for the activity view ("a view that stores no event is not an event stream"). Re-reading re-derives, so a deleted version makes the comparison unavailable rather than stale. |
| **Retained as a run** | A new content class needing a `KHEPRI-DEC-033` §2 row, an end trigger, a deletion cascade from either source version, and `FR-127`'s deleted-case test. Buys a stable citation identity and a comparison that survives its inputs. |

**The recommendation is derived-at-read-time**, on the least-data default — which is precisely the
article that is currently missing (§17 item 21). `KHEPRI-DEC-034` §3 made the identical choice by
citing "Constitution VII's least-data default," so this amendment would have to cite an article
that does not exist, or invent a different justification for the same answer. **That is the
dependency**: item 21 is not merely tidy-up, it is `G4-03`'s missing premise.

## 4. Ordering, and what it costs to get wrong

1. **Item 21 — restore `Constitution VII`.** `G4-03` §3.2 cannot cite least-data without it.
2. **`G4-02`.** Facts before orchestration: `FR-131` refuses on `G4-02`'s predicates, so the
   predicates must exist first. This is also the registry's own constraint — `depends_on` an
   unknown id is a validator error, so the RRA amendment's id must be registered before the RCA
   amendment names it.
3. **`G4-03`.**
4. **`G4-04`** freezes the contracts both produced.
5. **`C1-01`…`C1-08`.**

Reversing 2 and 3 produces an `RCA-005` requirement citing predicates no active artifact states —
which validates fine, because prose is not checked, and fails only when a slice tries to build it.
